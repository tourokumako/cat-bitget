## §0 全体方針

**アプローチ**: ML 主軸（LightGBM）+ k=2 全探索を並走（保険）

- ML を先に走らせる。結果が出るまでの間、k=2 全探索の設計は保留
- ML が不合格なら k=2 に切り替え、または ML + k=2 ハイブリッド
- CC の役割は「スクリプト実装・実行」。設計判断は Web Claude + まこさんが握る

## §1 ML 設計

### 1.1 ラベル（= ML に予測させる対象）

28 個全部を予測対象とする (2026-05-19 v3 改訂・旧 16 ラベル USD 絶対値版は archive):

- K 窓: K=6（30min）/ K=12（1h）/ K=24（2h）/ K=48（4h）/ K=96（8h）/ K=144（12h）/ K=288（24h）
- 方向: LONG / SHORT
- MFE / MAE (pct ベース・BTC 価格非依存)

各足（5m bar）ごとに 28 個の数値を予測するモデルを作る。

ラベル定義 (pct ベース・close[t] で正規化・BTC 価格非依存):
- `LONG_MFE_pct_K{K}`  = (max(high[t+1..t+K]) − close[t]) / close[t] × 100
- `LONG_MAE_pct_K{K}`  = (close[t] − min(low[t+1..t+K])) / close[t] × 100
- `SHORT_MFE_pct_K{K}` = (close[t] − min(low[t+1..t+K])) / close[t] × 100
- `SHORT_MAE_pct_K{K}` = (max(high[t+1..t+K]) − close[t]) / close[t] × 100

旧 USD 絶対値ラベル (`LONG_MFE(K) = max(high) − close` 等) は 2026-05-19 廃止 (価格非依存性違反・web_claude_self_check.md §価格非依存性 #1)。

ラベルデータファイル (pct 版・`build_labels_pct.py` で生成):
- train: `results/priority_rebuild/labels_mfe_mae_pct_train_2021_2024.parquet`
- test（仮テスト）: `results/priority_rebuild/labels_mfe_mae_pct_test_2025.parquet`
- 本テスト: `results/priority_rebuild/labels_mfe_mae_pct_test_2026_q1.parquet`
- 旧 USD 絶対値版 (4 ファイル) は `results/priority_rebuild/archive/` へ移動済 (leak 由来 + USD 絶対値で無効化・2026-05-19)

### 1.2 特徴量（= ML への入力）

1,432 指標全部を投入する。事前の絞り込み禁止。

指標カタログ: `indicator_catalogue.csv`（1,432 行 × 10 列）
カテゴリ: 1-A 指標値・推移（348）/ 1-B 値動きの形（347）/ 1-C 構造的要素（737）
時間軸: 5m / 15m / 30m / 1h / 4h / 1d（MTF）

### 1.3 モデル

**LightGBM**（回帰モード）

- 16 ラベルそれぞれに独立したモデルを作る（= 16 モデル）
- 初回はデフォルトハイパーパラメータで走らせる（数時間で結果を出す）
- 結果が見込みありなら、ハイパーパラメータ調整（数日）に進む

### 1.4 期間分割

BTC 4 年周期（2024 年半減期）と 2024 年以降の価格上昇を踏まえた設計:

| 期間 | 行数 | 用途 | 市場フェーズ |
|---|---|---|---|
| 2021-04 〜 2024-12 | 394,753 | 学習 | バブル→暴落→回復→上昇開始（全フェーズ網羅）|
| 2025-01 〜 2025-12 | 105,120 | 仮テスト（ハイパラ調整で何度見ても OK）| 上昇継続 |
| 2026-01 〜 2026-03 | 25,824 | 本テスト（最後に 1 回だけ）| 上昇継続 |

### 1.5 過学習対策

1. **本テスト（2026）は最後に 1 回だけ**。仮テスト（2025）でハイパラ調整する
2. **LightGBM 正則化**: 木の深さ・葉の数を制限（具体値はデフォルト設定から開始）
3. **特徴量重要度チェック**: 上位 20 指標を報告。1 個の指標に極端に依存していたら危険信号
4. **連続足の間引き再計算**: 仮テスト結果確認時に、連続して同じ判定の足を間引いて成績を再計算。間引き後も成績維持されるか確認

### 1.6 撤退ライン

**仮テスト（2025 年）で以下 4 指標を判定し、1 件以上 FAIL → ML 単独要協議**

| # | 指標 | 合格基準 |
|---|---|---|
| 1 | q99 net_quality (q99 のみ 8 組合せ件数加重平均) | 平均 > +10pp かつ 8 組合せ中 6 組以上で > 0 |
| 2 | net_quality 最小値 (8 組合せ) | > -50pp (-50pp 未満は ⚠️ 要協議) |
| 3 | valid_rmse / label_std (16 ラベル) | 16 ラベル中 14 以上で < 1.5 |
| 4 | mean_real_MFE / mean_real_MAE (q99 後・8 組合せ) | 8 組合せ中 6 以上で > 1.0 |

不合格時の対応 (まこさん協議型):
- 原因切り分け (ハイパラ vs データ品質)
- k=2 全探索切替 / ML+k=2 ハイブリッド / Phase 3 着手継続 を協議で決定
- 自動 k=2 切替は行わない (合格条件改訂 2026-05-14)

注記:
- net_quality = (q99 フィルタ後の MFE/MAE 平均) と (全 entry 平均の MFE/MAE) の lift% 差分
- lift% 計算分母 = 全 5min 足の MFE/MAE 平均
- 8 組合せ = K12/24/48/96 × LONG/SHORT (q99 のみ)
- 8 組合せの重み付け = q99 の Entry 件数加重平均
- q90/q95 は補助 lens として記録 (合格条件には算入しない・2026-05-14 案G で改訂)

### 1.6.1 合格基準変更ルール (audit#3 反映・2026-05-14 追加)

**原則**: 各 Phase の合格基準は当該 Phase 実行前に確定し、実行結果確定後の基準変更は
当該 Phase の合否判定に適用しない (構造的欠陥が判明した場合は次 Phase 以降に適用)。

**今回の例外**: 2026-05-14 の §1.6 指標1 改訂 (24 組合せ加重 → q99 加重) は、
audit#2 (Phase 2 実行前監査) で指摘されていた spec 欠陥への対応であり、
本来 Phase 2 実行前に行うべきだった補正の遅延取り込みとして処理する。
**これを最後の例外とし、今後この種の遅延補正は許容しない**。

**Phase 6-b への適用**: 本ルールにより、Phase 6-b 「月次 NET ≥ $1,900 全 3 ヶ月クリア」の
基準は Phase 6-b 実行前に最終確定し、実行後の緩和 (全月→平均月次・$1,900→$1,500 等) は
許容しない。

**公式判定 source ルール** (2026-05-14 追加・監査#8 必須3):
- 各 Phase 合否の公式 source は当該 Phase スクリプトが出力する `phaseX_summary.json` のみ
- 完了報告内の手計算・補完評価は「参考」とし、「公式判定」と称さない
- spec 改訂時は対応スクリプトの該当箇所を同タスク内で改修すること (実装漏れによる手計算依存を防止)
- 背景: 2026-05-14 監査#8 で run_phase2_precision.py が案 G (commit b14be88) の §1.6 改訂を反映していなかった事案 (Phase 2 完了報告の改訂後 spec PASS は手計算)

### 1.6.2 絶対閾値 drift 対処方針 (2026-05-15 改訂・audit#9 固定維持確定 → rolling 365日採用へ撤回)

**経緯**: 2026-05-14 audit#9 で「固定維持 + K96 SHORT q99 除外」を確定したが、
2026-05-15 セッションにてまこさん明示指示「どんな市場でも対応させる」を受けて
Web Claude が audit#9 確定を撤回し、rolling 365日方式を採用した（まこさん明示承認）。

**採用内容**: train 固定 q99 → 各時点 t-1 以前 365 日の rolling q99
- 実装: `shift(1).rolling(365*288).quantile(0.99)` (look-ahead leak verify 済)
- スクリプト: `scripts/priority_rebuild/run_phase4b_phase5_rolling_option5.py`

**未解消の留意事項（audit#9 で挙がっていた懸念・rolling 採用後も残る）**:
- 信号品質の全面低下: rolling 適用で 8 組合せの net_quality が固定 refit 後比で低下・K24 LONG はマイナス転落
- §1.6.1 メタルール（Phase 実行結果確定後の基準変更）抵触の疑い
- ハイブリッド却下理由（組合せ別固定/rolling 使い分け = selection bias 構造）は、rolling 全採用でも類似の設計選択として懸念が残る

**K96 SHORT q99 の扱い（rolling 採用後も no-trade 除外維持）**:
- test 2025 で発火 0 件 (BTC 価格 2.4 倍上昇に伴う予測値 % 圧縮により test 予測値 ratio の最大 2.39 < train q99 閾値 3.05・数学的に発火不可能)
- → **no-trade で除外**
- 除外による損失: 年 $169,400 (q99 全体の 9.6%)
- 全 12 ヶ月で月次 $1,900 維持は継続 (audit#3 で検証済)

**audit#12 (2026-05-15)**:
- rolling 採用後の Phase 4-b/5 実行で、trailing exit が MFE スカラーを直接 PnL に流用する leak が発覚
- rolling 自体の問題ではなく Exit 実装の問題。Phase 5 の月次 PnL 数値は無効
- 詳細: `false_positive_incident_policy.md` §3 #6

## §2 Entry 規則

ML の予測値を使って Entry を判定する。

**判定方法**: MFE ÷ MAE（予測値）が閾値以上なら Entry

- LONG Entry: LONG_MFE(K) ÷ LONG_MAE(K) ≥ 閾値
- SHORT Entry: SHORT_MFE(K) ÷ SHORT_MAE(K) ≥ 閾値
- 閾値は学習データからデータ駆動で決定（人間が事前に決めない）
- K 窓ごとに閾値が異なる可能性あり → データが決める

## §3 Exit 設計

Entry 時の 16 予測値パターンで Entry の性質を分類し、性質ごとに最適な Exit をデータ駆動で選択する。

### 3.1 Exit 候補（まず 3 方式で試す）

| 優先度 | Exit 方式 | 仕組み |
|---|---|---|
| 第 1 弾 | 固定 TP | 予測 MFE の X% で利確 |
| 第 1 弾 | トレーリング | 高値追従・反転で利確 |
| 第 1 弾 | 時間 Exit | N 分経過で強制決済 |

### 3.2 追加 Exit 候補（第 1 弾の結果を見てから）

| 優先度 | Exit 方式 | 仕組み |
|---|---|---|
| 第 2 弾 | ATR 連動 SL | ボラティリティに応じた損切り幅 |
| 第 2 弾 | MFE 比例 Exit | 含み益がピークの X% に戻ったら利確 |
| 第 2 弾 | Stale 検知 | 一定時間動きなしで決済 |

### 3.3 Exit 選択方法

1. ML が Entry を出す
2. その足の 16 予測値パターンで性質を分類（短期型 / 長期型 / ボラ高型 等）
3. 学習データ（2021-2024）で各性質 × 各 Exit 方式の組合せを全試行
4. 性質ごとに最も成績が良い Exit 方式 + パラメータを採用

## §4 Position 設計

| 項目 | 設定 |
|---|---|
| 1 回のサイズ | 固定 0.12 BTC |
| 同時保有数 | 上限なし |
| LONG/SHORT 同時保有 | 許可（hedge_mode 活用）|
| 追加エントリー（add） | 許可（Replay で効果を確認）|
| ナンピン | 追加エントリーとして処理（ML が再度「いける」と判断した場合）|

Position の制限（同時保有上限等）は、統合 Replay の結果を見てから追加する（データ駆動）。

## §5 実行フロー（CC の作業手順）

### Phase 1: デフォルト実行（目標: 数時間で結果）

1. LightGBM × 16 ラベルをデフォルトハイパラで学習（train: 2021-2024）
2. 仮テスト（2025）で予測値を出力
3. **必須報告項目**（§7 怠け防止参照）を全て出力
4. 結果を Web Claude に報告 → まこさんへ翻訳

### Phase 2: 精度判定

仮テスト (2025) の 16 ラベル予測値で §1.6 4 指標を評価。

- 全 4 指標 PASS → Phase 3 へ
- 1 件以上 FAIL → まこさん協議 (詳細は §1.6 不合格時の対応)

Phase 2 実行時の必須出力:
- q99 8 組合せ別 net_quality (K12/24/48/96 × LONG/SHORT)
- q90/q95 は補助 lens として記録 (合格条件には算入しない・2026-05-14 案G で改訂)
- 16 ラベル別 valid_rmse / label_std 比率
- 8 組合せ別 mean_real_MFE / mean_real_MAE 比率
- 全指標の合格/不合格判定 (4 指標すべての PASS/FAIL を明示)
- 旧 leak 由来実績 (q99 +80.65pp 等・参考並走) との比較表
- 大幅乖離があれば追加調査フラグ

### Phase 3: ハイパラ調整（目標: 数日）

1. ハイパーパラメータ調整（木の深さ・葉数・学習率等）
2. 仮テスト（2025）で再評価（何度見ても OK）
3. 改善が頭打ちになったら Phase 4 へ

### Phase 4: Exit 仕立て

1. 学習データで 16 予測値パターンによる性質分類を実施
2. 性質 × Exit 方式（第 1 弾 3 種）の全組合せを試行
3. 性質ごとに最適 Exit を選択
4. 仮テスト（2025）で Exit 込み成績を確認

### Phase 5: 統合 Replay

1. Entry（ML 判定）+ Exit（性質別最適）+ Position（§4 設定）で 365 日 Replay
2. 仮テスト期間（2025）で月次成績を集計
3. 同時保有数・最大ドローダウンを確認
4. 問題があれば Position 制限を追加

### Phase 5-e: Funding Rate 控除（8h ごと）

**設計基準（2026-05-20 まこさん承認・audit#19 確定値）**:

| 項目 | 値 | 用途 |
|---|---|---|
| Funding baseline | **median (p50) = +0.0002%/8h** | 月次 $1,900 合格判定の NET 計算基準 |
| Funding stress | p95 = 0.01%/8h | ストレステスト参考値（合格判定基準には使わない） |

- **適用方向**: LONG = funding 控除（支払い）/ SHORT = funding 受取（median 正値のため）
- **境界判定**: (entry_ts, exit_ts] 内に含まれる 8h 境界（00:00/08:00/16:00 UTC）をカウント
- **出典**: history-fund-rate API 91 intervals 2026-04-20〜05-20（2026-05-20・audit#19・sha256:3be5d64c）
- **旧設計**: 0.01%/8h 固定（暫定値）→ 廃止（2026-05-20）

### Phase 6: 本テスト（1 回限り）

1. 本テスト（2026 Q1）で最終確認
2. **月次 NET ≥ $1,900 をクリアしているか判定**
3. 結果を Web Claude に報告

## §7 怠け防止（必須要件・省略禁止）

CC は以下を**毎回の報告で全て満たすこと**。1 つでも欠けていたら報告として受理しない。

### 7.1 実行ログ強制出力

- スクリプトの開始時刻・終了時刻・処理行数・エラー有無をログファイルに保存
- 「結果だけ報告」禁止。ログファイルのパスを報告に含める

### 7.2 中間ファイル保存

- LightGBM の学習過程（各ラウンドの train/valid スコア推移）をファイルに保存
- 最終結果だけの報告は怠けの兆候として扱う

### 7.3 ダッシュボード視認

以下をダッシュボードの新規タブに表示:
- 特徴量重要度ランキング（上位 20）
- 予測値 vs 実際値の散布図
- 月次損益グラフ（仮テスト期間）
- Entry 発火分布（時間帯別・曜日別）

CSV/md だけの報告は採用判定に使わない。

### 7.4 再現コマンド提示

- 結果を再現できるコマンドを 1 行で提示（例: `python run_lgbm.py --config default`）
- 毎回の報告に含める

### 7.5 ランダム比較強制

- ML の成績と並べて「ランダム Entry した場合の成績」を必ず報告
- ランダム比較がない報告は受理しない

### 7.6 極端な手抜き検知

以下を必須報告項目とする:
- 予測値の分布（ヒストグラム）: 全部同じ値を出していないか確認
- 上位 20 指標のリスト: 1 個だけに偏っていないか確認
- Entry 発火率: 全足の何 % で Entry 判定が出たか（0% や 100% なら異常）

### 7.7 Web Claude 経由報告

- CC の結果報告はまこさんに直接渡さない
- Web Claude が先に読んで翻訳・チェックしてからまこさんに共有

## §8 制約・禁止事項

- **【Prime Directive・最大級】本番運用で再現不可能な実装の絶対禁止**: 全 Phase（Phase 0〜7・ラベル生成・特徴量計算・学習・予測・Entry/Exit/PnL/採用判定）において、本番運用の推論時点 t で因果的に取得不可能な値を計算式・判定式に使用してはならない。MFE/MAE 等の保有期間中最大値、K本後の値、期間全体集計、test 結果で決めたパラメータ等。詳細・例外条件は `.claude/rules/false_positive_incident_policy.md` §0-1 を参照。
- **実装前の本番再現性宣言（Prime Directive の運用ゲート）**: PnL/判定/採用ロジックを含むコードを書く**前に**、各入力変数について「本番運用の推論時点 t で因果的に取得可能か YES/NO」と「YES の場合の根拠（確定タイミング・参照ウィンドウ等）」を1行ずつ宣言する。宣言なしの実装着手を禁止する。宣言は完了報告に必ず含める。
- **【第二絶対規定・最大級】ポジション上限 0.12 BTC 合計厳守**: 任意の時点 t において、保有中の全ポジションの合計 BTC サイズが 0.12 BTC を超えてはならない。1 ポジあたりではなく合計上限。エントリー判定・新規発注・add・ナンピンの全工程に適用。配分は柔軟（combo 別・予測強度別等で個別サイズを変えてよい）が、合計上限のみは絶対制約。詳細は `.claude/rules/false_positive_incident_policy.md` §0-2 参照。
- **ポジション上限の実装前 verify 義務**: ポジションサイズ決定ロジックを含むコードを書く前に、「この設計で任意の時点 t に sum(active_position_btc) > 0.12 となり得るか」を1行で論証する。実装後は各時刻 t の sum を実測し max(sum) ≤ 0.12 を完了報告に明示する義務を負う。
- ポジション上限 0.12 BTC 合計厳守（1 ポジあたりでなく合計・詳細は §0-2 参照）
- 未来情報（MFE/MAE ラベル）を入力特徴量に含めない（リーク）
- 本テスト（2026）データを Phase 6 以前に使わない
- 特徴量の事前絞り込み禁止（1,432 指標全部投入）
- 「暫定値」「経験的に」「定番だから」でパラメータを決めない（データ駆動原則）
