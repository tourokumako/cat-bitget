## 経緯 (時系列)

### 1. 過去フローでの ML 学習: Phase 1 (Entry 学習) を 6 通り並列で実施

- 過去フロー (= `phase_flow_v4_with_recovery.md` というファイルに書かれていた手順) では「Entry (= 取引を開始するタイミング) を ML (機械学習・Machine Learning) で判定する」工程 (= Phase 1) を主軸に据えていた
- Phase 1 で 6 通りの学習方法を並列で試した:
  - 案 a: 連続値予測 (= 数値そのものを当てる学習)
  - 案 b: 二値分類 (= Yes/No の 2 択を当てる学習)
  - 案 c: 3 クラス分類 (= 上昇 / 下落 / 動かない の 3 択を当てる学習)
  - 案 d: ランキング学習 (= 取引の順位を当てる学習)
  - 案 e: トリプルバリア (= 利確 / 損切り / 時間切れ の 3 種類のどれが先に起きるか当てる学習)
  - 案 f: メタラベリング (= 案 e の上にもう 1 段、採用するか見送るかを判定する学習)
- 結果: **全部失敗** (= 予測精度が 0.43 = ランダムよりちょっと良い程度で頭打ち・実用にならない)

### 2. 全滅の構造的原因究明

まこさんが「ML が何を学習しているか」を検証するよう指示 → CC が確認した結果、以下が判明:

- **ML が見ている特徴量 (= 学習材料となる指標) が全部ボラティリティ系** (= 値動きの揺れ幅・どれくらい荒れているか) に偏っていた
- ML が「上昇するか下落するか」を予測するのを諦めて「値動きの揺れの大きさ」を予測することに逃げていた
- 原因: 入力特徴量に「今は上昇局面か / 下落局面か / レンジ (= 一定範囲内を行ったり来たり) か」という相場の状態情報が一切入っていなかった
- 結果: ML はどの時間でも同じ条件で学習させられ、相場の局面差を区別できなかった

### 3. フロー自体に欠陥があることが判明

まこさんが業界標準フレーム (= 7 工程フレーム) と過去フローを照合した結果、過去フローには本来必要な 3 工程が欠落していた:

| 工程番号 | 工程名 | 過去フローでの扱い |
|---|---|---|
| 工程 1 | 相場の状態判定 (= レジーム判定) | **存在しない** |
| 工程 2 | Entry 候補の生成 (= 固定ルールでまず候補を出す段階) | **存在しない** (= ML だけで全部判定する設計) |
| 工程 6 | リスク管理 (= 急変時の強制決済等) | **存在しない** |
| 工程 3 | Entry の ML 判定 | 設計思想が業界と違っていた (= 業界では「候補からの絞り込み」だが、過去フローでは「ゼロから判定」) |

= 8 工程中 4 工程が欠落・設計思想違い。まこさん判断: 「過去フローは破綻している。フローから作り直す」

### 4. ChatGPT 7 工程フレームに切り替え

業界標準の 7 工程フレーム + ハイブリッド構成 (= 一部の工程は固定ルール・一部は ML を使う混合方式) で再設計することが確定:

| 工程 | 内容 | 実装方針 |
|---|---|---|
| 1 | 相場の状態判定 (= レジーム判定) | 固定ルール (= 人が決めた閾値で上昇 / 下落 / レンジを判定) |
| 2 | Entry 候補の生成 | 固定ロジック (= テクニカル指標の組合せで Entry シグナル生成) |
| 3 | Entry の ML 判定 | ML (= 候補の中からどれを採用するか機械学習で判定) |
| 4 | ポジションサイズの配分 | 動的合成式 (= 予測の強さ・揺れの大きさ等で取引量を計算) |
| 5 | Exit の ML 判定 | ML (= いつ決済するか機械学習で判定) |
| 6 | リスク管理 | 固定ルール (= 急変時に強制決済等) |
| 7 | 運用監視 | 運用層 (= 本番でモデルの劣化を自動検知・自動切替) |

### 5. 案 B 学習 (= 業界知識の体系化) を実施

CC のトレード ML 業界標準の理解度が浅いことが原因で過去フローの欠陥を見抜けなかった → 5 セッションかけて業界知識を学習資料に整理:

- 学習資料: `.claude/memory/cc_entry_logic_self_study.md` (バージョン v1 → v6・2485 行)
- 学習領域 7 つ:
  1. 学習アルゴリズム (= LightGBM (= 軽量勾配ブースティング決定木) や XGBoost (= 勾配ブースティング決定木) 等、何の手法を使うか)
  2. 予測対象 (= 何を当てに行くか・方向 / 利益確定確率 / 揺れ幅 等)
  3. 特徴量設計 (= ML への入力データをどう作るか)
  4. 評価方法 (= 過学習を防ぐ検証手法・Walk-Forward (= 時系列順に train/test を slide させる) 等)
  5. 組合せ手法 (= 複数の学習器を統合する方法・Stacking (= 段重ね) / Cascade (= 多段絞り込み) 等)
  6. リスク管理 (= Kelly 公式 (= 数学的に最適な賭け額) / Stop-Loss 設計等)

## 重要な注意点

### 過去フロー (`phase_flow_v4_with_recovery.md`) の扱い

- **廃止判定済** (= 2026-05-25 まこさん判断)
- ただし「素材として参照」する用途では残してある (= ここから何を継承し何を捨てるかを決める素材)
- 「このフローをベースに改善する」と書いてあったら、それは「素材として参照しつつ作り直す」の意味で、フロー構造をそのまま受け継ぐ意味ではない

### 旧手動 Priority (`cat_v9_decider.py`) の扱い

- 旧手動 Priority = まこさんが過去に経験で組み上げた Entry/Exit ロジック (= P1〜P25 の優先度別ルール集)
- **スタートライン参照のみ** (= ML がデータから学習するならこれくらいの構成・複雑さは当然到達できるはずという最低ライン・ベンチマークではない)
- 業界全体に対して 5-10% しかカバーしていない最小単位
- 「素材として転用」「ハイブリッド」「経験則ベース」は禁止
- 業界標準を網羅検討した上で独立に同じシグナルに到達するなら採用可・「旧 Priority にあるから」は採用根拠にしない

### 工程 1 (相場の状態判定) の現状 (2026-05-25 セッションで再確定)

まだ実装はない (= 設計段階)。2026-05-25 セッションで、案 B 学習成果を踏まえて以下を確定した。

**確定事項**

- 判定間隔: 1 時間ごと (= 5 分足 BOT でも環境認識は上位足で行う・業界 MTF (Multi Time Frame・複数時間軸) 設計に整合)
- 切替の慣性: 連続 2 回同じ判定が出てから切替 (= 2 時間ヒステリシス相当)
- 分類数: 3 種類 (上昇 / 下落 / レンジ)
- アルゴリズム: HMM (Hidden Markov Model・隠れマルコフモデル・相場の隠れた状態を確率的に推定する手法) を採用・covariance_type=diag (= 過学習防止・step1_regime_design.md v2.1 で full から変更)
- 入力 (= 特徴量・14 指標 × 6 時間軸 = 84 次元・詳細は step1_regime_design.md v2.2 §2.2):
  - 6 時間軸 (5 分 / 15 分 / 30 分 / 1 時間 / 4 時間 / 日足)
  - ベース系 (log_returns, rolling_volatility) ← 業界 default 必須・Phase 0 v3.1 に存在しないため新規生成
  - トレンド方向性 (ADX14 / DI+ / DI-)
  - 移動平均線 (close_vs_sma20_pct / close_vs_sma50_pct / close_vs_ema200_pct)
  - 一目均衡表 (close_vs_tenkan_pct / close_vs_kijun_pct)
  - モメンタム (RSI14 / MACD ヒストグラム pct)
  - ボラティリティ (ATR14 pct / Bollinger Band 幅 pct)
- 前処理: RobustScaler (= 外れ値に強いスケーリング) を Pipeline で fold 毎 fit (= データリーク防止)
- 学習評価: Walk-Forward + Purged K-Fold 5 fold
- 出力: 3 状態 (上昇 / 下落 / レンジ) の確率

**保留 (= Phase 5 Replay 結果で再判定する候補)**

- 出来高系 (OBV / VWAP / Volume Profile / Chaikin Oscillator 等) = BTC 5m での効果が不明・PMC 2025 で importance 0 だった事例あり
- 板情報系 microstructure (OBI / Taker Ratio / Funding Rate / OI Delta) = レジームは大局判定なので高頻度ノイズが効くか不明・Phase 0 v4 でデータ取得実装が必要
- Fractional Differentiation = レジーム判定で必須という業界実証なし
- CPCV (Combinatorial Purged Cross-Validation) = Purged K-Fold で出発時は十分・計算コスト約 27 時間
- Clustered MDA (特徴量選択) = 出発時は特徴量数少なく MDI で十分
- Meta-Labeling 2 段構造 = まず HMM 単体で精度確認してから追加検討

**不採用 (= 工程 1 範囲外)**

- Drift Detection (ADWIN / KSWIN / Page-Hinkley) = 工程 7 (運用監視) で扱う範囲

**過去の経緯**

- 2026-05-25 セッション前: 4 時間判定 + ADX + DI 差の固定ルール MVP で一度確定していた
- 2026-05-25 セッション: 案 B 学習成果と feedback_regime_essence を踏まえて、判定間隔 1 時間 + ヒステリシス + HMM + 多時間軸入力に再確定
- まこさん指摘「5 分足 BOT でレジーム判定が 4 時間/1 時間でいいか」への答え = 業界 MTF 設計で大局を上位足で見るのが標準
- まこさん指摘「2 指標のみで判定できるか」「機械学習なら少なくていいのか」への答え = ML でも多特徴量入力が業界標準・固定ルールから HMM に変更
