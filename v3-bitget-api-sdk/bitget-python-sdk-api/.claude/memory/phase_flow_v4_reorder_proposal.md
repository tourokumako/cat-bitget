## §1 なぜ改善が必要か

phase_flow_v4 は ML 開発手順としては業界標準に沿っており、検証順序 (Phase 0 → Phase 1 → ... → Phase 5 → Phase 6-b) も問題ない。

ただし、月 $1,900 達成設計としては 2 つの構造的問題がある。

### 問題 1: 「悪い相場を避ける」工程が無い

業界では悪い相場 (= 相場が荒れて損が出やすい時期) を検知して取引を見送るのが標準的だが、現 phase_flow_v4 にはこの工程が存在しない。これだけで月の売上が 1.3 倍違うことが業界実証されている。

### 問題 2: 試食会 (Phase 5 Replay) の合格ラインが「月 $1,900 ジャスト」

過去データを使ったテストと本番運用では、性能が **半分くらいに落ちる** のが業界の経験則 (= 過学習で精度デグレ・Lopez de Prado + Bailey 2014 で実証)。Phase 5 で月 $1,900 ジャスト達成だと、本番では月 $950 程度になって全工程やり直しになるリスクが大きい。

## §2 各フェーズの判定方法について (重要)

改訂内容を見る前に、**各フェーズの判定方法** を業界標準で整理する。

### 業界標準の判定構造

ML 学習は **全工程通してから Phase 5 Replay で月の売上を一括判定** するのが業界標準。Replay 結果を見て「どのフェーズに改善余地が大きいか」分析して該当フェーズに戻って調整する、というサイクル。

各フェーズ完了時に行うのは **進捗 verify** のみ:

- leak チェック (= 未来データを過去のフリで使っていないか)
- データ整合性 (= 列数や期間が正しいか)
- 学習収束 (= モデルが正しく学習し終わったか)
- artifact 命名規則 (= 「test」文字列禁止等)
- false_positive_incident_policy の関所 A-G 通過

これらは「次のフェーズに進んで良いか」のフロアチェック (= ミス検知) であり、月の売上に直結する判定ではない。

### 各フェーズで数値目標 (TP Precision > 0.5 等) を出さない理由

「予測精度 > 0.5」「entropy_lift > 0.10」のような統計指標は **目安** であって必達ではない。Phase 1 で予測精度 0.4 でも、Phase 4-a (cluster 並立) や Phase 4-b (Exit 設計) でカバーされる可能性がある。各フェーズで数値目標を強制すると本来達成可能な道を閉ざしてしまう。

したがって、月の売上判定は Phase 5 Replay で一括、各フェーズ途中は進捗 verify のみ、というのが業界整合的な構造。

## §3 改善すべき 4 箇所

### 改善 1: Phase 4-c (Regime filter) を新規追加

**何を追加するか**

「悪い相場の日は取引しない」判断工程を、Phase 4-b (Exit 設計) の後・Phase 5 (Replay) の前に新規追加する。

**v4 の現状**

該当工程が存在しない。悪い相場でも無条件に取引する設計で、月の売上の足を引っ張る損失が発生する。

**修正後の工程内容**

HMM (Hidden Markov Model・隠れマルコフモデル) または 200-day MA (移動平均線) フィルターで「悪い相場 (= 過去データで月次 NET 平均 -50% 以下となる局面)」を検出し、その局面での取引発火を抑制する。

凍結中の `regime_research.md` 素材を Phase 4-c に転用可能。

**進捗 verify の項目** (= 月の売上判定ではなく工程完了確認)

- regime filter の作成完了 (artifact `regime_filter_train_2021_2024.joblib` 出力)
- artifact 名規則 (= 「test」文字列禁止)
- leak verify (= filter が未来データを参照していないか)

**期待効果**

月の売上が **1.3 倍** (業界実証範囲 1.1-1.6× の中央値)。

**根拠**: `industry_benchmark_knowledge_base.md` §2.4

---

### 改善 2: Phase 4-a を独立工程化

**何を変えるか**

cluster (= 似た性質の取引をグループ化したもの・k=3 で 3 グループ) 並立を明示工程として独立化する。

**v4 の現状**

cluster の作成と評価は Phase 3-b (前処理) と Phase 4-b-1 (Exit 設計) に分散しており、cluster 同士が似た収益パターンでも合格してしまう。これだと「3 グループ並立」と言いつつ実質 1 グループの繰り返しになり、戦略並立の効果が出ない。

**修正後の工程内容**

Phase 4-a を独立工程として明示し、cluster 並立の品質要件を追加。

**進捗 verify の項目**

- k-means k=3 で cluster 作成完了
- artifact `kmeans_train_2021_2024.joblib` 出力 (名前規則準拠)
- cluster 間の収益パターン相関 (Pearson 相関係数) < 0.3 を確認 (= 3 つが独立した収益源)
- 各 cluster の月次 Sharpe > 0.5 を確認 (= 全 cluster が独立に収益貢献)

これらは月の売上判定ゲートではなく、cluster 並立の品質要件 (= 進捗 verify レベル)。

**期待効果**

戦略並立で月の売上 **1.5 倍**。

**根拠**: `industry_benchmark_knowledge_base.md` §2.3 (Square Root Rule)

---

### 改善 3: Phase 5 (Replay 仮テスト) の合格ライン 2 倍

**何を変えるか**

過去データを使った試食会 (Phase 5 Replay) の合格ラインを、月 $1,900 から **月 $3,800** に上げる。

**v4 の現状**

Phase 5 Replay で月 $1,900 達成すれば合格 → Phase 6-b 本テストに進む。

**なぜ 2 倍にするのか**

過去データのテストと本番運用では、性能が **半分くらいに落ちる** のが業界相場。これは「過学習」と呼ばれる現象で、ML モデルが過去データに「偶然合った」部分も学習してしまうため、新しい期間 (本番) ではその偶然が再現しない。

Lopez de Prado + Bailey の 2014 年論文 (Deflated Sharpe Ratio) で、業界では性能のデグレ幅は **30-70% (中央値 50%)** と実証されている。

Phase 5 で $1,900 ジャスト達成だと、Phase 6-b 本テストで $950 程度に落ちて不合格になるリスクが高い。$3,800 (2 倍マージン) 持っておけば、半分に落ちても本番で月 $1,900 達成可能。

**修正後の合格基準**

- 全 12 ヶ月の月次 NET ≥ **$3,800** (単月でも未達なら不合格)

これは **本物の撤退判断ゲート** (= ここで月の売上判定する)。未達なら Layer 2/3 投入 or 5 レバー値再見積もりに戻る。

**期待効果**

本番運用 (Phase 6-b) での目標 $1,900 達成確率が上昇。「Phase 5 通ったけど本番で死ぬ」リスクを構造的に減らす。

**根拠**: `industry_benchmark_knowledge_base.md` §3.2

### 改善 4: Phase 5-d (Position sizing) を動的化

**何を変えるか**

各取引の量 (ポジションサイズ) を、固定値から自動調整に変更する。

**v4 の現状**

全 cluster に 0.024 BTC 固定 (= 合計上限 0.12 BTC ÷ cap=5 想定の単純割り算)。予測の強弱や相場の状況に関わらず、すべて同じサイズ。

**修正後の工程内容**

3 つの調整方法を組み合わせる。

1. **Half-Kelly (半 Kelly) 公式**: 数学的に最適な賭け額 (Kelly 公式) の半分を採用。Kelly そのものは予測の精度が完璧に分かっていれば最適だが、実際には不確実性があるため、業界では半分が標準 (= 75% の成長率を維持しつつ揺れを 50% に抑える)
2. **ボラティリティ・ターゲティング**: 相場の揺れ具合に応じてサイズを調整 (揺れが大きい時は小さく)
3. **cluster 強度別の動的配分**: 予測が強い cluster には多めの 0.04 BTC・弱い cluster には 0.01 BTC など、合計 0.12 BTC 上限を守りつつ重み付け

**絶対遵守事項**

任意の時点で `sum(active_position_btc) ≤ 0.12` を verify。これは false_positive_incident_policy §0-2 第二絶対規定で、変更不可。

**進捗 verify の項目**

- sizing 関数の実装完了
- Half-Kelly 計算式の verify (= 75% 成長 / 50% 揺れ削減の業界実証式)
- sum(active_position_btc) ≤ 0.12 BTC の verify (= 各時点で合計上限遵守)

**期待効果**

月の売上 **1.2 倍**。

**根拠**: `industry_benchmark_knowledge_base.md` §2.5

## §4 改訂後の全体フロー

順序は v4 のまま。★ は改訂箇所。

```
Phase 0 (ラベル生成) ✅完了済
   ↓
Phase 1 (Entry 学習) 既存維持 (= 進捗 verify のみ・数値目標縛りなし)
   ↓
Phase 2 (ハイパラ最適化) 既存維持
   ↓
Phase 3-a (アルゴ比較) / Phase 3-b (cluster 前段) 既存維持
   ↓
★ Phase 4-a (cluster 並立・独立工程化) 改善 2
   ↓
Phase 4-b-1 (Exit 設計) / Phase 4-b-2 (Entry 閾値) 既存維持
   ↓
[CP4 ゲート: Entry-Exit 整合性 review] 既存維持
   ↓
★ Phase 4-c (Regime filter・新規工程) 改善 1
   ↓
★ Phase 5-d (Position sizing・動的化) 改善 4
   ↓
★ Phase 5 (Replay 仮テスト・合格ライン $3,800) 改善 3
   ↓
Phase 6-b (本テスト) 既存維持 (= 全 3 ヶ月 NET ≥ $1,900)
   ↓
Phase 7-a〜e (Bot 統合・既存維持)
```

各フェーズの判定方法は業界標準と同じ:
- **各フェーズ完了時**: 進捗 verify (leak チェック等) のみ
- **Phase 5 Replay**: 本物の合否判定 (= 全 12 ヶ月 NET ≥ $3,800)
- **Phase 6-b 本テスト**: 最終判定 (= 全 3 ヶ月 NET ≥ $1,900)

## §5 5 つのレバー × 担当工程 対応表

月 $370 → $1,900 (= 5.1 倍) を作るには 5 つのレバーを全部使う必要がある。

| # | レバー | 業界実証範囲 | 中央値 | 担当工程 | 改訂内容 |
|---|---|---|---|---|---|
| 1 | Entry 改善 | 1.1-1.6× | 1.4× | Phase 1 | (既存工程・改訂なし) |
| 2 | Exit 最適化 | 1.3-2.0× | 1.7× | Phase 4-b | (既存工程・改訂なし) |
| 3 | 戦略並立 | 1.2-1.8× | 1.5× | Phase 4-a | 改善 2 (独立工程化) |
| 4 | Regime filter | 1.1-1.6× | 1.3× | Phase 4-c (新規) | 改善 1 |
| 5 | Position sizing | 1.1-1.3× | 1.2× | Phase 5-d | 改善 4 (動的化) |

5 レバー中央値の積: 1.4 × 1.7 × 1.5 × 1.3 × 1.2 = **5.57 倍** = 月 $2,060 (= 目標 + 8% マージン)

### 重要な気付き

- **単一レバーでは達成不可能**: Entry 単独 1.6× = 月 $592 で大幅未達
- **5 レバー全部必要**: 1 つでもサボると未達
- **Exit が最大レバー (1.7×)**: Phase 1 だけ頑張る現アプローチは構造的に未達
