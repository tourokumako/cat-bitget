【4-0 この仕組みは何か】
**この工事は、設計書の元の形を直す工事です。**設計書の元とは、工事1件の設計書を作る前に、CC が書いて まこさんの OK をいただく物です。中身は4つです。やることリストの行・読むもの宣言・やることの表・案です。

**直す理由。**いまの設計書の元には、その工事が要件定義の何番のための工事かを書く所がありません。目標を書く所もありません。CC が自分で「合っている」「当たりません」と判定を書く所があります。別セッションの監査（2026-10-12・結論 CONDITIONAL-GO）は、この形では、設計の誤りを実装の前に CC 以外が見つけられない、と答えました。

**①やることリストに「結ぶ要件」を持てるようにする（F-1）。**やることリストの1件に「結ぶ要件」（その工事が、要件定義の何番のためか）を書くと、やることリストの文書に、その行が出ます。書くのは、その行の工事を始めるときです。CC が案を書き、まこさんが決めます。

**②読むもの宣言に2行を足す（F-2）。**読むもの宣言を作る hook が、「やることの番号」と「結ぶ要件の項目」の2行を出します。結ぶ要件は、やることリストの行から写します。CC は書きません。行に結ぶ要件が無ければ、宣言を作らずに止まります。やることリストに行が無い工事（この工事のような、プログラムを直す工事）だけ、宣言の元データに書いた文を写します。あわせて、要件定義の文書（core_requirements.md）を、どの工事の宣言にも必ず足します。宣言の検査も、この2行と要件定義の文書が無ければ止めます。

**③やることの表の共通の ひな型を作る（F-3）。**足す所は3つです。「やることリストのどの行の工事か」（要件との違いを、どこまで減らすか）・「目標」（6つ）・頭の使い方（出す順と書き方）です。やらないことは、1か所にだけ書く形にします。

**④案の共通の ひな型を作る（F-4）。**いまの ひな型は、工事ごとに1本ずつ在ります（14本・見出しは同じ32個）。共通の1本にします。足す所は、【4-3】【4-4】【4-6】【4-7】【4-8】【4-9】【4-10】【4-13】の中の書く所と、新しい見出し3つ（検査やプログラムを直す工事で書く5つ・新しく入る数字と式の一覧・確かめていないこと）です。【7-1】【7-3b】【7-6】は書き方を直します。【0-R】は置きません。

**なぜこの形にするか。**設計書を作るプログラムは、設計書の元を読んで設計書を作ります。読む相手の形が決まらないと、読む側は直せません。だから、元の形を先に決めて、監査を通します。設計書を作るプログラムは、読む所と設計書に出す所が項目ごとに対になっているので（gen_acceptance.py の 311〜322行・373〜412行と、1435行から後ろ）、次の工事で一緒に直します。

**この工事が済んでも、まだ出来ないこと。**新しい ひな型で書いた元からは、設計書を作れません。設計書を作るプログラムが、新しい形を知らないためです。案の ひな型で書いた案は、知らない見出しで止まります（gen_acceptance.py の 412行）。やることの表の ひな型で書いた表は、手書きの項目に「### 3-1 やらないこと」が無いので止まります（同 314〜316行）。作れるようになるのは、次の工事の後です。
