### §1 概要

工事を始めるとき、CC はまず「設計書の元」を書きます。まこさんの OK をいただいた後に、プログラムがそこから設計書を作ります。設計書の元とは、やることリストのその工事の行、読むもの宣言（設計書を書く前に読むファイルの一覧）、やることの表（やること・やらないことをまとめた表）、案（設計の中身を書いた文章）の4つです。

ところが、いまの設計書の元には、その工事が要件定義の何番のためのものか、何を目標にしているか、CC が何を確かめていないか、を書く場所がありません。その一方で、CC 自身が「要件に合っています」「作ってはいけないものに当たりません」と結論を書き込む場所はあります。これでは、監査は CC の結論を読んで認めるだけになり、設計の誤りを実装の前に CC 以外の人が見つけることができません。2026-10-12 の別セッションの監査でも、同じ指摘を受けました。

そこでこの工事では、設計書の元の形を、次の4点で改めます。

1. やることリストの各行に、「結ぶ要件」（その工事が要件定義の何番のためのものかを示す一文）を書けるようにする。
2. 読むもの宣言を作るプログラムを直し、宣言に「やることリストのどの行の工事か」と「その行の結ぶ要件」を自動で載せる。あわせて、要件定義の文書を、読むファイルの一覧に必ず含める。
3. やることの表を書き始めるときに使う、共通の ひな型を1つ作る。ひな型とは、見出しと、各見出しの下に何を書くかの説明だけが入った、中身が空の文書である。いまは工事のたびに前の工事の表を手本にしているため、前の表に無い見出しは、次の工事でも抜けたままになる。
4. 案にも、同じ目的の共通の ひな型を1つ作る。

設計書を作るプログラムそのものは、今回は直しません。設計書の元の形が決まってから、次の工事で直します。新しい ひな型2つを実際に使い始めるのも、その工事が終わった後です。

### 4-19 通しの例

今回の直しで何が変わるかを、工事1件に当てはめて示します。指標の検査を直す工事（呼び名は K-4。やることリストでは M2-C-15 の行に当たります）を、もう一度 最初から始める場面で、直す前と直した後を比べます。

**直す前**　CC は、読むもの宣言の元になるファイル（read_plan_src.json）に、読むファイルの一覧だけを書いて、プログラムを走らせます。出来上がる宣言にも、ファイルの一覧しか載りません。そのため、この工事が要件定義の何番のためのものかは宣言のどこにも現れず、まこさんが宣言を見ても確かめようがありません。

**直した後**　CC は、ファイルの一覧に加えて、やることリストの行の番号「M2-C-15」も書きます。プログラムは、やることリストの M2-C-15 の行を開いて「結ぶ要件」を探します。見つからなければ、宣言を作らずに止まり、「やることリストの M2-C-15 に「結ぶ要件」が無い」と表示します。この場合は、CC が結ぶ要件の案をまこさんに示し、まこさんが決めた文をやることリストに書き込んでから、もう一度プログラムを走らせます。

今度は宣言が出来上がり、そこに「★**やることの番号**：M2-C-15」「★**結ぶ要件の項目**：M2-C-15＝（まこさんが決めた文）」の2行が載ります。要件定義の文書（core_requirements.md）も、CC が書き忘れていても、プログラムが読むファイルの一覧に加えます。そして、CC が承認をお願いする前の検査のときと、まこさんの承認のときに、検査のプログラムが宣言を調べます。この2行か、要件定義の文書の行が欠けていれば、承認へ進めません。
