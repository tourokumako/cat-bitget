【4-0 この仕組みは何か】
監査の直しを当てる道具 apply_audit_fix.py の、根拠の抜き書きの照らし方を2つ直す。
いまは、根拠の逐語が実物のその行にそのまま含まれるかだけを見る（apply_audit_fix.py の check_evidence と _cmp_line）。そのため cp52 の4件（修正2・10・12・14）が「合わない」になり、1件も当てられない（worklog 20260930 §9）。
直した後は、①根拠が設計書（acceptance.md）の行なら、監査が見た版（結果ファイルの「監査が照らしたハッシュ値」と sha256 が同じ承認の控え）と照らす。②逐語に「…」が在れば、「…」で区切った文が、その行の中に順に全部在るかで照らす。
それ以外の照らしは今までどおり（1件でも合わなければ1件も当てない）。

【4-3 部品と責任の割り当て】
- check_evidence＝根拠のファイル名が acceptance.md なら、監査が見た版の控えを照らす相手にする。
- _cmp_line＝逐語に「…」が在れば、区切った文が順に全部在るかで見る（行番号のずれを探すときも同じ見方）。
- main＝監査結果から「監査が照らしたハッシュ値」を読み、その sha256 の控えを探して、check_evidence に渡す。
- selftest＝場面を足す（「…」の文が順に全部在れば合う・1つ欠ければ合わない・設計書の行は控えと照らす）。

【4-4 処理の流れ】
- ①main が監査結果を読み、「監査が照らしたハッシュ値」を取り出す。②承認の控えのうち sha256 が同じものを探す（無ければ今までどおり）。
- ③全件の確かめで、根拠が acceptance.md なら控えの行と照らす。④「…」が在れば区切って照らす。⑤合わない件が1件でも在れば、1件も当てない（今までどおり）。

【4-5 異常系】

- 「…」で区切った文が1つでも無い＝「合わない」。1件も当てない。
