### §1 概要

### 4-19 通しの例

今回の直しで何が変わるかを、工事1件に当てはめて示します。指標 ADX の役割を直す工事を、新しい ひな型を使って始める場面で、直す前と直した後を比べます。

**直す前**　CC は、新しい ひな型のとおりに、やることの表に「目標」の6つを書き、案に「確かめていないこと」を書きます。そのうえで設計書を作るコマンドを走らせると、プログラムは「知らない見出し【確かめていないこと】が在る」と表示して止まります。やることの表の「目標」は、止まりもせず、設計書にも出ません。そのため CC は、古い形の表と案に書き直すしかありません。古い形には、目標を書く場所も、確かめていないことを書く場所もありません。あるのは、CC が「要件に合っています」と自分で判定を書く表です。監査は、その判定を読んで認めるだけになります。

**直した後**　同じ表と案から、プログラムが設計書を作ります。設計書の先頭には「工事の種類＝指標・探索・売買のロジック・設定に触る工事」と出ます。これは、直すファイルの一覧からプログラムが決めた物です。2番の節には、やることリストのどの行の工事かと、その行に結んだ要件が、読むもの宣言から写されます。3番の節には、CC が書いた目標の6つが出ます。

4番の節では、CC が案に書くのは「ADX に関わる」「役割の印を直す」といった、その工事の判断だけです。ADX の役割の文、パラメータの範囲、スキャルとデイトレの代表の値、その出どころ、オンかどうかは、プログラムが置き場から写します。閾値の代表の値は、置き場にまだ無いので、「未決」と出ます。閾値の修正の工事が、決めた形で置き場に値を書けば、プログラムを直さなくても、ここに値が出るようになります。

要件定義との照らしの表は、CC の判定ではなく、どの要件をどの節に書いたかの索引に変わります。6番の節には、CC が「確かめていないこと」に書いた行が、そのまま出ます。監査は、設計書に載った目標と、根拠と、確かめていないことを材料にして、設計の中身が正しいかを自分で判定できます。

古い形で承認した設計書（たとえば K-4）は、この直しの後に作り直しても、1行も変わりません。
