**いま何が起きているか。**工事の型は6段です。③（監査結果から設計書を直す）と⑥（監査結果から実装を直す）は、当てる道具 `apply_audit_fix.py` が受け持っています。④（設計書から実装を当てる）だけ道具がありません。設計書の「組み方」は日本語の散文なので、プログラムが読んで当てられる形になっていません。だから実装は私が手で書いています。手で書くと、設計書に書いた文と違うものを書いても、それを見つける仕組みがありません。

**どう変えるか。**設計書に「実装の指示」の節を足します。節の中身は、監査結果の修正の指示と同じ6つの欄です。当てる道具に `--design` の口を足し、設計書からその節を読んで当てます。読み取り・確かめ・当てる処理は、いま監査結果に使っているものをそのまま呼びます。

**ほかの形と比べて、なぜこの形か。**比べた形は3つです。①新しい道具を別のファイルで作る＝読み取りと確かめの処理を2か所に書くことになり、片方だけ直って食い違います（恒久の決まり69番）。②設計書の「組み方」の散文を、プログラムが読み取れるように解析する＝日本語の文から直す場所を当てる形になり、当て間違いを見つけられません。③実装の指示を設計書の外（別のファイル）に置く＝承認の印は設計書のハッシュ値なので、外に置いた指示は承認で凍結されません。この設計は、指示を設計書の中に置き、承認で凍結し、当てる処理を1か所にまとめます。

**完成したときに出るもの。**`apply_audit_fix.py --design <設計書> --dry` が、設計書の実装の指示を全件 確かめて一覧に出します。承認の印と設計書が合わないときは、1件も当てずに止まります。売買は1件も回さないので、net は動きません。

### 4-4 処理の流れ（うまくいったとき、何がどの順に起きるか）
