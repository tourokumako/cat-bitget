### 4-0 この仕組みは何か（全体・一続きの文章で書く）

**この仕組みは、場面の判定の束について、①段3（持続）が数える相手を §2.2 の正本の形に合わせ、②転がし窓の順位を付けるかを法則で決め、③別枠の印の照らしを実行器でも揃えるものです。**3件を1つの設計書にまとめた理由は、3件とも触るファイルが `engine_tuner_gen.py`・`engine_tuner_exec.py` で同じで、途中の実測の数字で中身が変わらないためです（まこさん OK 2026-09-24「上記でOK。」）。

**①いま何が起きているか。**engine_tuner が組むレンジの判定の束は、入る条件が「帯の幅 A ∩ 帯 B ∩ 強さの否定 C ∩ 向きの否定 D ∩ 3枠目 G ∩ 持続 F」の形です。持続 F は「内側の条件が直近 n本 全部 真」という形で、いまの内側は帯 B の1つだけです。だから A・C・D・G は「いまのバーで真」であればよく、直近 n本 の途中で偽になっていても成立と数えます。§2.2 の段3 の正本は「成立の連続本数」で、成立の全体が n本 続くことを求めています。

**①どう変えるか。**持続 F の内側を「A ∩ B ∩ C ∩ D ∩ G の全体」にし、入る条件を F の1つにします。こうすると、5つの枠が全部 真のバーが n本 続いたときにだけ、入る条件が真になります。出る条件（解除の緩め幅＝A・B・C を緩い側へずらした条件のどれか）と、保つ上限は変えません。

**①なぜ実行器も直すのか。**いまの実行器は、持続の内側に条件1つしか受けません。向きの否定 D は「真偽の列を not で包んだもの」で条件1つの形ではないので、「各枠に同じ n の持続を1つずつ掛ける」やり方では D を包めません。内側に条件の束を受けられるようにするのが、形を正本に合わせる道のうち、持続を1つで済ませる道です（各枠に同じ n の持続を1つずつ掛ける形も、内側に not と真偽の列を受ける直しが要り、真偽は同じになる）。

**①ほかの形と比べて、なぜこの形か。**候補を総当たりで組むのは成り立ちません（まとめて回したときの通り数は `grep -n '通り' .claude/ratchet/s22_combi.md`、束を1本 測る時間は `grep -n '合計' .claude/ratchet/s22_breakdown.md` で見られます）。だから §2.2 は段ごとに絞る形で、段3 は「段1〜段2c を通った上位の束に、続く本数を掛けて測る」段です（M2-F-14）。その段3 が測る相手が正本と違う形のままだと、M2-F-14 で並べる順位が、正本と違う判定の成績で決まってしまいます。2026-09-20 の実測では、いまの形は §2.2 の形より真のバーが 9.65%〜18.55% 多く、その差は全部「成立が途中で切れたのに成立と数えたバー」です。

**②転がし窓の順位。**M2-C-4 で受け口（`sample_regime_build` の引数 `pre_b`）を作りましたが、呼ぶ側が0件で、engine_tuner は一度もこの形を作っていません（監査 cp24 の実測）。付けるかどうかは相場の法則で決める、という まこさんの決定（2026-09-06）に従って法則の正本（`regime_laws.json`）を読むと、レンジの法則 R6 の説明「幅が過去より狭い状態」と根拠の逐語「near the low end of its six-month range」、R10 の「ATR% の自分の平均との比較」が、直近の窓に触れています（2-1 の表・監査 CP39 の問い2）。いまの閾値は値決め窓の分布から1回だけ固定した分位です（`build_qtable`＝rolling しない）。まこさんは 2026-09-25 に「②と③はどちらもCCのおすすめ案でOK」と決めました＝固定の線は残し、6か月で動く線は別の番号 M2-E-4e で段2c の候補に足す。だから束1 では付けず、受け口の引数も消しません。N も書きません。元データの `pre` は段2a にしか読まれず（`build_stage_candidates` の中で段2a にだけ読む）、窓の本数の欄も無いので、段2c に窓の本数つきの前処理を付ける道は M2-E-4e で作ります（窓の本数は法則の逐語 six-month から取る）。

**③別枠の印の照らし。**印（`indicator_switch.json`）の別枠3種（レンジ幾何 `geo_on`・需給 `demand_on`・時間帯 `time_on`）を、組む側は候補を作る所（`_lineage_candidates`）と審査（`assert_provenance`）の両方で3種とも照らしています。実行器の `_material_name` は需給だけを印と照らし（`demand_enabled`）、レンジ幾何と時間帯は定義表に在るかしか見ません（監査 cp26 の 6-6＝148番）。実行器でも `geo_enabled`・`time_enabled` を呼び、印から外した材料を G6 で拒否します。自己テストに、需給の T-f-3 と同じ形の T-g を足します。

**完成したときに出るもの。**`streak_scope_diag.py --builds 3` で、実行器が作った入る条件の列と、診断が別の式（成立の全体の連続本数）で作った列の食い違いが、3本とも 0 になります。組む側と実行器の自己テスト（T46・T-STREAK-TREE・T-g を含む）が全部 通ります。売買は1件も回さないので、net は動きません。

### 4-4 処理の流れ（うまくいったとき、何がどの順に起きるか）

**この項目に書くこと**＝工程の順番と、工程の間で何を渡すか。組み方の根拠（何の法則で決めるか）も。

1. `sample_regime_build` が、今までどおり A・B・C・（D）・（G）を、段ごとの候補の一覧の順位から案の番号で取ります。B の材料に前処理を付ける分岐（受け口 `pre_b`）は残りますが、呼ぶ側は0件のままです（まこさん決定 2026-09-25）。前処理が付くのは、候補の一覧（`build_stage_candidates`）が元データの `pre` から付けたものだけです。
2. 法則に持続の形（R4）が在れば、F＝{streak・n・inner: {all: [A, B, C, (D), (G)]}} を作ります。n は今までどおり `_nv_fixed` が承認済みの範囲（`int_range`）から案の番号で決めます。
3. 入る条件を {all: [F]} にします。出る条件と保つ上限は今までどおりです。
4. 束の単位で数える法則（C4）を、今までどおり `_check_bundle_counts` が確かめます（実行器の `_scene_scan` を呼ぶ。`_scene_scan` は `inner` が辞書なら自分を呼ぶので、内側が束でも今のまま歩けます）。
5. 実行器の検査が束を歩きます。hysteresis の入る条件 → `_walk_build_tree` → F → `_check_cond`。F の内側が束なので、性質表の欄 `inner_tree_ok` と「判定の束の中か（`in_build`）」を見て、内側を `_walk_build_tree`（`in_nest=True`）に回します。内側の束の中の各条件は、今までどおり `_check_cond` の検査（G5・G6・分位の範囲・本数の範囲）を受け、材料の名前は `_material_name` が印と照らします。
6. 審査 G7 が束を歩きます。持続の形が在る（R4）・not の形が在る（R8）・hysteresis の形が在る（C6）・部品の数（R1・R3・R5・R6・R7・R10・C4）・系統の重なり（R2）を、今までどおり数えます。枠の条件は F の内側に1回ずつしか出ないので、数は直す前より増えません（直す前は B が外と内側で2回 出ていました）。
