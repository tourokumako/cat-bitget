## 3｜真因（root cause）

**設計書に「どの要件のために作るか」を書く欄がありません。**

**＝CC は、要件に無いものでも設計書に書けます。**そして、合格の条件（何ができたら満たしたと言えるか）も、CC が自分の言葉で書けます。

**★禁止の一覧では止まりません。**理由3つ（実測）。

| # | 理由 | 実測 |
|---|---|---|
| 1 | 後追いにしかならない | 違反の記録22件のうち、CC が自分で気づいて止まったのは **1件だけ** |
| 2 | 増えるほど、照合が形だけになる | 同じ性質の禁止が既に **89件** |
| 3 | 「当たりません」と書ける欄が増えるだけ | 55回目まで、「作ってはいけないもの」2番は「当たりません」と書かれたまま破られていた（78番） |

**＝禁止は数え切れません。許可制は要件16件で有限です。**

## 4｜何を作るか

### 4.1 一言でいうと

> **設計書に「どの要件のために作るか」を必須にし、その要件の逐語をプログラムが差し込む。**

### 4.2 足す関数（6つ・全部 `verify_design_contract.py`）

| # | 名前 | 何をするか |
|---|---|---|
| 1 | `requirements_index()` | `engine_tuner_requirements.json` の `requirements` を読み、`{R1: {title, decided, accept, state}}` を返す |
| 2 | `extract_requirements(md)` | 設計書の `REQUIREMENTS: R5, R9` の行から番号を取り出す |
| 3 | `requirement_block(ids)` | 番号ごとに **`title`・`decided`・`accept`** を並べた表を作る |
| 4 | `check_requirements(md)` | ①`REQUIREMENTS:` の行が在るか ②番号が要件に実在するか ③差し込みが最新か（ハッシュ値）。**1つでも欠ければ exit 1** |
| 5 | `write_requirements(md)` | `REQ_START hash=… 〜 REQ_END` の間に、3 の表を差し込む |
| 6 | `req_coverage()` | **要件16件のうち、設計書が1本も指していない番号を出す**（＝作ったフリの検出） |

### 4.3 差し込みの形

```
<!-- REQ_START hash=… ここは verify_design_contract.py が自動生成＝手で書き換えない -->
| 要件 | まこさんが決めたこと（逐語） | 何ができたら満たしたと言えるか（逐語） |
|---|---|---|
| R5 レンジ以外の相場でも最適解を探せるようにする | 「…」 | 「①局面の判定を戦略の側から受け取る形になっていること ②…」 |
<!-- REQ_END -->
```

**★この表は、要件の json の逐語をそのまま入れます。CC が書き写しません。**
**★形は `gen_windows.py` の `WINDOWS_START/END` と同じにします。新しい方式を作りません。**

### 4.4 止める所（2つ・どちらも既に在る所に足す）

| # | 止める所 | 何をするか |
|---|---|---|
| 1 | **`approve_impl.sh`（設計書の承認）** | `check_requirements` が ❌ なら承認しない＝**要件に紐づかない設計書は承認できない** |
| 2 | **`require_design_contract_before_run.sh`（実行の前）** | 差し込みが古い・番号が要件に無い ときは走らせない |

### 4.5 これで何がどう変わるか

| いま | 直した後 |
|---|---|
| 設計書は、要件のどれを満たすのか書いていない | **書かないと承認できない** |
| 合格の条件を、CC が自分の言葉で書く | **要件の逐語が自動で入る** |
| 要件に在るのに作っていないものが見えない | **`--req-coverage` で番号が出る** |

**★2つ目が、まこさんの「CCがタスクを軽くしたいから甘い合格基準を選ぶことを禁じたい」への答えです。**
