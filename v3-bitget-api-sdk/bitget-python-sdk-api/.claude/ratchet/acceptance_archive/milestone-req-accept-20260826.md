## §3 深掘り4点

### ① 真因（root cause）

**真因は「合格の条件を書く人と、満たしたと宣言する人が、どちらも CC であること」です。**

やることリストの「確かめ方」欄は CC が自由に書きます。`✅済` を付けるのも CC です。
**＝私が引いた線を、私が満たして、私が終わったと言えます。**

**実例（`session_worklog_20260823.md` の §39.5・逐語）**

> **「確かめ方が、要件の一部しか見ていないのに ✅済 にした」。**
> **実例＝M2-5。**「乱数をやめて法則で組める」は確かめたが、**要件のもう半分（探す値は範囲で探す）を確かめていなかった**（78番・まこさん認定＝重大な不正）。

**★要件の逐語と並べれば、この「半分」は目で見えます。**並べていないから見えませんでした。

### ② 期待値分解

**★売買の期待値（勝率・平均利益・敗率・平均損失）には、この設計は1つも触りません。非該当です。**
理由＝触るのは文書を作るプログラムと対応表だけで、売買の判断にも採点にも入りません。

**代わりに、この設計が動かす数字を書きます。**

**root です。**

## §4 やること（5件）

### やること1｜対応表を新設する（`.claude/ratchet/milestone_req_map.json`）

**やることリストの行の番号（`M1-A-3`・`M2-1-1` など）ごとに、その行が満たしにいく要件の番号を書きます。**

```json
{
  "M2-1-1": { "req": ["R5"], "basis": "M2 は場面の判定＝R5「レンジ以外の相場でも最適解を探せるようにする」の前提" }
}
```

- **`req`＝要件の番号の一覧**（1行が2つ以上の要件に効くこともある）。
- **`basis`＝なぜその要件だと言えるかの1行**（空は許しません）。
- **★どの要件に効くかを選ぶのは、作る側の判断です**（`session_worklog_20260823.md` §29 の表＝作る側の判断は残す）。
- **★何をもって満たしたと言うかは、この表には書きません**（確かめる側の判断＝消す）。それは要件の `accept` です。

**★この対応表は まこさんの承認をもらいます**（型の表・出口の表と同じ形＝私の判断が入る所は承認の指紋が記録になる）。

### やること2｜要件の逐語を差し込む（`gen_materials.py` に足す）

**印**＝`<!-- REQ_ACCEPT_START hash=… ここは gen_materials.py が自動生成＝手で書き換えない -->`〜`<!-- REQ_ACCEPT_END -->`。
**印を2本のやることリストに1か所ずつ置き、その間に次の表を機械が書きます。**

| 行 | 要件 | **要件の逐語（`accept` の全文）** | いま「確かめ方」の欄に書いてあること |
|---|---|---|---|
| M2-1-1 | R5 | （json の `accept` をそのまま） | （表の4列目をそのまま） |

**★左の2列は対応表から、3列目は要件の正本から、4列目はやることリストの実物から取ります。私が文を書く欄は1つもありません。**
