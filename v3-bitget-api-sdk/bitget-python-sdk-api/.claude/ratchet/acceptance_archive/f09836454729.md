## 深掘り4点

### ① 真因（root cause）

**E36 の決済の 38.1% が成行（taker）で、手数料と滑りを余計に払っている。** 内訳は CENTER_LOCK 87件・TIME_EXIT 75件・SPIKE_SL 10件（出典＝worklog 20260802 §12.3 の機械出力）。

真因は2つに分かれる。

- **CENTER_LOCK＝分類の誤り。** 実装（e36 694行）は中心の水準 `Cc[i]` ちょうどで約定させている＝置いた注文に価格が戻って約定する形。E37 の SL_FILLED / MFE_DRAWDOWN_CUT とまったく同じ形なのに、E36 側と score.py の両方で taker に分類されていた。**執行の実態と計算が食い違っている。**
- **TIME_EXIT＝機構の欠落。** 実装（e36 683・697行）はバー終値 `c[i]` で成行決済する。E37 には「成行で投げず建値へ指値を置いて待つ」機構（v31）が既にあるが、E36 には無い。

### ② 期待値分解（勝率／平均利益／敗率／平均損失 のどれを動かすか）

- **レバー1（CENTER_LOCK）＝平均利益を動かす。** 玉の集合も勝敗も変えない。1玉あたりのコストが下がる分だけ平均利益が上がる。ただし悲観処理（(a)）は逆に下げる方向で、飛び越えたバーの分だけ平均利益が減る。**両方を分けて出す。**
- **レバー2（TIME_EXIT の待機）＝敗率と平均損失を動かす。** 時間切れで成行決済していた玉のうち、建値へ戻る玉は BE_EXIT（損ゼロ級）に変わる＝敗率が下がる。戻らない玉は待つ間にさらに逆行しうる＝平均損失が悪化しうる。**勝率は上がって平均損失は悪化する形になる可能性が高い。** 差引きは採点窓の net で決める。

### ③ root を直すか symptom か（Y/N＋理由）

**Y＝root を直している。**

- レバー1 は「執行の実態に計算を合わせる」＝分類の誤りそのものを直す。手数料の数字をいじって良く見せるのではない。だから悲観処理（不利になる方向）を同時に入れる。
- レバー2 は「時間切れで必ず成行に投げる」という機構の欠落を埋める。**E37 で同じ真因に対して作った機構をそのまま移植する**＝新しい発明をしていない。
- symptom 患いの候補は「手数料率の安い口座にする」「TIME_EXIT の本数を伸ばして件数を減らす」だが、どちらも決済の方式の問題を回避するだけで直していない。**特に「件数を減らす」は E36 の役割（デイトレ型）を壊すので採らない。**

## 受け入れ判定（採点前ゲート）

1. **恒等**＝新フラグを両方 OFF で走らせ、現行 base と**玉の集合（entry/exit の時刻・価格・出口理由）が一致**すること。⚠️ CENTER_LOCK の maker 化は無条件なので、net と fee の列は変わる＝md5 は一致しない。**変わってよいのは net と fee の列だけ**であることを機械で確かめる。
2. **測り方**＝E36 を1回だけ走らせて売買記録CSVを1本出し、**同じCSVを score.py の変更前と変更後の2回で採点する**。これで (a) 悲観処理の効果と (b) maker 化の効果が混ざらない。
3. **採否**＝採点窓の score.py の net。あわせて件数を見る（E36 はデイトレ型＝件数が減る尻すぼみは却下）。
4. **merit と demerit を必ずセットで出す**（feedback_crude_must_show_merit_and_demerit）。レバー2 は「BE_EXIT に変わって助かった玉」と「待った結果さらに深い損で確定した玉」の両方を出す。
