## この道具は何か

建玉の観察と探索を、決まった型で機械が全部出す道具（read-only 診断）

## この道具の目的（まこさん確定 2026-07-26・正本は observe_diag.py の説明文）

・新規で Entry/Exit ロジックを構築する際に、
  設定した戦略や条件に沿った、指標、閾値、時間足、パラメータの組み合わせロジックを見つける
・既存 Entry/Exit に対しては、目標達成するために改善すべき点を見つける

この2つに紐づかない機能は足しません。

## 言葉の説明

この説明書と observe_diag の出力に出てくる言葉です。先にここを読んでください。

| 言葉 | 意味 |
|---|---|
| 既存ロジックの検証 | 既に動いている戦略の売買記録CSVを渡して、改善すべき点を見つけるやり方。道具の目的の2つ目にあたる。旧称は売買記録モード。 |
| 新規ロジックの検証 | まだ取引記録が無い新しい入口の候補を、値動きだけから調べるやり方。玉が無いので、値動きから仮の勝ち負けを機械で付けて調べる。道具の目的の1つ目にあたる。旧称は場面観察モード。 |
| フェーズ | 出力のまとまり。番号が付いていて、上から順に出る。既存ロジックの検証と新規ロジックの検証で中身が違う。 |
| 型（down / flat_up） | 入口の型。建てた時点で決まる2種類。down は下落系で、天井が直近の高値。flat_up は平坦上昇系で、天井がレジスタンス帯の上端。値動きの形が違うので分けて見る。 |
| 母集団 | 分析する玉の全部、または観察する場面のバーの全部。統計の言葉をそのまま使っていた。 |
| 場面 | 入口の候補になる値動きの状況。例えば S2 は「レンジの中で戻ったところを売る」状況。どんな場面を見るかは設定ファイルに登録する。 |
| 指標・時間足・パラメータ・閾値の組み合わせ | 検証の最小の1個。指標はRSIなどの計算方法。時間足は5分足や1時間足。パラメータはRSIの期間などの数値。閾値は「どこで線を引くか」。この4つが決まって、はじめて1つの条件になる。 |
| 閾値と分位 | 閾値は値そのものでは決めない。分布の何%の位置かで決める。上位30%より上、といった決め方。こうすると相場の水準が変わっても同じ意味の条件になる。設定の quantiles がその刻み。 |
| 分離力 | 指標1つで勝ちと負けがどれだけ分かれるかの強さ。強いほど、その指標だけで見分けられる。ただし実際には1つでは足りないので、材料として順位を出すだけに使う。 |
| コンフルエンス | 複数の条件が同時に成り立つこと。1つの指標では弱いので、種類の違う指標を2〜3個重ねて勝率が上がる組を探す。同じ種類の指標を二度掛けするのは禁止している。 |
| 巻き込み | 負けを切ろうとしたときに、同じ条件に当たってしまう勝ち玉のこと。負けだけを切ることはできないので、切る案には必ずこれを付ける。 |
| 出口理由 | その玉がどうやって決済されたか。利確、損切り、時間切れ、などの区別。売買記録に記録されている。 |
| 検証できる期間が採点窓と同じ理由 | 今の値動きに近い直近の期間だけで見るため。学習窓は2021年からで、価格の水準も相場つきも今と違う。だから観察にも使わない。窓を変えられるのはまこさんだけ。 |
| 設定ファイルに並んでいる値 | 検証の探索範囲。どの時間足を使うか、閾値を何段に刻むか、各指標の期間をいくつ試すか、など。走らせる前にこのファイルを編集して、範囲を広げたり狭めたりする。使った値は出力の先頭に全部出る。 |

## 2つのモード

| モード | いつ使うか | 渡すもの |
|---|---|---|
| 既存ロジックの検証 | 実際に取引した記録を分析するとき | 売買記録CSV と 5分足CSV |
| 新規ロジックの検証 | まだ取引記録のない新しい入口の候補を、値動きから観察するとき | --scene で場面ID |

どちらも `--plan` を付けると、検証計画だけを出して本走しません。まこさんへ提出する1枚です。

## 既存ロジックの検証が出すもの（12フェーズ）

| # | 何を出すか |
|---|---|
| 0 | 分析する玉の全体を、型と出口理由と勝ち負けで数える |
| 1 | どの撤退の仕組みが切ったかを分ける（概算・ものさしはその走行で実際に使った値から解決する） |
| 2 | 建てた瞬間の相場の状態を、出口と型ごとに見る |
| 3 | 保有している間の値動きを、出口と型ごとに見る |
| 4 | 決済した瞬間の相場の状態を、出口と型ごとに見る |
| 5 | 決済した後に価格がどうなったかを追う（episode_gap_h 時間） |
| 6 | 前後の玉との違いを見る（価格差・時間間隔・レンジ内で何番目か） |
| 7 | 負けを切ったときに勝ち玉に当たる量を測る |
| 8 | 改善の条件の候補を探す（side×型ごとに search_modes で選んだ系統だけ・前半で探して後半で確認） |
| 9 | 両方の期間でプラスの候補だけを抜き出す（機械が抽出・手書きなし） |
| 10 | この結果から次に何をすべきかを出す（戦略名を見ず、売買記録の共通列だけを使う） |
| 11 | 増やす方向＝建てなかった場面のうち、建てていれば取れた条件を探す（建値からの%で判定・枠は見ない） |

## 新規ロジックの検証が出すもの（5フェーズ）

| # | 何を出すか |
|---|---|
| 0 | その場面が1日に何回あるかと、条件なしの勝ち負け・負けの中身・概算の期待値を数える |
| 1 | 指標1つずつで勝ち負けがどれだけ分かれるかを順位づける（材料出しのみ＝ここでは決めない） |
| 2 | 種類の違う指標を2〜3個重ねて、勝率が上がる組を探す（時間足2種以上・前半で探して後半で確認） |
| 3 | 両方の期間で勝率も期待値もプラスの組だけを抜き出す（機械が抽出・手書きなし） |
| 4 | 出口の組み合わせを比べる（利確 × 損切り × 保有の上限・期待値で順位づけ・入口の条件とセットでも見る） |

## 実行のしかた

```
# 既存ロジックの検証
python3 scripts/priority_rebuild/observe_diag.py <売買記録CSV> <5分足CSV>
# 新規ロジックの検証（まず計画を出してまこさんに提出→OK が出てから本走）
python3 scripts/priority_rebuild/observe_diag.py --scene <場面ID> --plan
python3 scripts/priority_rebuild/observe_diag.py --scene <場面ID>
# 自己検査
python3 scripts/priority_rebuild/observe_diag.py --selftest
```

| 引数 | 意味 |
|---|---|
| trades_csv | 実エンジンが出した売買記録CSV（--scene の時は不要） |
| bars_csv | 5分足CSV（Binance Spot 正本・--scene の時は不要＝e37 の計器で読む） |
| --scene | Entry 候補観察＝場面ID（observe_config.json の scenes・例 S2＝まだ玉のない新候補の層1） |
| --inspect | データと指標の検査（歩0・5段・read-only）＝5分足CSVのパスを1つ渡す（売買記録は使わない） |
| --plan | 検証計画だけを自動生成して印字（本走しない・まこさんへ提出する1枚） |
| --config | observe_config.json のパス（既定は同ディレクトリ） |
| --title | 出力の見出しに付ける題名 |
| --selftest | 自己検査だけ走らせる（この道具が守ると言っていることを機械で確認） |

結果は `results/priority_rebuild/ratchet` に保存されます。既にある同名は archive へ逃がすので上書きしません。
計画（--plan）は画面に出すだけで保存しません。

### 2. 探索の系統

一度に全部は回しません。1系統ずつ順番に回します。どれを回すかは設定の search_modes で決めます。

| いま | 系統 | 何を検証するか | 検証する値 |
|---|---|---|---|
| オフ | 切る（損失最小化） | 『急騰急落と判定された玉だけをエントリー価格からの % で早く切る』ロジック（まこさん指示 2026-07-20）の『急騰急落の判定シグナル』そのものを候補プールから探す＝実装済みの急騰判定（v47）は使わない。急落判定は未実装＝ロング側は指標の向きを反転した下向き候補から探す（設計の材料を出す）。v47 と同族の候補（RSI9_15分・BB%b 高分位）もプール内で他候補と同じ土俵で対決する | 判定シグナル候補（逆行側プール＝指標96種×時間足×分位 quantiles・ショートは上向き/ロングは下向き） × 待ち分 wait_grid × 判定窓 early_windows × 切る% sl_grid（エントリー価格からの%） |

## 検証できる期間

採点窓 2026-03-01 〜 2026-06-30 の中だけです（periods.py が正本）。

## 渡せるもの／渡せないもの

渡せる  : 売買記録CSVのパスと、設定ファイル observe_config.json のパス。

## この道具が守ると言っていること

・売買記録CSVを書かない。score を呼ばない。金額を出さない（件数と価格に対する % のみ）。
  勝敗の分類にだけ net_usd の符号を使う。
・結果の言い換え（最大逆行・一度も利にならず 等）は TAUTOLOGY_COLS で隔離し、
  分離力の順位づけに入れない。勝った玉に利が出るのは定義上そうなるだけで、発見ではない。

## engine_tuner との違い

どちらも条件を探索します。名前も役割も似ているので混同しやすいですが、評価のしかたが根本的に違います。

| | observe_diag | engine_tuner |
|---|---|---|
| 何をする道具か | 観察して材料と候補を出す | 候補の値を決める |
| 売買エンジンを回すか | 回さない | 回す |
| 審判の式を使うか | 使わない | 使う |
| 手数料・約定・funding | 入らない | 入る |
| 同じ枠の取り合い | 入らない | 入る |
| 玉の集合 | 条件を変えても変わらない | 条件を変えると変わる |
| 使う期間 | 採点窓だけ | 探索窓と確認窓 |
| 出す数字の意味 | 材料。順位づけまで | 候補の順位づけ |
| 採否を決めるか | 決めない | 決めない |

### 一番大きい違い

observe_diag は、既にある玉や場面のバーに条件を当てはめて、勝ち負けを静かに数えます。条件を変えても玉は増えません。

engine_tuner は、条件を変えるたびに売買エンジンを最初から回し直します。だから玉の集合そのものが変わります。同じ枠を別の玉が取り合う動きも入ります。

これが「疑似シミュで上位だった条件が、実際に回すと順位が逆転する」の理由です（L-330）。observe_diag が良いと言った条件が engine_tuner で悪くなることは普通に起きます。

### 検証の3層での位置

```
層1 観察      → observe_diag（材料と候補を出す）
層2 あたり付け → 疑似シミュ（採否にも候補選定にも使わない）
層3 候補選定  → engine_tuner（実エンジン × 審判の式で値を決める）
本走・採否    → e38_priority_stack + score.py（採点窓・まこさんが決める）
```

observe_diag は入口です。engine_tuner は出口の1つ手前です。

### 紛らわしい点

observe_diag のフェーズ8 も条件を探索します。engine_tuner と名前も動きも似ています。

ただしフェーズ8 は「既にある玉のうち、どれを除外すると合計がどうなるか」を静かに計算するだけです。engine_tuner のように回し直しません。だから同じ「探索」でも数字の重みが違います。

## この道具では分からないこと

- 採否は決められません。採否は score.py を採点窓に通して、まこさんが決めます。
- 場面観察の数字は疑似シミュです。スロットの取り合い・約定の不確実・funding を含みません。
- 実際の成績は層3 の実エンジンでしか出ません。観察は候補の材料までです。
