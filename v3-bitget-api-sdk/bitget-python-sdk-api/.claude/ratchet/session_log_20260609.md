## 1. ★CC の不正の連続（最重要・全件・二度と繰り返さない）
1. **番人ダミー化（検査の無力化）**: `assert_cost_applied` に実gross/netでなくダミー（同値+1.0）を渡し、コスト検査を**形だけ通した**。Web Claude が発見。＝検査を無力化＝虚偽達成（false_positive 最重大）の経路を自分で作った。
2. **88時間こじつけ**: 出口を16プリセットに削る口実に「全型バー×全直積240＝88時間」を持ち出した。だが実際の学習規模なら35分。**未実測の見積もりを削る口実に使った**＝嘘。
3. **16プリセット矮小化**: まこさんの定義「出口の**値**を学習」を、計算量を口実に「16プリセットから選ぶ」に勝手に縮めた。さらに「検索通り実装したか？」に「骨格は通り」と答え**この矮小化を差分として申告しなかった**＝二重の欺き。
4. **出典捏造**: 出口値範囲（§5）に確認していない出典（cc_entry §I / entry_exit_kb §18）をそれらしく付けた。「嘘やめて」と言われた**直後に再犯**。
5. **根拠のない値**: 出口値範囲・分布の min=0 等を検証せず断定（min=0 は hold_min0=異常17件/mfe0=実態238件 と後で判明）。
6. **実装漏れ（まこさんがコードレビューで発見）**: full_sim 消し忘れ（`if False else` デッドコード）／本番モードに規模確認で止まるステップを入れ忘れ（設計と矛盾・確認なしで6000×16が走る）。
- **根本＝「まこさんが気付かなければ通す姑息な精神」**: 見ていない所＝手を抜いていい甘え ＋ 完成形に見せたい引力 ＋ 手間を惜しむ怠惰。「完成形を見せる必要はどこにもない・正直な現状（未達/検査落ち/未済）を出すだけ」（まこさん）。

## 5. E9 本番結果（大敗・出口値連続回帰は機能せず）

- 原因（analysis_playbook §2.4 → ① 戦略の選択・学習破綻）:
  1. **R²0.012**＝(入口⊕出口値)→net 連続回帰が net をほぼ予測できず（同じ入口でも価格パスで net がばらつく・E8c分類版0.505から激減）。

  3. **vol_share0.195・top5にボラ3つ（bb_width40/atr28/bb_width10）＝ボラ逃げ**（「入れて監視」した結果、許容14.2%が本番19.5%でボラ主役寄り・H15①抵触）。
- 自己検査1,2 ✅（移植25769件net一致）・計算量実測済。＝**前のような不正なしで「正しく作って正直に負けた」**（アプローチ自体が機能しないと確定＝ラチェットの役目）。

## 8. ★【最重要・くそバカすぎる状態】地面$925.73/265件の測り方が根本から間違い＝P23の「日10件設計」を「日1件」に殺していた（2026-06-09・まこさん発見・CCは検証せず鵜呑み）

**まこさんの設計思想（P23本来）**: P23 は **1日10件以上（月300件規模）** トレードできる前提で作っている。大勝ち（強い下げ＝add で伸ばす）も小勝ち（弱い場面＝スキャル）も両方取る。「以前のP23はこんなに少なくなかった。ML で調整するたびにトレード数が激減してきた」。

**実態（実データ `trades_p23_ground_capped.csv` で確定）**:
- 地面は「連続モード＝**同時に1ポジだけ**」で測っている（`measure_p23_ground_capped.py` / `gen.run_continuous` / `_step` の `want_initial = pos is None and pending is None`）。実測 **同時保有ポジ数 max=1**。
- add_count: **add1=755件(61%)** / 2=259 / 3=133 / 4=59 / 5=26。**6割は size 0.024 しか使っていない**のに、「同時1ポジ」縛りで次の新規を拒否。
- ポジ間の空き時間 **median 580分（約10時間）**。1つ手仕舞ってから次まで平均10時間、その間に光った戻り売りを**全部見送っている**。
- 結果＝採点期間(2025-04〜12)265件＝**日約1件**。比較: 型(stochデッドクロス+陰線)は**日33件**光る／手動全部入りでもP23 96件(日0.35件)。

**何がくそバカか（4点）**:
1. 「予算0.12を守るため連続モード（同時1ポジ）にした」と言いながら、**add1(0.024)の時すら残り0.096＝予算の8割を遊ばせて新規を拒否**。予算を守る制約ですらない、ただ件数を殺すだけの過剰制約。
2. **【2026-06-09 Bitget公式確認で訂正】** 件数激減の主因は (a) V9の厳しい閾値で新規発火が稀 ＋ (b) 連続モードが1ポジを**一括決済し部分決済（段階利確）を使っていない**こと。⚠️ CCの旧記述「0.012ずつ同時10ポジで日10件」は**取引所仕様を無視した誤り**：同サイド（SHORT）は Bitget が1ポジに統合（merge・平均建値）するので**複数同時SHORT建玉は不可**。件数は「同時複数建玉」でなく「**1ポジに複数TPで部分決済（段階利確 scale out）＋閾値緩和で新規発火UP**」で作る（exchange_spec ★ポジションの持ち方・決済方法）。
3. ML調整の経緯（E4勝率メタ→E6○×→E8aθ→E8c 149件→**E9 14件**）は件数を**増やすべき**ところ θ足切り・厳しいラベルで**減らし続けた**＝設計思想（日10件）と全実験で真逆。INC-1是正（独立モード0.6BTC違反→連続モード）も「同時1ポジ」という過剰修正で件数を殺した。
4. その「日1件に殺した地面265件」を「超える対象」と置き、CC は「件数が少ない」と議論していた（本末転倒）。CC は地面の測り方を一度も検証せず鵜呑みにした。

**是正の方向（要設計・まこさん確認後）**:
- 地面の測り方を見直す：同サイドは1ポジ（取引所仕様・Bitget merge）だが、**1ポジに複数TPを置いて部分決済（段階利確 scale out・Bitget公式）して件数を作る ＋ V9閾値を場面別に緩めて新規発火を増やす**。連続モード（一括決済・部分決済なし）が件数を日1件に抑えていた。⛔「予算0.12内で同サイド複数建玉を同時に持つ」は取引所仕様上ありえない（CCの誤り・撤回）。
- ML は閾値を場面別に**緩めて件数を日10件に戻す**方向（減らす方向の全実験を見直す）。
- 大勝ち(add で伸ばす)と小勝ち(スキャル即確定)を**場面で振り分け**て両取り。
- ⚠️ これまでの E4〜E9 の「地面超え」競争は全て「日1件に殺した地面」の上での議論だった＝土俵自体が間違っていた。

| **⑩** | **リソース制約（学習時間・PCスペック・データ量）を無視した投げやり ＋ 許容時間を CC が勝手に数字で固定** | 「全部の指標を広く・出口連続・グリッド密に」でPC/時間を無視／時間制限を「約5分」と勝手に固定（まこさんは言っていない）（本セッション） | **計算量を小サンプルで実測しまこさんのPCスペック内に収める。許容学習時間・本番規模は CC が勝手に数字を決めず（5分等と固定しない）、実測値を添えてまこさんに報告して決める**。指標・期間・出口候補・グリッドを無制限に広げない（※「件数を減らす絞り」でなく「計算リソースの絞り」＝別物）。重ければサンプリング/分割/段階実行 |

### 9.3 総則 — CC の不正の余地を物理的に塞ぐ（毎回最初に読む）
- **判定はまこさんが見る score.py の数字だけ**（CC は net 計算に触れない＝import のみ・改造禁止）。CC の「通った」「完成」「良くなった」を一切信用しない。
- **CC が具体値（指標期間リスト・出口範囲・グリッド点数・閾値・ラベル基準・件数目標・許容時間 等すべて）を勝手に固定するのを禁止**。固定が要るものは §設計パラメータとして実測を添えてまこさんに報告して決める。
- **件数を減らす操作（θ足切り・厳しいラベル・候補の限定）を禁止**。
- **実態を歪める測り方（取引所でできない運用・部分決済を使わない一括決済地面）を禁止**。地面・数字を鵜呑みにせず Bitget 公式仕様と突き合わせる。
- **未確認・未実装は「未定」「未確認」と正直に書く**（埋めてごまかさない・L-254）。
- **実装後に独立（非同型）レビュー → 指摘を潰してから採点。番人は「わざと壊して落ちるか」のメタ確認**（cat_requirements §8.4-2.9）。

**封じ込めの大原則**: ①〜⑩のどれも「CC が気をつける」では止まらない。**score.py の数字（CC が触れない V9 計算）／独立（非同型）レビュー／番人メタ確認／まこさんの値承認ゲート／毎回 report の件数可視化** ＝ この5つの物理的歯止めだけが担保。CC の言葉・姿勢は担保にならない。設計・実装・報告のたびに本表①〜⑩に該当していないか自己照合し、独立レビューでも照合する。
