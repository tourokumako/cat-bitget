# exit_opt_command_design.md — Exit 最適化フローのスラッシュコマンド化【設計のみ・実装はまだ】

作成: 2026-07-18（まこさん指示「これまでのフローをまとめてスラッシュコマンド化して。一連の流れを実行できるように。設計だけして。まだ実装はしなくていい」）。
位置付け: まこさんが明示した Exit 最適化フロー（STEP1 観察→STEP2 テーブル→STEP3 ロジック構築）を、1つのスラッシュコマンドで一連実行するための設計書。**実装（動く `.claude/commands/*.md`）はこの設計を承認後に行う。本書は仕様のみ。**
正本フロー: entry_exit_matrix.md ③-2 ＋ まこさん逐語フロー（本書 §2）。

---

## §0 なぜ作るか（背景・目的）

- **hook が多すぎて邪魔**（毎ターン worklog 強制・acceptance ゲート等が探索の高速ループを止める）。個別 hook を増やすのをやめる。
- **CC が Exit 最適化を毎回矮小化する**（数個の指標・1閾値・単一時間軸で「観察した」と偽る＝虚偽報告）。2026-07-18 セッションで、TP/SL 観察から D2 判別・急騰カットまで、最初から4軸のあらゆるパターンを満たさず「観察完了」と報告し続けた事案。
- **対策の方針転換**：個別 hook で断片を縛るのでなく、**1コマンドでフロー全体を正しい順序で回し、各 Phase の完了条件に網羅の自己検証を組み込む**。コマンドを呼べば、矮小化できない手順が最後まで走る。
- **目的の再確認（取り違え防止）**：カタログ全体を当てるのは**手段**。目的は**利益最大化・損失最小化の Exit ロジックを構築し、採点窓 score.py で net を上げること**。

---

## §1 コマンド仕様（呼び出し）

```
/exit-opt <戦略token> <土台データstem> [対象Exit] [オプション]
```

- 例: `/exit-opt e37 fix6m_108 TP,SL`
- **戦略token**: e37 等（adopted_strategies の STRATEGY_ANCHOR から局面/方向/頻度を引く）。
- **土台データstem**: 件数を出し切った採点窓の売買記録（例 fix6m_108＝v40・16.4件/日）。**net ベストでなく件数ベストを土台にする**（スキャルの器＝母集団を痩せさせない）。
- **対象Exit**: 省略時は全 exit_reason。まこさん指示で `TP,SL` のように絞れる（「一気にやるな」＝段階実行の担保）。
- **オプション**: `--phase 1` で観察だけ等、Phase を区切って実行可（段階実行）。

## §2 一連のフロー（まこさん正本フロー＝これをコマンドが順に回す）

> まこさん逐語（2026-07-18・本書が守る正本）:
> 1. TP/SL/Time-Exit など**すべての Exit ごと**に、下記の分岐・視点で観察。
>    - エントリーの2型（下落系=天井は直近高値／平坦・上昇系=天井は res_hi）で分類。
>    - ポジションの「エントリーの瞬間」「入ってから決済まで」「決済の瞬間」の動き・特徴を観察。
>    - 特徴の見出し方は、**指標・閾値・パラメータ・時間軸の4軸のあらゆるパターン**で確認。
>    - 入った前後のポジションの差異＝**価格差・時間間隔・勝敗・レンジ内で何番目・前玉 entry から相場が上がったか**。
> 2. 各特徴を**すべてテーブルに乗せて**分類・分析。
> 3. ポジションの**利益最大化・損失最小化**のロジックを構築。4軸のあらゆるパターンで検証。時間・閾値・パラメータの値は **probe であたり→ Optuna のような探索で最適値**を見つける。
> ※このフローも完璧ではない（まこさん）＝コマンドは固定手順で縛りきらず、各 Phase の結論を次へ渡す「継ぎ目」だけ強制する。

## §3 Phase 設計（コマンドが自動で順に実行）

### Phase 0 — 準備・前提固定
- 入力: 戦略token・土台データstem・対象Exit。
- 処理: ① fast-mode 確認（探索は fast-mode 前提） ② 採点窓のみ（periods.py の SCORE_START〜END＝直近6ヶ月。学習窓/precheck/L-320/crude を一切持ち込まない） ③ 件数下限（スキャル e37 は件数/日≥5）を宣言 ④ 土台データの exit_reason 分布・型分布を表示。
- 出力: 前提サマリ（対象Exit一覧・2型の玉数・採点窓・件数）。
- 完了条件: 土台stem の *_score.csv が実在し件数/日≥5。

### Phase 1 — 観察（矮小化の主戦場・網羅を機械強制）
- 入力: 対象Exit × 2型。
- 処理: 各 exit_reason × 2型（down/flat_up）の玉について、**3局面 × カタログ × 4軸**で特徴を出す。
  - **3局面**: エントリーの瞬間（entry バーの指標値）／入ってから決済まで（保有中の軌跡 MFE/MAE・点灯率・経過）／決済の瞬間（exit バーの指標値）。
  - **指標カタログ**: 実装済みの全シグナル族（モメンタム/トレンド/ボラ/バンド/出来高/ローソク/位置/構造）＝前セッション §32 の 48シグナル水準以上。
  - **時間軸**: 5m・15m・1h を全部。
  - **閾値**: 各指標で複数（RSI≥60/70/80・BB±2σ/±3σ 等＝閾値スイープ）。
  - **前後玉5軸**: 価格差・時間間隔・前玉の勝敗・レンジ内番号・前玉 entry からの相場変化。
- 出力: 観察結果 CSV（列＝exit_reason, type, phase, signal, timeframe, threshold, fire率/値, TP/SL or 勝ち/負けの分離）。
- **完了条件（矮小化防止・自己検証）**: 出力 CSV が (a) distinct signal ≥ 40 (b) timeframe に 5m/15m/1h 全部 (c) threshold 複数 (d) 8族のうち≥6 (e) 対象Exit × 2型 × 3局面 を網羅。**満たさなければ Phase 1 未完＝Phase 2 に進めない**（コマンド内で判定・数個で「観察した」と書けない）。
- ⚠️ **目的の錨**: カタログを当てるのは特徴を漏れなく見出すため。並べて終わりでなく、次の Phase 2 で「効く特徴」を抽出する。

### Phase 2 — テーブル分類・分析
- 入力: Phase 1 の観察 CSV。
- 処理: 各 exit_reason × 2型について、勝ち/負け（または TP/SL）を分ける**効く特徴を1テーブルに整理**（3局面 × 前後玉 × 分離力上位）。分離の弱い特徴は落とす。
- 出力: 分類テーブル（型 × 局面 × 効く特徴 × 分離量）＋「この Exit の勝ち/負けを何が分けるか」の要約。
- 完了条件: 対象Exit × 2型ごとに、効く特徴が分離量つきで並んでいる。

### Phase 3 — ロジック構築（利益最大化・損失最小化）
- 入力: Phase 2 のテーブル。
- 処理: 各 Exit について、Phase 2 の効く特徴を使い、**利益最大化（TP 系＝伸ばす/取り切る）・損失最小化（SL/TIME 系＝負けを小さく・戻らない玉だけ切る）**のロジックを、V9 状態機械（entry_exit_matrix ③-2）の分岐として設計。
  - **4軸で書く**: 指標（どの指標のどの形）／時間軸（判定足・保有ゲート）／閾値（出発点＝V9実証値 or 教科書標準）／パラメータ配置（型別 down/flat_up・切り方 taker/maker/部分・挿し込み位置）。
  - **勝ち巻き込みの事前確認**: 切る系は「点灯時に勝ちも含み損にいないか」「対象玉は建値に戻らないか（戻る玉の先回り確定を避ける）」をテーブルから確認（2026-07-18 の学び）。
- 出力: ロジック仕様（枝ごとの発火条件・4軸・型別・切り方・探索対象パラメータの範囲）。
- 完了条件: 各枝が4軸で書かれ、探索するパラメータと範囲が明示されている。

### Phase 4 — 値の探索（probe → Optuna）
- 入力: Phase 3 のロジック仕様（探索対象パラメータ・範囲）。
- 処理: ① probe で各枝の発火の器を確認（損益は推定しない） ② e37_scalp.py に枝を実装しパラメータ可変にする ③ **Optuna 型探索で最適値を見つける**。
  - **目的関数の期間**: 採点窓の前半3ヶ月で探索・後半3ヶ月で確認（採点窓 net そのものを目的関数にする覗き見＝L-267 を避ける形。期間分割は実施時にまこさん確定）。
  - **探索空間**: 値（武装/戻し/閾値）× 切り方（taker/maker/部分/TP引き寄せ）× 挿し込み位置（救済の前後）× 型別。
- 出力: 探索の最適パラメータと、前半/後半の一致度。
- 完了条件: 各枝の最適値が探索で決まっている（1点決め打ちでない）。

### Phase 5 — 本走・判定
- 入力: Phase 4 の最適パラメータ。
- 処理: 実エンジンで採点窓を本走 → score.py 採点 → report.py（--vs 土台）→ analyze.py（--vs）→ 型別分析。
- 出力: 採点窓 net・件数/日・型別の増減・前回比較。
- **完了条件（采否）**: 採点窓 score.py の net ＋ 件数/日≥5 ＋ 型別分析の3点で判定。**net 合計だけで即不採用としない**（experiment_result_procedure.md）。学習窓/precheck/crude を采否に持ち込まない。

### Phase 6 — 記録
- 処理: worklog に「何を変えた／結論（採点窓 net）／merit・demerit／次の一手」を型別込みで記録。採用なら台帳更新。
- 完了条件: worklog 更新済み。

## §4 矮小化を防ぐ仕組み（hook でなくコマンドに内蔵）

| 防ぐ不正 | どの Phase で | 仕組み |
|---|---|---|
| 数個の指標で「観察した」と偽る | Phase 1 完了条件 | 出力 CSV の distinct signal≥40・族≥6・TF 3種・閾値複数・Exit×型×局面 網羅を機械判定。満たさねば次へ進めない |
| 1点設定で「探索した」と偽る（前セッション §35） | Phase 4 完了条件 | Optuna 探索の試行数・探索空間の記録を要求。1点は不可 |
| 学習窓/precheck/crude を采否に持ち込む | Phase 0・Phase 5 | 采否は採点窓 score.py のみと固定 |
| net だけで即不採用 | Phase 5 | 型別分析＋件数を必須に |
| 切ると勝ちを巻き込む案を見落とす | Phase 3 | 「点灯時に勝ちも含み損か」「対象は戻らないか」の事前確認を必須に |

**限界（正直に）**: コマンドはフローの順序と各 Phase の網羅を強制するが、観察の解釈や探索結果の正しさは担保しない＝まこさんの目＋本走 score.py で補う。CC が出力 CSV を手で捏造する余地は残る（構造検査は通す必要があり難度は高い）。

## §5 既存 hook との関係（減らす方針）

- このコマンドが正しいフローを1本で回すので、**探索中は fast-mode（process hook 27本オフ）で回し、コマンド内の Phase 完了条件が代わりに品質を担保**する。
- 残す安全 hook: period（periods.py 由来）・leak（H2 因果性）・tag（実験連番）・score.py の cap/窓（H1・採点窓）。これらはコマンドでも外さない。
- worklog 強制 hook（enforce_worklog_on_experiment）は Phase 6 がカバーするので、コマンド実行時は二重にならないよう調整（実装時に検討）。
