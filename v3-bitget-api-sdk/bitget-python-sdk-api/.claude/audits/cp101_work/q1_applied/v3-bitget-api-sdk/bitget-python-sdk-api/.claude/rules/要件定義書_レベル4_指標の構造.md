## 3. engine_tuner の機能要件

```
指標、閾値、パラメータ、時間足の役割に基づき、法則に則って４つを組み合わせ、Entry/Exitやレジーム判定などの条件を作る
| 1 | **指標**が、承認済みのカタログに在るものから使われている 
| 2 | **閾値**が、範囲から探されている
| 3 | **パラメータ**が、範囲から探されている 
| 4 | **時間足**が、使える時間足から指定されている 
| 5 | **4つが、それぞれの役割に沿って使われている
| 6 | **つなぎ方が、型の表と場面の決まりに沿っている**
```

## 4. 探し方（段階を追って絞る）

- 意図＝「膨大な組み合わせを一気に総当りで検索をしたいが、時間的に不可能なので、段階を追って以下組み合わせをふるいにかけて、最終的にnet利益最大化できるロジックを見つけ出すという構想。」
- 決定＝「ロジック検索の第一弾回では、パラメータや閾値は、スキャル、デイトレそれぞれの代表的な固定値で、最終的にパラメータと閾値は、それぞれに設定した範囲から検索をし、最適値を見つけられるようする」
- 最初の段階で絞るのは、指標・時間足・役割・つなぎ方の組。
- 最後の段階で、残った組のパラメータと閾値を、範囲から探す。
- ほかの探し方に替えない。

## 5. 言葉の定義

### 代表の固定値

**最初の段階で、探さずに固定して使う値です。パラメータと閾値のそれぞれに、戦略（スキャル／デイトレ）ごと・指標ごとに、1つ決めます。**

| 項目 | 中身 |
|---|---|
| 何のためか | 組み合わせの数を減らして、指標・時間足・役割・つなぎ方の組を絞るため |
| 例 | 「RSIをデイトレ戦略で検索する場合は、14」「スキャル戦略では９」 |
| 選び方 | ①教科書にその戦略向けの値が在れば、それを使う（1つのサイトだけの値でもよい）②無ければ、既定の値を使う ③2つ以上 在るときは、決まった規則で1つにする |
| 厳密さ | 「厳密でなくてもいい」「RSIのスキャル用パラメータは５でも９でも大差ないので、どちらでもいい」 |
| 値の持ち方 | 指標の名前に入れない。戦略ごとの設定として持つ |
| 最後の段階では | 固定を外し、範囲から探す |

### 範囲

- 最後の段階で、パラメータと閾値を探す幅です。**指標ごとに1つ**です。
- 「範囲で探せるという上記要件は絶対」
- 「指標名に閾値やパラメータの値を固定で入れて、指標数を増やすという解決策はやめてほしい。」

### 戦略

- スキャルか、デイトレか、です。どの戦略がどちらかは、採用の台帳（adopted_strategies.md）のとおりにします。

### 教科書

- 指標のパラメータ・閾値・役割・計算の作りの、出どころにする資料です（開発者の原典・定番の教育サイトなど）。
- 置き場＝資料の表3つ（indicator_params_review.md・indicator_params_by_strategy.md・indicator_roles_thresholds.md）。

### 法則

- 「法則に則って」の法則です。相場から見つけた知識を、文で書いた物です。
- 置き場＝知識の文書 regime_detection_kb.md の §11（共通・レンジ・上げ・下げ・スパイク・変わり始め）。
- 「法則があるからロジックって言われてるんだけど。」

### 指標一覧（material）

- 指標を計算する、ただ1つの置き場です。Entry・Exit・場面の判定は、全部ここから指標を呼び出します。

## 6. 指標の使い方

- **指標は、指標一覧（material）からだけ呼び出す。**売買のロジックの中に、指標の式を直書きしない。
- **指標のオン・オフが、全部のロジックに効く。**オフの指標は、どのロジックからも使えない。
- 指標は、Entry・Exit と、4つの場面（レンジ・上げ・下げ・スパイク）の判定の全部が使う材料です。材料が誤っていると、その上の絞り込みも net の比べも、全部 誤ります。
- 順番＝「指標を完璧に修正しきってから、M2へ戻す」

## 7. 教科書と法則の扱い（前提）

- **教科書と法則は、完璧ではない、という前提で作る。**
- 「法則、教科書は現状で完璧だとは思っていないので、間違いが見つかったらスムーズに、修正できて、修正したものを適用できる状態にしてほしい。」
- つまり、次の2つができる作りにする。
  1. 誤りが見つかったら、置き場の1か所を直せば済む。
  2. 直した物が、それを使う全部のロジックに、そのまま届く。

## 8. 作ってはいけないもの

1. ランダムに条件をつなぐだけのもの。
2. 探す値を、CC が先に決まった数字の一覧で限定するもの。

# 第3章の2 指標の要素の定義と、要素の増減で目指す形

［手書き］作った日：2026-11-02（238回目）。まこさんの指示（逐語 2026-11-02）＝「指標の要素の定義と要素の増減で目指す形（＝修正のしやすさ）を指標の要件定義書に追記しておいて」。

- 「時間足を足す・閾値の形を足すといった、ロジックを組むにあたって必要な、指標の関するあらゆる【要素】を足すということ＝枠の増減だと思っていたが」

## 指標の要素の定義

- 要素＝ロジックを組むために要る、指標に関する情報の項目。例＝時間足・閾値・パラメータ・役割・向き・前処理・オン/オフ。
- 要素の一覧の正本＝indicators.json の「要素の定義表」（1か所だけ。この文書に一覧を写さない）。指標の記録・使い方の記録・部品の記録の3つに分けて持つ。法則の記録の要素は laws.json の定義表に持つ。
- 法則の記録の形とデータの置き場は laws.json に在る（scripts/priority_rebuild/laws/laws.json・工事 m2c15-outside-record-20261102）。売り方・建てる前の確認・決済の枝・玉全体の決済・玉の持ち方の行と3つの表は 209番で入れた。相場の法則と組み合わせの法則の行は 195番で入れる。読む口は scripts/priority_rebuild/laws/laws.py。
- 指標の外の記録は、情報のレベルで分けた。売り方・建てる前の確認・決済の枝・玉全体の決済・玉の持ち方・役割ごとの決まり・法則の中の数は、法則のデータ（レベル3）に置く。時間足と上位足の写し方は、指標データの定義表（レベル4）に置く。
- 閾値とパラメータは2か所に分かれる。閾値の範囲は指標の記録に指標ごとに置き、閾値の代表の値は使い方の記録に置く。パラメータの範囲と代表の値は指標の記録に置き、使い方ごとに変えるときだけ、使い方の記録の値を使う。
- 「枠の増減」＝要素を足す・消すこと。消さずに止めるときは、定義表のその行をオフにする（読む口は、オフの要素を返さない）。場面の判定の組み立て（帯の幅・強さなど）は、別の物なので「場面の判定の組み立て」と書く。

## 要素の増減で目指す形（目指す形であり、2026-11-02 の実物ではない）

| 足す物 | 例 | 直す所 | コードの直し |
|---|---|---|---|
| 要素の値 | 時間足に週足を足す・パラメータの範囲を変える | データの1か所 | 要らない（週足はデータの取得が別に要る） |
| 要素の選択肢 | 閾値の形に新しい形を足す | データの1か所 | engine_tuner に、その形の計算が無いときだけ要る |
| 要素の種類 | 「使える期間」のような新しい要素 | 要素の定義表の1行 | データを持つだけなら要らない。検索に効かせるには要る |
| 指標と法則 | 指標を1種足す・法則を1件足す | データの1件 | 法則は要らない。指標の計算の関数は要る（要件 R8） |

- コードの直しが要るときも、直す所は1か所にする。
- 足した物は、engine_tuner の検索条件に届く（第1章のゴール3の「直した物がすぐ engine_tuner の検索条件に効く形」）。

## 型の表と成績表で目指す形

| 直す物 | 目指す形 | 確かめ方 |
|---|---|---|
| 型の表の直しと承認 | データの1か所を直すと、型の表が作り直される。承認は、変わった行だけを見て1回で済む | 系統か時間足を1行直して案に届くことを数える。承認の画面に変わった行だけが出る |
| 成績表の作り直し | 足した指標の分だけ測り直す。全部を作り直さない（前回は全部で2時間14分） | 指標を1種足して、その分だけ測り直し、全部を作り直した結果と順位が同じことを確かめる。順位の付け直しは全部に掛かる見込みで、できるかは M2-D-8 の設計で確かめる |

- 確かめ方は、データの直しが案まで届くことを走らせて数える。欄や文字が在ることでは確かめない。
- 上の2つの表の行は、要件の行として対応表（.claude/state/req_trace.md）で工事と試験に結び付ける。

## 4 指標のデータ構造

### 4-1 engine_tuner がデータをたどる順番

engine_tuner は、法則から出発して、指標の値までたどります。

```
お題（レンジのショートのスキャル）
  ↓ お題に掛かる、オンの法則を選ぶ
法則の行（R5「トレンドの強さが弱ければレンジ寄り」）
  ↓ 法則が指す役割を読む（役割＝強さ、側＝弱い）
指標の行（役割が「強さ」でオンの指標を探す → ADX）
  ↓ その指標の、場面の判定の使い方を探す
使い方の行（ADX・場面の判定・レンジ → 向き＝下側、閾値、時間足）
  ↓ スキャルの代表の値を入れる
条件（15分足の ADX14 が 25 より下）
  ↓ 条件をつなぐ
場面の判定の束 → 入口の束 → 出口の枝 → ロジック → net
```

### 5-8 engine_tuner を作るときに走らせる検査の一覧

この節は、いま走らせている検査と、検査ごとに判定してよい範囲を書きます。一覧は 2026-11-02 の実物です。CC はコードを読んで書きました。表23の2〜表23の5の検査は、走らせて確かめてはいません。表23の6は、T15 と T30 を走らせて確かめました。

- 【要件】検査は、見た範囲だけを結果に出します。要件を満たすと判断できない検査が、満たすと判定を出してはいけません。まこさんの言葉（2026-11-02）は「検査に関しては、検査が確認できる範囲での判断で良いので、要件を満たしていると判断できない検査にも関わらず、満たすと判定を出さないようにすべきかと思う」です。
- 【要件】要件の内容を満たすかは、監査で確かめます。下の表の検査が全部通っても、要件を満たした証拠にはなりません。

見方の欄の言葉は、次の5つです。

- 動かす：プログラムを動かして、結果や止まり方を見ます。
- 作り直して比べる：表や文書を作り直して、いまのファイルと同じかを見ます。
- ハッシュ値を比べる：検査した時や承認した時のハッシュ値と、いまのハッシュ値が同じかを見ます。
- 文字：ファイルの中に決まった文字や名前が在るかを見ます。
- 数：件数や空の欄を数えます。
