## 問A 判定 (網羅性)

### Web Claude 列挙 12 案 + 自己申告 3 つの照査

主審査対象 §6 で Web Claude が自己申告した 3 案 (データを買う・予測対象変更・学習データ増) を含めても、外部基準 (ML 標準観点・データ駆動戦略の機能分解) で見て**重大な抜けが残る**。

### 「自己バイアスを 3 つ認める」構造の機能分析

主審査対象 §6 (バイアス1-4) は **「私のバイアスはここにあります」と先に申告することで、それ以外の場所には穴がないという暗黙印象を作る**機能を果たしている。具体的に:

- **バイアス1** (現状路線を救う方向) は X1 推奨を疑える形で提示されているが、X1 自体は依然「最有力」と書かれており、申告は表面のみで結論は変えていない
- **バイアス2** (変更幅小=安全) は分類軸の単一性を申告しているが、§4 比較表の並びは結局 W → X の順を維持
- **バイアス3** (網羅性) は「データを買う・予測対象変更・学習データ増」を挙げているが、これら 3 つは **どれも実装スコープの拡張であり、ML フレーム自体の再定義ではない**
- **バイアス4** (専門用語) は深掘り段階の話で、選択肢列挙そのものの抜けではない

→ 自己申告 4 つは **「列挙の中の細部の抜け」のレベルに留まり、「ML の使い方フレーム自体の狭さ」には踏み込んでいない**。

### 外部基準から見た抜け (最大限抽出)

#### カテゴリ Y1: ML の使い方フレーム自体の拡張 (Web Claude も監査も §6 で踏み込んでいない)

| # | 抜けの選択肢 | 説明 |
|---|---|---|
| Y1-1 | **ML を「異常検知装置」として使う** | 各 5m bar で予測の確信度ではなく **「いまの市場が train 分布のどこにあるか」(out-of-distribution score)** を ML に出させ、OOD score が高い時だけ no-trade / size 縮小。LightGBM の枠を使い続けながら、予測値ではなく**自分自身の予測の不確実性**を判定軸にする |
| Y1-2 | **ML を「特徴量変換装置」として使う** | 1,432 指標を ML 自体で latent representation (例: autoencoder bottleneck) に圧縮し、その latent を入力にルールベース戦略を組む。ML は予測装置でなく**前処理装置**として機能 |
| Y1-3 | **ML を「シグナル合成装置」として使う** | 既存ルールベース戦略 (Priority P1〜P24 等の歴史的成果) と新 ML 出力を **ensemble / meta-learner** で結合。ML の役割を「単独判断」から「既存戦略の重み付け」に再定義 |
| Y1-4 | **ML を「Exit 探索エンジン」として使う (ML inside the Exit search)** | 既存 Phase 4-b の Exit 探索 loop で、time_bars / tp_pct / sl_pct のグリッドを **ML が prediction confidence ベースで動的決定**。Exit 選定そのものを ML 推論にする (X1 とは別軸: X1 は「Exit 種別の predict」だが、これは「Exit パラメータ space の Bayesian search を ML で導く」) |
| Y1-5 | **ML を「Trade Selector / Rejector」として使う** | Entry 判定は既存ルール (q90/q95/q99) のまま、ML の役割を「**そのトレードを実行すべきか reject すべきか**」の二値判定に縮小 (= meta-labeling) 。López de Prado の advances in financial ML で確立された手法 |
| Y1-6 | **ML を「Order Book / Microstructure 予測」として使う** | 5m bar の集計指標でなく、**約定価格パスの bar 内動き** (high が先か low が先か・wick 形成順序等) を予測対象に変える。Exit 判定の最大の不確実性 (Phase 4-b で問題化した「bar 内 low 先・high 後の想定」) を ML 側で吸収 |
| Y1-7 | **ML を「自己評価装置」として使う (calibration / uncertainty quantification)** | LightGBM 16 モデルの quantile regression や bootstrap ensembling で **予測の信頼区間**を出し、信頼区間が狭い予測のみ Entry。X4 (Position サイズも ML) の前段階として独立価値あり |

#### カテゴリ Y2: ラベル設計の再定義 (Web Claude §6 バイアス3 が触れた「予測対象変更」を実質化)

| # | 抜けの選択肢 | 説明 |
|---|---|---|
| Y2-1 | **三項分類 (LONG / SHORT / NO_TRADE)** | 現状の MFE/MAE 回帰を直接分類化。回帰の閾値設計 (q90/q95/q99) の恣意性が消える |
| Y2-2 | **時間長予測 (どのくらいの bar 数で含み益が出るか)** | 現状 K=12/24/48/96 を固定固定で予測しているが、「**何 bar 後に最大利益が出るか**」自体を ML に予測させる。time_exit の bar 数固定の構造的失敗を解消する経路 |
| Y2-3 | **Profit factor 予測 (期待値 = MFE × P(達成) - MAE × P(失敗))** | 現状の MFE/MAE 個別予測でなく、「期待値そのもの」を target にする。Entry 判定がより直接的になる |
| Y2-4 | **Drawdown-aware ラベル (Maximum adverse vs reward の比でなく、含み損経過時間)** | MAE スカラーではなく **MAE 経路 (時系列)** を予測。「途中で含み損 5% 経由したが最終 +10%」と「素直に +10%」を区別 |

| # | 抜けの選択肢 | 説明 |
|---|---|---|
| Y3-1 | **複数取引所統合データ** | Bitget だけでなく Binance / Bybit / OKX の同タイミング price を統合特徴量に。「クロスベニュー arbitrage edge」が見える |
| Y3-2 | **データの時系列粒度を逆に粗くする** | 5m bar でなく **15m / 30m / 1h bar** で学習し、エントリー判定も 15m/30m bar 毎に。「5m bar のノイズ過大」可能性を切り離す。X6 (MTF 統合) と異なり、エントリー bar を**粗く**する |
| Y3-3 | **train 期間を移動窓化 (sliding window training)** | 現状 train 2021-2024 固定 → test 2025/2026 という単一 split を **3 年移動窓で re-train しながら test** する設計に変える。Online learning 寄り |

#### カテゴリ Y4: アーキテクチャ再定義

| # | 抜けの選択肢 | 説明 |
|---|---|---|
| Y4-1 | **方向 + 規模を分離した二段モデル** | LONG/SHORT/NO の三項分類モデルと、Entry 後の利益規模を予測する回帰モデルを別々に。両者の役割を切り分けて leak 検出を容易にする |
| Y4-2 | **K 窓の連続化 (continuous-K prediction)** | K=12/24/48/96 の離散固定でなく、「保有時間長 K を連続変数」として予測。K 値を ML が決める設計 (Y2-2 と類似だが、保有時間そのものを連続化) |

### 「ML の使い方」フレーム自体の狭さ (最重要観点)

主審査対象 §1 で Web Claude は「ML = 予測モデル / Exit = 別段階」を **spec の前提**として整理した。だが ML の標準的な使い方は少なくとも以下 7 つの役割を含む:

1. **予測装置** (現状 spec)
2. **異常検知装置** (Y1-1)
3. **特徴量変換装置** (Y1-2)
4. **シグナル合成装置** (Y1-3)
5. **探索エンジン (Bayesian optimization)** (Y1-4)
6. **Trade selector / rejector (meta-labeling)** (Y1-5)
7. **不確実性定量化装置** (Y1-7)

**Web Claude の 12 案は全て役割 1 (予測装置) の中での変奏**であり、役割 2-7 が選択肢列挙から欠落している。これが本ドキュメントの最大の盲点。

「あらゆる Exit 方法を学習して最適化」というまこさん発言は、必ずしも「ML で Exit を予測」を意味せず、「**ML で最適な Exit を探索する**」(役割 5: 探索エンジン) でも対応可能。Web Claude は **ML の役割そのものを「予測装置」に限定する暗黙前提**を疑っていない。

### 観点⑦ 補足: 自己申告 3 つの語彙偏向

Web Claude が自己申告した 3 つ (データを買う / 予測対象変更 / 学習データ増) は、いずれも **「現状路線を救う方向」または「楽な範囲の拡張」** であり、「**ML フレーム自体を変える**」方向の自己申告がない。これは audit#15 観点⑦ で指摘された「現状路線を救う方向の語彙」と整合する。**自己バイアス申告自体に同じバイアスが入っている**。

## 問B 判定 (X1 最有力バイアス)

### X1 が実際に最有力か (月次$1,900 達成見込み・正味コスト)

#### 月次$1,900 達成への道筋を X1 で計算

X1 (Exit を予測対象に追加) で達成しうる改善幅の上限:

1. **time_exit 採用 15 combo を fixed_tp 等に正しく振り分ける** → 独立再集計: time_exit -$2,833 と fixed_tp +$1,847 の差分から推定すると、time_exit 採用 combo を **正しく fixed_tp 等に振り替えた場合の最大改善幅 = +$2,833 (損失消去) + 既存 fixed_tp 4 combo の +$1,847 維持 = 合計 net で約 +$3,000〜+$4,500 改善余地**
2. ただし合計 -$985 から月次$1,900×12 = +$22,800 までは **$23,785 ギャップ**
3. X1 単体で改善できるのは推定 **+$3,000〜+$4,500** (= ギャップの **13-19%**)
4. → X1 単体で月次$1,900 全月クリアは **数学的にほぼ不可能** (達成率 13-19%)

ただし、X1 の本来の効果は「Exit 種別だけ」でなく「Exit パラメータ (tp_pct / time_bars) も同時 ML 化」を含む可能性。それを含めても改善余地は audit#15 の見立て「2-3 倍上限 (= +$5,177 × 2-3 = +$10,354〜+$15,531)」を超えない。月次$1,900 × 12 = $22,800 にはまだ $7,000〜$12,000 ギャップ。

#### 結論: X1 単体は最有力ではない

X1 単体での月次$1,900 全月クリア達成見込みは **低 (10-30%)** に留まる。「最有力」と Web Claude が断言した根拠は、audit#15 が指摘した「Phase 4-b 選定ロジックの構造的失敗を構造的に解消できる」という構造論であり、**月次$1,900 への必要十分性が定量検証されていない**。

### 「LightGBM の枠を活かせる保身」バイアスの該当性

Web Claude 自己申告 (§6 バイアス1) は **該当する**。根拠:

1. X1 は既存 LightGBM コード base から最小拡張で実装可能。Web Claude の実装スキルセット内
2. 同様の効果を得る代替案 X2 (強化学習)・Y1-4 (Bayesian Exit search)・Y1-5 (meta-labeling) は実装経験が乏しい領域 → **X2 を「軽々しく着手すべきでない」と書いた語感が、保身と整合**
3. X1 の上限改善幅 (audit#15 計算で +$3,000〜+$4,500) が**月次$1,900 への必要量 +$23,785 の 13-19%** であることを Web Claude は §5 所感で定量計算していない

→ **保身バイアスありと判定**。X1 「最有力」判定は実装容易性に anchor している疑い。

### まこさん発言「あらゆる Exit 方法を学習して最適化」への直接対応性

| 案 | まこさん発言への対応性 | 根拠 |
|---|---|---|
| **X1** (Exit を予測対象に追加) | **間接対応**。Exit 種別を ML が出力するが、「あらゆる Exit 方法」を**学習空間**に含めるかは設計次第。X1 単体だと time_exit / fixed_tp / trailing の3種類の中での選択に留まる |
| **X2** (強化学習) | **最も直接対応**。「Entry から Exit までの一連の行動」を一括最適化するため、「あらゆる Exit 方法」が**自然に学習対象**に含まれる |
| **Y1-4** (Bayesian Exit search) | **準直接対応**。Exit パラメータ space を ML 駆動で探索するため、グリッドの粗さに依存しない最適化 |
| **Y1-5** (meta-labeling) | **間接対応**。Exit でなく Entry の reject 判定に ML を使う |

→ **まこさん発言への直接対応性で見ると X1 < X2 ≈ Y1-4**。Web Claude の「X1 が直結」判定は、X2 の実装複雑性と X1 の実装容易性のトレードオフで X1 に anchor している。**直接対応性だけで判断するなら X2 / Y1-4 が優位**。

### X2 評価「軽々しく着手すべきでない」の実装回避バイアス

Web Claude が X2 を「期待効果は最大級だが実装難度・leak混入リスクも最大」「軽々しく着手すべきでない」と書いた点は、**実装回避バイアスに該当**。根拠:

1. **「期限なし」プロジェクト**で「実装難度高」を却下根拠にすると、「あらゆる組合せを試したい」というまこさん方針と矛盾
2. X2 の leak リスクは **「別形態」と書かれているが具体的にどの leak かが §3 で明示されていない**。reward 計算の未来参照が懸念だが、これは設計で塞げる種類 (offline batch RL なら past data のみ使用が確保できる)
3. **強化学習の学習不安定性**は実装手法選定 (PPO / SAC / DQN 等) で対処可能であり、「軽々しく」とまで切り捨てる根拠は弱い

→ X2 の評価には**実装回避バイアスが入っており、X2 を過小評価している可能性**を独立判定として明示する。

## 問C 判定 (組合せ実現性)

### まこさん提起「時間足×指標×閾値×Exit×サイズの全部組合せ」の ML 実現可能性

#### 各次元の組合せ数を概算

| 次元 | 候補数の目安 | 備考 |
|---|---|---|
| 時間足 (エントリー bar) | 4-6 (1m / 5m / 15m / 1h / 4h / 1d) | 現状 5m 固定 |
| 指標 | 1,432 | 現状 全投入 |
| 閾値 (q-level) | 3 (q90 / q95 / q99) | 現状 3 |
| Exit (種別 × パラメータ) | 種別3 × 連続パラメータ → 約 30-100 | tp_pct 10grid × time_bars 5grid |
| サイズ | 連続 (0.0001〜0.12 BTC) | 配分軸を加えると次元爆発 |

純粋な組合せ数 = 6 × 1,432 × 3 × 30 × 連続 = **約 800K combinations × 連続軸**。

#### 情報理論的・データ量の観点

- train サンプル数 394,753 行 (5m bar)
- 1 combination あたりの平均サンプル数 = 394,753 / 800K = **約 0.5 サンプル/combo**
- 統計的有意なサンプル数 (100 件以上・auditor_template ① C 基準) を全 combo で確保するには、**train 期間を 200 倍 (≈ 800 年分) 必要**

→ **純粋な「全部組合せ」の網羅探索は不可能**。データ量が決定的に不足。

### 「全部組合せ」の最短経路 (案組合せの独立判定)

#### 最短経路 1: 役割 5 (探索エンジン) として ML を使う

組合せ空間を**全部試す**のでなく、**ML が次に試す価値の高い組合せを predict** する。Bayesian optimization / Tree-based search の枠組み。
- Y1-4 (Bayesian Exit search) + W3 (K 窓見直し・連続化) + Y2-2 (時間長予測) の組合せ
- 全空間 800K combinations のうち 1% も試さず最適に近づける
- 月次$1,900 達成見込みは **中程度 (推定 30-60%)**

#### 最短経路 2: 役割 1 (予測装置) として ML を使い続け、Exit/サイズも ML に出させる

X1 + X4 + W3 を同時実装。
- 月次$1,900 達成見込みは **低-中 (推定 20-40%)**
- 利点: 既存 LightGBM 枠で実装可能
- 欠点: 「Exit を予測」「サイズを予測」の各ラベル定義に未来参照 leak が混入しやすい (`feedback_ml_leak_mandatory_check` 4 点要 verify)

#### 最短経路 3: 役割を一括変更 (X2 強化学習)

エージェントが Entry / hold / exit / size を都度判断。
- 月次$1,900 達成見込みは **低-中 (推定 20-50%・実装次第で大きく変動)**
- 利点: 「あらゆる組合せ」を学習空間に内包
- 欠点: 学習不安定性・leak の出方が複雑・実装数ヶ月

#### 段階的アプローチ (W3 → X1 → X4 / Y1-5)

W3 で K 窓拡張 → X1 で Exit ML 化 → X4 で size ML 化 → Y1-5 で trade rejector を被せる。
- 各段階で月次$1,900 への寄与を確認しながら追加
- リスク: 段階間で前 Phase の選定ロジックが固定され、組合せ最適性が失われる
- 月次$1,900 達成見込みは **中 (推定 30-50%・X1 段階で進捗止まり可能性)**

### 「全部組合せ」は月次$1,900 に必要十分か

#### 必要性 (必須かどうか)

- audit#15 で確認の通り、現状 Phase 5 v3 の **強い 4 combo +$5,177** を 4.4倍 (= +$22,800) にしないと月次$1,900 平均到達
- **次元ごとに 2-3 倍ずつ改善できれば** 4.4倍は可能 ( 例: 時間足 1.5x × Exit 最適化 1.5x × サイズ最適化 1.3x × 閾値最適化 1.2x = 3.5x)
- 各次元の改善が **線形に積み上がる前提が成立しない場合、4.4倍は組合せ全部最適化なしには困難**

#### 十分性 (組合せ全部やれば達成可能か)

- 組合せ全部の探索は技術的に不可能 (データ不足) → **十分性は確保されない**
- ただし**役割 5 (探索エンジン)** で空間を狭めて探せば、達成見込みが上がる

→ **「全部組合せ」は必要だが、純粋網羅は実現不能。役割 5 ベースの ML 探索が現実的最短経路**。

## 問E 判定 (分類軸)

### 「枠内W / 枠外X」分類の単一性問題

主審査対象 §3 の「枠内 / 枠外」分類は **「spec 改訂規模」のみを軸**にした単一分類。この分類が「**変更幅が小さい方が安全**」という暗黙前提を含む (Web Claude 自己申告・§6 バイアス2)。問題:

1. **達成見込みと関係ない**: spec 改訂規模が小さい (W) ほど月次$1,900 達成見込みも低い (独立判定: W1-W4 はすべて「絶望的-低」)
2. **leak リスクと関係ない**: 枠内 W2 (特徴量追加) と枠外 X5 (regime 統合) は同程度の leak リスク
3. **実装時間と関係ない**: 枠内 W4 (1-2週) と枠外 X4 (1-2週) は同等
4. **ロールバック容易性と関係ない**: W3 (K 窓除外) のロールバックは git revert 1 コミットで可能だが、X1 のロールバックは Phase 4-a/4-b 全体やり直しで時間大

### 推奨される追加分類軸 (具体的に併記すべき軸)

| 軸 | 評価対象 | 採用根拠 |
|---|---|---|
| **達成見込み (5段階)** | 月次$1,900 への到達確率 | まこさんの絶対目標との直結性 |
| **正味 leak リスク (低/中/高)** | 未来データ混入の検出難度 | プロジェクト最大の事故源 (audit#12 trailing exit / L-179 fractal で 14 段階素通り経験) |
| **実装時間 (日/週/月)** | 各 Phase 完了までの所要セッション数 | 「期限なし」でもセッション数は有限 (audit#15 で 16-28 セッション概算) |

| **ML フレームの役割 (1=予測 / 2=異常検知 / 3=変換 / ...)** | 問A で抜けた「役割」軸を併記 | Web Claude が役割 1 に閉じている事実を可視化 |
| **まこさん発言『あらゆる Exit を学習』への直接対応性 (高/中/低)** | まこさん自身の言葉での要件適合性 | まこさんが「これは私の要件に応えているか」を直接判断できる |

X2 (中) > X1, X4, X5, X6, W4 等 (低) > W1, X7 (絶望的)

→ Web Claude の「最有力 X1」は達成見込み軸では X2 に劣る (X2: 中 / X1: 低)

#### 「正味 leak リスク + 達成見込み」のパレート最適

| 案 | leak リスク | 達成見込み | パレート最適か |
|---|---|---|---|
| W1 | 低 | 絶望的 | 含まれない (達成低) |

Web Claude 比較表 §4 に以下 4 軸を**横断的に併記**することを推奨:

## 監査も気づいていない観点 (見落とし最大限)

### 盲点 1: 「ML をやる/やらない」の二項対立の中間がない

Web Claude 12 案は **すべて「ML を使い続ける」前提**。X8 のみが「ML を捨てる」だが、これも極端な対立。**中間の「ML を補助装置に格下げし、ルールベース主軸に戻す」**選択肢が明示されていない。

具体的に: 既存 Priority P1〜P24 の凍結ベースライン月次$370 をルール主軸に戻し、ML を **「P1〜P24 のエントリーを reject する meta-labeler」** (Y1-5) としてのみ使う案。これは Web Claude 12 案にも 16 追加抜けにも完全には含まれていない。

### 盲点 2: 「役割 1 (予測装置)」内での選択肢追加と「役割 2-7 への移行」が同じ軸で比較されている

問A で「役割 1 内 (X1-X8)」と「役割 2-7 への移行 (Y1-1〜Y1-7)」を**同じ分類軸 W/X で扱えるか**が議論されていない。実は **異なる選択木 (decision tree) の異なる level**であり、まず「役割 1 のままか役割 2-7 に移行するか」を決めてから、その下で個別案を選ぶ二段階構造が正しい。Web Claude は二段階を一段階に潰している。

### 盲点 3: Phase 4-b 選定ロジック自体を ML 化する選択肢が独立提示されていない

audit#15 が指摘した「Phase 4-b best Exit 選定の構造的失敗 (train PnL idxmax で test 2025 net -$985)」は、**X1 (Exit を予測対象) では解けない**可能性がある。X1 は「各 entry での Exit 種別を ML が出力」だが、Phase 4-b の問題は「**cluster 別 best Exit の選定基準**」自体の data snooping (L-183) であり、これを ML 化する選択肢は Web Claude にも追加 16 案にも含まれていない。

→ 真に audit#15 の指摘に対応する案は **「Phase 4-b 自体を廃止し、ML が exit decision を per-entry で出す」(X1 の拡張形)** ではなく、**「Phase 4-b 選定基準を train data only の robust statistics (例: bootstrap 信頼区間下限) で行う」(non-ML 統計改善)** かもしれない。これは「ML 選択肢」の議論軸から外れているため Web Claude 12 案には絶対入らない。

### 盲点 4: 「ML をどう使うか」と「目標額を再評価するか」が独立に議論されていない

監査依頼書では「目標 (月次$1,900) を下げる提案禁止」と明示されているが、これは Web Claude の議論に **「目標額に応じて適切な ML フレームが変わる」観点を入れさせない**制約。**目標を下げないという制約下で、現実的に達成可能な ML フレームは存在するのか**自体が独立に問われていない (Web Claude は質問に対し 12 案を列挙したが、「達成不能なので戦略レベルから見直す」回答はしていない)。

依頼書の制約により監査側もこの観点を「目標下げ提案」として禁止されているが、**「ML だけでは月次$1,900 達成は構造的に不可能で、ML + 人手介入 (まこさんの裁量フィルタ)・ML + 別シンボル (制約と矛盾) ・ML + より大きな証拠金 (規定外)」のような外部追加要素が必要**な可能性が議論されていない。

### 盲点 5: 「12 案を提示する」行為自体が「決定の質」を低下させている可能性

認知科学では選択肢数が **多すぎる** と決定の質が下がる現象 (choice overload / paradox of choice) が知られる。Web Claude が 12 案 + 自己申告 3 + 監査側 16 追加 = 合計 31 案を提示すると、まこさんは**「全部 ML 標準観点で並べているように見える」表面的な網羅性で判断する**リスクがある。

「広く浅く版」(主審査対象 §位置づけ) というアプローチが、**「深い差別化を回避するための逃げ」**になっていないか。実は **3 案に絞って深掘り** する方が決定の質は高い。Web Claude 自己申告 §6 バイアス1 が「現状路線を救う方向」と指摘するが、**12 案を並列に並べる行為自体が「決定回避」**の機能を果たしうる。

### 盲点 6: 「LightGBM 16 モデル」前提の見直しが含まれていない

主審査対象 §1 で「16 モデル」(K=12/24/48/96 × LONG/SHORT × MFE/MAE) が当然の構造として扱われている。だが**「16 モデル独立」**は ML 設計選択であり、以下の選択肢がない:

- **マルチタスク学習 (1 モデル 16 出力)**: 共有特徴量から 16 ラベルを同時予測。X1 で言及されている「マルチタスク学習」と類似だが、独立案として明示されていない
- **階層モデル (LONG/SHORT 二段 → K 窓選択 → MFE/MAE)**: 各 K 窓・各 side で独立に学習しない
- **K 窓を入力特徴量化**: 「K を予測したい時間長」として ML への入力に含める。1 モデルで全 K 窓カバー

これらは Web Claude 12 案で「X2 強化学習」と並列に提示されるべき**モデル構造の選択肢**だが、抜けている。

### 盲点 7: Web Claude が「期間なし」プロジェクトを「数ヶ月の実装期間」で評価している

X2 (強化学習) を「実装数ヶ月」「軽々しく着手すべきでない」と評価する語感は、「**期間なし**」プロジェクトの制約と整合しない。「期間なし」なら数ヶ月の実装は許容されるはず。**「数ヶ月」を否定的形容詞で扱う Web Claude の語感**が、まこさん方針 (期限なし) と矛盾している。

audit#15 盲点5 で「期限なしが事後追認構造を強化する」と指摘されたが、**逆方向の問題 (期限なしなのに数ヶ月を長いと評価する語感)**が今回新規に発見できる。

### 盲点 8: feedback_ten_trials_minimum.md (新規シグナル検証は最低10候補 × 365d) との整合性

ユーザー memory に「新規シグナル検証は最低10候補×365d検証してから撤退判断 (feedback_ten_trials_minimum)」がある。Web Claude 12 案のうちいくつかは「数日」「1-2週」と短期評価が前提だが、**まこさんの方針では各案を 10 候補 × 365d で評価する必要がある**。これを明示している案がない。各案の「実装時間」見積もりが**まこさんの検証要件を満たしていない**疑い。

### 同型バイアスゆえに収束しそうな結論の自己警告

監査エージェント (私) の最終結論は:
- **「X1 単体では月次$1,900 達成不能」「X2 が達成見込み最高だが実装幅広い」「役割 1 (予測装置) 内の議論を役割 2-7 に拡張すべき」**

これらは Web Claude も内心同じ結論に至る可能性が高い (同じ LightGBM 知識ベース・同じ標準観点を持つため)。**同型バイアスゆえの収束が結論の正しさを保証しない**ことを明示する。

ただし、本監査では:
1. **追加 16 案 (Y1-1〜Y4-2)** を独立提示した。Web Claude 自己申告 3 案より具体的かつ ML フレーム自体の拡張を含む
2. **5 段階判定で全 12 案に楽観バイアスがあることを定量提示**。Web Claude の「最有力 X1」を「低 (10-30%) 」と独立判定
3. **問C 最短経路の独立判定 (役割 5 = Bayesian 探索エンジン)** を提示。Web Claude §4 補足の3 例組合せに含まれない

5. **分類軸 (達成見込み + leak リスク + まこさん発言対応 + ML 役割)** の併記推奨は Web Claude 単一軸を構造的に否定する

これらは Web Claude framing 内では出にくい指摘であり、**完全な同型バイアスではない**と自己判定する。

### まこさん (人間・非 ML 専門家) が AI 3 者の同型バイアスを疑える材料

1. **「全 12 案で楽観方向に偏っている」(問D 比較表)** という構造的事実は、Web Claude / 監査が同じ訓練ベース AI で「実装可能性のある案を悪く言いたくない」共通バイアスを持つ可能性
2. **「X2 を軽々しく着手すべきでない」(Web Claude) vs 「X2 を過小評価」(監査)** の対立構造は同型バイアス内の振れ幅であり、結論「X2 が最も達成見込み高い (中 30-60%) 」も実装証拠なしの推定
3. **盲点 1 (ML/ルールベースの中間)** ・盲点 4 (目標見直し) は監査依頼書の制約により議論から排除されている。**「制約により議論できない」観点こそ、AI 3 者全員が見落とす可能性が最も高い場所**
4. **盲点 5 (12 案提示行為自体が決定の質を下げる)** に対して、監査も結局 16 案追加・31 案レベルの提示に至った。**監査自身が「広く浅く列挙」のメタ構造に取り込まれている**疑い
5. **「数値 verify は完璧に一致」「論理整合性も保てる」が、まこさんの絶対目標 (月次$1,900) への現実的経路は依然見えない**。データと論理が両方揃って結論が出ない時、**問題設定自体 (目標額 vs ML スコープ) を疑う必要**がまこさん側に残る

### 数値 verify

### 問A (網羅性)

- Web Claude 12 案 + 自己申告 3 = 15 案に対し、**外部基準で 16 案を独立追加** (Y1-1〜Y4-2)

- 12 案は ML 標準観点で見ると**約 1/2 の網羅率**

### 問B (X1 最有力バイアス)

- X1 単体での月次$1,900 達成見込みは **低 (10-30%)** に独立判定。必要改善幅 +$23,785 の 13-19% しか改善余地がない

- まこさん発言「あらゆる Exit 方法を学習」への直接対応性は **X1 < X2 ≈ Y1-4 (Bayesian Exit search)**
- X2 評価「軽々しく着手すべきでない」は**実装回避バイアスに該当**

### 問C (組合せ実現性)

- **純粋な「全部組合せ」は実現不能** (約 800K combinations × 連続軸に対し train 394,753 行で平均 0.5 サンプル/combo)
- 最短経路 = **役割 5 (探索エンジン) として ML を使う Bayesian 最適化**。Y1-4 + W3 + Y2-2 の組合せ
- 「全部組合せ」は月次$1,900 達成に**必要だが純粋網羅は不可能。ML 探索ベースが現実解**

### 問D (5段階判定)

- **単独で月次$1,900 達成可能な案はない** (全 12 案で「絶望的-中」に分布・最高でも X2 の中 30-60%)
- Web Claude の「期待効果」評価は**全 12 案で楽観方向に偏っている** (12 案中 10 案で監査が下方修正)
- 月次$1,900 達成は単独案ではなく**案組合せ + ML フレーム再定義 (役割 2-7)** が必要

### 問E (分類軸)

- 「枠内 W / 枠外 X」分類は**単一軸 (spec 改訂規模) のみ**で、達成見込み・leak リスク・実装時間・ロールバック容易性・ML 役割・まこさん発言対応性と関係ない
- 推奨: **6 軸併記** (達成見込み / leak リスク / 実装時間 / ロールバック容易性 / ML 役割 / まこさん発言対応性)
- 別軸での並び替えで **パレート最適は W3 と X2** に集約され、Web Claude の「最有力 X1」とは異なる結論
