### 2.2 ★一致しなかった項目（本監査の最重要の発見）

#### 発見1 — 「1試行7秒」は engine_tuner の実測値ではありません。実測は 0.32秒 と 2.29秒 でした

engine_tuner が実際に呼ぶ経路を、いまの値決め窓で計測しました。助走60日込み 52,416バーです。

| 経路 | 実測（3回平均） | 依頼書・要件書の主張 |
|---|---|---|
| e38 アダプタ `ad.run(df,"S2",…)` | **0.32 秒**。`score.score` 0.09 秒を足して約 0.41 秒 | 7 秒 |
| e37 アダプタ `ad.run(df,"v59",…)` | **2.29 秒** | 7 秒 |

「7秒」の出どころは `gen_engine_tuner_manual.py:61` に文字列で直接書かれています。もとの実測は `lessons_active.md:29` の「engine_search_e37.py（共通部分キャッシュで1試行7秒・200試行25分）」です。**別の道具の実測値を、engine_tuner の実測値として機械生成の説明書に転記した状態です。** 2026-07-27 の V9 Exit 事案と同じ型の誤りです。

この誤りは飾りではありません。R7 の存在理由そのものが「1試行が実測でおよそ7秒」だからです。実測 0.41 秒なら、30分・6並列で回せる試行数は約 26,300 回です。要件書と依頼書が前提にしている約 1,500 回の**17倍**です。R7 の絞り込み設計は、17倍きつい制約の上に建てられています。

#### 発見2 — 依頼書の試行数の算術が内部で矛盾しています

依頼書 L192 は「1試行7秒・目標30分（≒約1,500試行を6並列なら約8,600試行相当）」と書いています。
30分は 1,800秒です。6並列で 10,800 プロセス秒です。7秒で割ると **1,543 試行**です。8,600 という数字はどの組み合わせからも出ません。
正しい数字は次の通りです。7秒前提なら 1,543 試行です。実測 0.41 秒前提なら **26,341 試行**です。

#### 発見3 — 「E37 が42回失敗した」の出典が社内に存在しません

requirements.md:90 は「数個の決め打ちは E37 が42回失敗したやり方。」と書いています。
`42回` を全 `.claude/` から検索すると、ヒットするのは requirements.md と同 json の2箇所だけです。社内の記録は22回です。`entry_exit_matrix.md:29`「E37 が v2〜v13 の22回」。`lessons_active.md:123`「v2〜v13 の22回失敗」。`lessons_active.md:4762`「v2〜v11oe の22回」。
機械生成の要件定義書に、出典のない数字が事実として入っています。

#### 発見4 — 4部品の分類は 96種のうち 27種を無言で圏外にします

設計の4部品に列挙された系統に、カタログの96指標を機械的に割り当てました。

| 部品 | 該当指標数 | 時間足数 | 列数 |
|---|---|---|---|
| 環境認識 | 19 | 5 | 95 |
| トリガー | 18 | 2 | 36 |
| 十分性 | 15 | 3 | 45 |
| 位置 | 17 | 3 | 51 |
| **どの部品にも入らない** | **27** | — | — |

入らない27種は次の通りです。ROC6/12/24。OBV傾き10/20。close vs 転換線%(9)。close vs 基準線%(26)。包み足。pinbar。連続本数。body比。上ヒゲ比。下ヒゲ比。高値からの経過バー24/48/96。安値からの経過バー24/48/96。形スコア24/48/96。close vs VWAP%288。close vs Keltner上/下。close vs Supertrend%。close vs pivotPP%288。

設計は「分類できない指標は『その他』として一覧に出す（黙って落とさない）」と書いています。しかし4部品のどこにも席が無い以上、一覧に出ても探索されません。「落とさない」の意味が「表示する」にすり替わっています。

とくに包み足と pinbar は entry_exit_matrix の E-e(2)「反転ローソク（陰陽転・pinbar・engulfing）」として確認軸に明記されている部品です。V9 P23 の入口条件にある「陰線」も同じ系統です。設計自身が「V9 の条件は『陰線』のように形と関係で書かれている」と書きながら、その陰線を扱える部品を4分類から外しています。

#### 発見5 — 「値が無い列だけ落とす」で落ちるのは 768列中 7列だけです

値決め窓で 768列を実際に構築し、欠損率を測りました。

- `build_features` の所要時間は **108.7 秒**です。52,416バー × 768列・1窓あたりです。
- 欠損率 > 50% の列は **7列**です。768列の 0.9% です。
- 欠損率 > 0% の列は 23列です。
- 生き残る列は **761列**です。

R7 ① の「落とすのは値が無い列だけ」は、実測で 0.9% の削減しか生みません。これを絞り込み設計の第1段として提示することは、実質的に段が空であることを隠しています。

#### 発見6 — 「相関がほぼ1の列を束ねる」は、ほとんど束ねません

同じ 761列で相関行列を作り、階層クラスタリングで切りました。complete linkage・距離は 1−|ρ| です。

| 束ねる基準 | クラスタ数（元 761列） | 削減率 |
|---|---|---|
| \|ρ\| ≥ 0.98（＝「ほぼ1」） | **595** | 22% |
| \|ρ\| ≥ 0.95 | 513 | 33% |
| \|ρ\| ≥ 0.90 | 396 | 48% |
| \|ρ\| ≥ 0.80（業界標準の閾値） | **263** | 65% |
| \|ρ\| ≥ 0.70 | 190 | 75% |

固有値から見た実効次元は **34.1** でした。分散の90%を説明するのに必要な主成分は78本です。95%で131本です。
768列の情報量は実質 34〜263 本ぶんしかありません。設計の「ほぼ1」という基準は、業界標準の ρ≥0.8 より2段階ゆるく、実効的にほとんど何も束ねません。

#### 発見7 — 探索空間は絞っても全数試行に届きません。5〜9桁の差があります

4部品から1本ずつ取る組み合わせは 95 × 36 × 45 × 51 = **7,848,900 通り**です。
各部品に「上下どちら側か」を掛けると ×16 で 1.26億通りです。
閾値を observe_diag と同じ分位7段で刻むと ×7⁴ で **約 3.0 × 10¹¹ 通り**です。
実測 0.41 秒・30分・6並列で回せるのは 26,300 試行です。**カバー率は 0.0000088%** です。
|ρ|≥0.8 で束ねて列数を 34.6% に減らしても、空間は 4.4 × 10⁹ 通りでカバー率 0.0006% です。

ここが設計の最大の論理のすり替えです。**設計は「落とさない＝嘘をつかない」と書いていますが、落とさなくても 99.9999% は試されません。**「何を落としたか」を機械出力しても、出るのは「7本」だけです。本当に知るべき「どれだけ試していないか」は出ません。

#### 発見8 — 診断は採点窓の中でしか動きません

`observe_diag.py:100` は `from periods import SCORE_START, SCORE_END` を読みます。同 185-189 行で採点窓の外を指定すると停止します。マニュアルの「検証できる期間」も採点窓だけです。
一方 engine_tuner は値決め窓の 2024-04〜07 で値を選びます。
使う順番は「observe_diag で診断 → 改善点を見出す → その改善案に基づき engine_tuner でチューニング」です。
**この経路は、採点窓で見つけた改善点が engine_tuner の探索対象を決める構造です。** L-267 と正面から衝突する経路が、フローの中心に置かれています。この経路をどう遮断するかを決めるのが要件 R10 です。R10 は未着手です。

### Q0（最重要）— この設計で、道具の目的を達成できるか

#### (a) 目的1（組み合わせを見つけて「調整しきる」）に届くか — **届きません**

理由は2つあり、どちらも数値根拠があります。

**理由1。「調整しきる」の終わりの条件が、この設計のどこにも書かれていません。**
R3 の完了の線は「扱えること／使える列の数が出ること／セットで探せること」です。これは道具の**機能**の線です。
R7 の完了の線は「段階的に絞る手順が決まっていて、各段の所要時間が機械で出ること」です。これも**手順**の線です。
どちらも「どの数字がどうなったら、この調整を終わりにしてよいか」を1行も定義していません。R8 で目的関数は決まりましたが、目的関数に上限は無いので、最大化は永久に終わりません。

**理由2。探索空間の 99.9999% は試されません。** だから「あらゆる組み合わせから最適なセットを見つけた」とは原理的に言えません。発見7の通りです。

終わりの条件として置くべきものを示します。値はまこさんが決める前提で、枠だけを提示します。

| # | 終わりの条件（すべて満たしたら終わり） | なぜ必要か |
|---|---|---|
| 1 | 直近2段で、値決め窓の目的関数の改善が δ 未満。δ はまこさんが決める | 収穫逓減の停止規則。これが無いと永久に回る |
| 2 | 試行数の上限 N_max に到達。N_max は着手前に宣言し、途中で増やさない | 事前登録。途中で増やすと多重検定の N が事後的に膨らむ |
| 3 | DSR > 0.95。有効試行数 N_eff で補正する | cat_requirements H11 |
| 4 | PBO < 0.5 | 同上 |
| 5 | 件数/日 ≥ 5 | §8.6 の絶対下限。役割からの逸脱を止める |
| 6 | ATR% の全帯で、採択候補が土台を悪化させない | ARC31/ARC32 の実証。低ボラ帯の見かけ改善を止める |
| 7 | 確認窓の表示が値決め窓と同符号 | 選び直しはしない。符号が割れたら「調整しきれていない」と宣言する |

**この7条件は、探索を始める前に宣言する必要があります。** 探索の途中で条件を決めると、それ自体が採点窓の覗き見と同じ構造になります。

#### (b) 目的2（改善すべき点を見つけて調整しきる）に届くか — **届きません。設計の穴です**

診断の出力が engine_tuner のどこに入るかは、この設計のどこにも定義されていません。定義するのは要件 R10 で、R10 は未着手です。
いま存在する唯一の入力口は R8 の `--minimize <exit_reason>` です。これは出口理由の名前を1つ渡すだけの口です。
observe_diag が実際に出しているものは、それよりはるかに広いものです。フェーズ8は「改善の条件の候補を探す」です。フェーズ9は「両方の期間でプラスの候補だけを抜き出す」です。フェーズ10は「この結果から次に何をすべきかを出す」です。フェーズ11は「建てていれば取れた条件」です。

**observe_diag は「指標 × 時間足 × 閾値」の候補まで出しているのに、engine_tuner はそれを受け取る口を持っていません。** 現状の受け渡しは人の手です。要件 R10 の「なぜ要るか」に書かれている「毎回ぶれる」がそのまま残ります。

さらに深刻な点があります。**observe_diag は採点窓でしか動きません。** その候補をそのまま engine_tuner の探索対象の絞り込みに使うと、採点窓で選定したことになります。L-267 違反であり、false_positive 類型C です。

穴を塞ぐ方向を示します。

1. 診断の出力を機械可読な1ファイルに固定します。中身は「減らしたい出口理由」「注目する部品と時間足の候補」「増やしたい場面」の3種だけにします。
2. その候補は探索空間を狭めるためには使いません。Optuna の `enqueue_trial` で**最初に試す順番**としてだけ使います。順番は結果を変えないので、採点窓の情報が選定に入りません。
3. 「候補で空間を絞った」場合は機械が停止する番人を置きます。
4. R10 を R3・R7 と同時に決めます。**R10 を後回しにすると、目的2 は R3・R7 が完了しても達成できません。**

#### (c) 完了の線は目的を満たすのに十分か — **不十分です。3つの穴があります**

**穴1。R3・R7 の線を全部満たしても、いま実際に稼いでいるロジックは1本も調整できません。**
説明書の一覧では、登録12本のうち回せるのは8本です。回せない4本のうち S1 と L1 は「実装が e37_scalp＝共通の売買ループで動かない」ためです。S1 は採用土台 v59d_164 相当です。これを直すのは要件 R1 で、R1 は作業中です。
**目的2 は、R3・R7 が完了しても R1 が終わるまで実行できません。** 完了の線がこの依存を書いていません。

**穴2。線に「絞ったときに何を落としたか」はありますが、「どれだけ試していないか」がありません。**
落ちるのは7本です。試されないのは 3×10¹¹ 通りです。出力すべきは「落とした本数」ではなく「試した割合」と「未探索領域の大きさ」です。

**穴3。線に多重検定の補正の合否が入っていません。**
R7 の設計本文には DSR/PBO が書かれていますが、完了の線には入っていません。線に入っていない項目は実装時に落ちます。H11 は合格ラインの正本なので、線に明記すべきです。

### Q1 — 4部品への分け方は妥当か

分け方の骨格は妥当です。トレンド系・オシレーター系・ボラ系の相互補完は technical KB §2.2／§2.3／§2.4 と一致します。V9 P3 の3系統 AND とも整合します。「位置」を4本目に足したことは、レンジ逆張りでは場所が方向を決めるので合理的です。

**足りない部品が3つあります。うち1つは自社の実験が「次の軸」と名指ししたものです。**

1. **玉と枠の状態（スロット・クールダウン）。** これが最も重い欠落です。`entry_exit_matrix.md:200`（ARC29・L-330）は、状態機械が中立化した原因を「スロット再回転の相殺」と特定しています。早期撤退すると入口が即再エントリーし、救った損を新玉の負け期待値が食う、という構造です。そして次に筋のある組を「(A) #22＋クールダウン＝機械退出後 N 本再エントリー禁止・Exit×Entry 結合部の新軸」と書いています。4部品にはこの軸がありません。`generic_logic_loop` は `max_lots` と `pend` を持つだけで、直前決済からの経過や枠の空き具合を入口条件にできません。
2. **時間帯・曜日。** 5分足スキャルでは標準の軸です。カタログ96種に時刻由来の列は1つもありません。funding の精算時刻は 00/08/16 UTC で確定しています。保有5〜60分のスキャルでは funding 跨ぎの有無が単価に直接効きます。
3. **需給・オーダーフロー。** `observe_diag.load_demand` が taker 比・L/S 比・CVD を読み込む実装を既に持ち、被覆率も報告します。4部品はこれを丸ごと外していますが、外した理由が書かれていません。E28 で有効・E37 SHORT で AUC 0.52 という混在した実測があるので、外すなら実測を引いて外すべきです。

**不要な部品はありません。** 4つとも別の役割を持ち、重複していません。

### Q4 — たくさん試して最良を選ぶことへの補正は十分か

**不十分です。方向は正しいのですが、適用の条件が1つも書かれていません。**

#### (1) Optuna に DSR/PBO をそのまま当てると、補正が甘くなります

`archive/dsr_pbo.py:44-54` の `expected_max_sharpe` は、独立試行 N 回で真のスキルがゼロのときに期待される最大 Sharpe を返します。式の中の V は**試した全戦略の Sharpe の分散**です。
TPE は良い領域に試行を集中させます。その結果、**sr_estimates の分散 V が縮みます。** V が縮むと SR0 が縮み、DSR が過大に出ます。同ファイルの docstring 自身が「過少申告すると DSR が過大化」と警告しているのは N についてですが、V にも同じことが起きます。
**TPE の試行だけから V を推定すると、補正が構造的に甘くなります。**

#### (2) 「試行数 N」の数え方の答え

N は Optuna の trial 数ではありません。3つの層を足します。

- **N1。** 実際に評価した回数を数えます。評価していない点は選択バイアスを生みません。
- **N2。相関で割り引きます。** López de Prado & Lewis (2019) の ONC アルゴリズムは、バックテストの収益系列をクラスタリングして「実効的に無相関な試行数」を出します。これが DSR に入れるべき N です。実測では 768列の実効次元は 34.1、|ρ|≥0.8 のクラスタ数は 263 でした。試行の収益系列も同程度に相関するはずなので、N_eff は生の試行数よりかなり小さくなります。
- **N3。人間の反復を足します。** engine_tuner の1セッションの試行だけでなく、同じ値決め窓に対して過去に行った全ての探索を累積して数えます。E37 は v2 から v59 まで到達しています。累積カウンタのファイルを1本置き、engine_tuner が起動のたびに加算する仕組みが要ります。

**結論の式は次の形です。** N_eff = ONC(全試行の収益系列) + 過去セッションの実効試行数の累積。この N_eff を DSR に渡します。

#### (3) T の取り方が未定義です

`score.py:151` は月次で集計します。値決め窓は 122日で 4ヶ月です。**月次リターンで DSR を計算すると T = 4 です。** PSR は √(T−1) = √3 なので、統計量として意味を持ちません。
**日次リターン（T = 122）を使う必要があります。** そのためには trades CSV から日次 net 系列を作る処理を新設します。設計にこの記述がありません。

#### (4) PBO の入力行列の作り方と計算量が未定義です

`pbo_cscv(perf_matrix, n_blocks=10)` は shape (T, N) の全試行の1期リターン行列を要求します。

- 行列の生成方法が設計に書かれていません。engine_tuner は `results` に trades を保持しているので生成は可能ですが、日次化の処理が要ります。
- 計算量が問題になります。C(10,5) = 252 通り × N 戦略 × 2 の Sharpe を Python ループで回します。N = 26,300 なら 1,325万回の呼び出しになり、数十分かかります。**`pbo_cscv` のベクトル化が必須です。**
- 統計的にも N ≫ T は不健全です。T = 122、N = 26,300 では IS 最良はほぼ確実にノイズです。**PBO には全試行ではなく、重複を除いた候補集合を渡すべきです。** 例えばクラスタ代表の上位数百です。

#### (5) DSR/PBO より適した手法。両方使うのが正解です

| 手法 | 何に効くか | この設計での使いどころ |
|---|---|---|
| **White の Reality Check / Hansen の SPA** | 「最良の1本がベンチマークを超えるか」の族全体の検定 | 段の最後に、土台 v59d_164 をベンチマークにして1回 |
| **Romano-Wolf StepM** | 「どれとどれが有意か」を段階的に。RC より検出力が高い | 上位複数を残すという ④ と相性が良い |
| **BH / BHY による FDR 制御** | 有意な候補を複数選び分散したいとき | ④「最良を1つだけ選ばない」を統計的に裏づける唯一の手法 |
| **DSR** | 選択バイアスと非正規性と標本長 | H11 の合格判定 |
| **PBO（CSCV）** | 過学習の確率 | H11 の合格判定 |
| **CPCV** | 学習/検証分割そのものの頑健化 | 値決め窓を purged block に切って探索する形へ |

**ただし重要な限界があります。** CPCV も DSR も PBO も、**同じデータで何十もの「戦略のアイデア」を試すメタ過学習は防げません。** E37 は v2 から v59 まで、同じ枠組みで数十のアイデアを試しています。**この累積が N に入らない限り、DSR>0.95 は形式的な合格にしかなりません。**

#### (6) 適応的探索そのものへの正しい対処

TPE は前の結果を見て次を選ぶので、独立試行を前提とする補正の仮定を破ります。実務上の解は2つです。

- **解A（推奨）。段を2つに分けます。** 段1はランダムサーチで N1 回回します。ランダムサーチの試行は互いに独立なので、V の推定・RC/StepM/FDR の p 値・PBO の行列は**すべて段1のサンプルだけから作ります**。段2は TPE で精緻化しますが、**段2の結果は統計的判定に使いません**。値の微調整だけに使います。
- **解B。事前登録と固定予算です。** 試行数の上限を着手前に宣言し、途中で増やしません。停止規則も先に決めます。

### Q5 — 「1つずつ試した成績で列を落とさない」は実務として成立するか

#### 判断そのものは正しいです

単軸の成績で列を落とすと、代替効果で相互作用のある列が消えます。これはクラスタベース特徴選択の文献が繰り返し示している標準的な結論です。コンフルエンスを探すこの設計では、単軸フィルタは目的そのものを壊します。**この判断は維持すべきです。**

#### ただし、この判断は実務上の制約ではありません。ここが設計の誤解です

発見7の通り、落とそうが落とすまいが 99.9999% は試されません。**制約は「何を落とすか」ではなく「限られた試行をどこに置くか」です。** 設計は前者を丁寧に議論し、後者をほぼ議論していません。

#### 実測値に基づく、具体的な取り扱い

前提を実測値に置き換えます。1試行 0.41 秒、30分、6並列で **26,300 試行**です。指標の一括生成は1窓あたり 108.7 秒で、これは1回だけなので parquet にキャッシュします。

30分の目標にほぼ収まります。**7秒前提では 1,500 試行しか回せず、この段構成は組めません。だから前提の実測やり直しが着手の前提条件になります。**

業界標準の使い分けも答えます。

- **ランダムサーチ**は高次元では格子より効率的で、かつ独立性が保たれるので統計判定の土台になります。段1に最適です。

- **遺伝的アルゴリズム**は評価が高価で勾配が無い離散空間に向きますが、多重検定の統計量を出しにくいので、この用途では劣後します。

## 7. CC プロセス欠陥対策

本監査で見つかった欠陥は3つで、いずれも仕組みで止められます。

### 欠陥1。機械生成の文書に、手書きの数値が混入しています

`gen_engine_tuner_manual.py:61` は「実測でおよそ7秒かかる」を文字列で持っています。`engine_tuner_requirements.json` は「42回」を持っています。
文書の見出しは「gen_*.py が自動生成＝手書き禁止」です。しかし生成器の中身が手書きなら、機械生成の保証は「生成器を編集しないと変わらない」だけで、「実体と一致する」保証にはなりません。**これは V9 の Exit 要約と同じ構造です。** あれは手書き要約を実装の事実として扱いました。

**対策。** 生成器の中で数値を出す箇所に印を付ける規約を作ります。印は2種類だけにします。「実体から取った値」と「出典つきの引用」です。どちらでもない数値は生成器に書けないようにします。`--verify` に、印の無い数値リテラルを検出する検査を足します。

### 欠陥2。要件の完了の線が「機能」だけで、「目的」を見ていません

R3・R7 の完了の線は、どちらも「〜が扱えること」「〜が機械出力で出ること」という機能の線です。目的の「調整しきる」「改善点を見つけて」に対応する線がありません。
**この形の線は、要件が全部完了しても目的が未達のまま「完了」と宣言できてしまいます。**

**対策。** 要件 json の各要件に「目的1に効くか／目的2に効くか」の欄を必須にします。どちらにも紐づかない要件は登録できないようにします。さらに「この線を全部満たしたとき、目的のどこがまだ残るか」を1行で書く欄を足します。engine_tuner.py の説明文に目的2つが書いてある以上、その2つとの対応は機械で照合できます。

### 欠陥3。道具ごとの窓が違うのに、道具をつなぐフローに窓の検査がありません

observe_diag は採点窓だけです。engine_tuner は値決め窓だけです。両方とも単体では窓を物理ゲートで守っています。observe_diag.py:185-189 と engine_tuner.py:69-70 です。
しかし**2つをつなぐフロー**には検査がありません。診断の結論が探索の対象を決める経路は、窓を越境します。

**対策。** 道具の出力に「どの窓で作った数字か」のタグを必ず付けます。engine_tuner が外部の候補ファイルを読むときは、タグを見て「採点窓由来のファイルを探索空間の宣言に使っていないか」を起動時に検査します。使っていたら止めます。**順番のヒントとしての利用だけ許可します。**
