## 監査観点 (本監査固有・Q-C〜Q-E)

### Q-C — 「効果」を測る道

事実データ1の定義（効果＝net・Entry/Exit を固定して束だけ差し替える・判定の1枚表 B1/B2/B8・R9 の①③）は、レンジ判定の良し悪しを測る道として正しいか。**足りないもの・間違っているものを断言する。**特に①「Entry/Exit を何に固定するか」（採用土台 S2 の恒等レシピか・別か）②**測る道が2つ（net＝機械／⑪タブ＝まこさんの目）在ることを前提に、2つの関係**＝net が良いが絵がおかしい束・絵は正しいが net が悪い束が出たとき、どちらを先に見るか・どう戻すか（M2-5 へ戻る／Entry/Exit の側を疑う）③事実データ0（うちの実測）から根拠をもって言えること（起案 CC の読み＝件数は桁で動くが net は Entry/Exit と出口が支配、が合っているか）④「判定だけを差し替えて net を比べる」測り方の統計的な落とし穴（判定が真の時間の長さで net が変わる・選んだ束が値決め窓に過剰に合う）を、外部検索1件で確かめる。

### Q-D — いまの束が法則のどれを満たすか

事実データ3（起案 CC の数え）を、実物（`engine_tuner_gen.py` `sample_regime_build`・`observe_diag.py` L363-371・L5439-5455）で確かめ、違う所を直す。**1回目で根拠ありとなった法則に絞って数え直す。**あわせて、一例（RG-v6・1回目の依頼書の事実データ4＝ロジックの逐語と、13要素の「書けるか」の表）が満たす法則との差を1件ずつ示す。13要素の表で ❌ の3件（束ねる・連動する閾値・成立時の価格を覚える）が § 案のどの行で足されるか、足されていないなら欠けている行として挙げる。★差を埋める提案は「例の定数を持ち込む」形でなく「何を測る決まりか・その値は engine_tuner が範囲から探す」の形で（#23）。

### Q-E — やることリストの作り直しは道になるか（★主題）

§ 案（M2-12・M2-13・M2-11-0）は、1回目の結果と Q-C・Q-D に照らして、**根拠ありの法則で「ある程度」効く判定を engine_tuner が見つけて提案する道になるか。名ばかりの行・欠けている行・順番の誤りを断言する。**特に「起案 CC が自分で疑っていること」①〜④に1件ずつ答える。**★あわせて、§ 案を全部 実装し終えたとき、engine_tuner が一例（RG-v6）と同じ水準のロジック（上位足の帯・状態を保つ・解除の条件・否定を持つ）を自分で出力できる状態になるかを断言する。**ならないなら、どの行が足りないかを挙げる（★例の定数を持ち込む形でなく「何を測る仕組みか」の形で）。
