## 監査観点 (本監査固有・Q1-Q5)

### Q1 — 絞ること自体の妥当性

**読み込む指標を 249種 → 68種（部品 551 → 147）に絞ることは、engine_tuner の目的（net を最大にする条件の組み合わせを見つける）に対して、得か損か。**

verify すべき事項＝①探索する候補を減らすことが過剰最適化を減らす方向に働く根拠（業界・学術）②逆に「本来 net を出せた条件を永久に組めなくする」危険の大きさ ③絞る基準を `ta` の43種（業界の定番ライブラリ）にすることの妥当性。**「まこさんが決めたから妥当」で済ませないこと。**

### Q2 — 起案 CC の案の誤り・抜け・矛盾

**下の §案 を1件ずつ検分し、誤り・抜け・矛盾を挙げること。**

特に verify すべき事項＝①「型の表を減らさない」案（取り下げ済み）が、本当に誤りだったか。取り下げが正しいか ②`addf` の1か所で絞る作りに穴はないか（`build_catalog` の外に部品を作る道が無いか）③型の表・`materials.md`・成績表の3つが自動で追随するという主張が本当か。

### Q3 — オン・オフの粒度

**オン・オフの単位を「指標の種類」（例＝ADX を丸ごと）にする案でよいか。**

verify すべき事項＝①時間足ごと（1m〜1d の11本）にも切り替えが要るか ②パラメータごと（ADX7 と ADX14 を別に）はどうか ③走行時間を減らす目的に対し、どの粒度が一番 効くか（部品551 × 時間足11 ＝ 6061列 のどこが重いか）。

### Q4 — `ta` の43種と、うちの材料の対応づけ

**起案 CC は、43種のうち機械で当たったのは26種だけで、残りは名前を見て人（CC）が当てた。**

verify すべき事項＝①この対応づけに誤りがあるか（例＝`UlcerIndex`→`UI`／`AroonIndicator`→`AROONU`・`AROOND`・`AROONOSC`）②機械だけで当てる方法があるか ③「材料に対応が無い5件」（AccDist・WilliamsR・CumulativeReturn・DailyLogReturn・DailyReturn）を足すべきか。

### Q5 — 既定値

**これから新しい指標が材料に増えたとき、既定を「使う」と「使わない」のどちらにすべきか。**

verify すべき事項＝①どちらが事故を防ぐか ②既定「使わない」にした場合、足した指標が誰にも気づかれないまま眠る危険をどう塞ぐか。

## § 案（★これは起案 CC の案であって、事実ではない。監査は この案に引きずられないこと）

1. **オン・オフの表を `observe_config.json` に持つ。**指標の種類ごとに1行（例＝`"ADX": true`）。**行は機械が書き出す**（`indicator_reference_diag.REFS` の全 family）。まこさんは true / false の値だけを変える。
2. **`build_catalog` の `addf` の入口で、false の指標を飛ばす**（足すのは1か所）。`add` は呼ばれていないので対象外。
3. **初期値は機械で作る**＝`ta` の43種の対応づけ ＋ `regime_laws.json` が名指しする指標だけ true。それ以外は false。
4. **型の表・`materials.md`・成績表は、同じ `build_catalog` から作られるので自動で追随する。**型の表が変わるので、まこさんの `--approve` と、印（G2 → H2）の取り直しが要る。
5. **恒等の確認**＝表を全部 true にすると、部品が 551種に戻る（いまと1バイトも変わらない）ことを実測する。
6. **fail-closed**＝表に無い指標名を書くと止まる（打ち間違いを黙って通さない）。
