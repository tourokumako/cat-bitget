## 結論（先に3行）

- **Verdict: GO**（強制は設計できる。核は下の E1・E2・E3 の3件＝Critical）
- **強制の核＝「目隠しの回収試験」**。合成データに、機械には教えていない「稼げるルール」を植え込み、engine_tuner が**自力でそれを見つけ出せるか**を、実データの本走の前に毎回 機械で検査する。見つけられない器は本走も「完了」の報告も物理的にできない。

## ★問いへの答え — どんな強制をすれば、目的に沿った機能を実装させられるのか

**設計の核を1行で。** 目的の文「見つけることができる機械」は**能力の主張**であり、能力は「答えを教えられていない状態で、実際に見つけたか」という**実技試験でしか検査できない**。だから強制の核は、宣言でもチェックリストでも成果物の形式検査でもなく、**目隠しの回収試験を審判格の関所として開発フローの上流に置き、試験に合格するまで実データの本走と「完了」を物理的に許さないこと**。CC がこの試験を攻略する唯一の方法が「本当に見つけられる探索器を作ること」になる（Goodhart の法則への標準対策＝検査の指標を目的そのものに近づける）。

### E1【Critical】能力検収＝目隠しの回収試験（強制の本体）

- **(a) いつ・何を・どう検査するか**
  - **いつ**: ①engine_tuner_gen / engine_tuner_exec に1バイトでも変更を入れた後、実データの本走（--run）の前（既存 pre_run_gate の関門3つと同じ場所に足す）。②「直った」「完了」の報告の前。
  - **何を**: 合成5分足データに**既知の稼げるルール**を植え込む（例＝特定の指標2〜3条件が同時成立した直後に、決まった値動きが起きる系列）。植え込みの仕様（どの指標・どの時間足・どの向き・効果の大きさ）と乱数の種は**実行のたびに乱数で決まる**（またはまこさんが当日 種を1つ言う）＝CC は試験の中身を事前に知り得ない。正解の net（オラクル）＝植え込んだルール自身をレシピとして走らせた審判の機械出力（CC の手書きゼロ）。
  - **どう検査するか**: engine_tuner に植え込みを**教えずに**、宣言済みの試行数で探索させる。**最良候補の net ≥ 正解の net × X%** で合格（X はまこさんが決める・例 50%）。あわせてメタ確認（§2.9③）＝**探索を殺した版（型の表を無効化して乱数選択だけにした版）では必ず不合格になること**を毎回確かめる。落ちなければ試験そのものを不合格にする。
  - この1本の試験が D1（意味の無い空間）・D3（売買ゼロが最良）・D5（OR 不在）・D6（門の不発）・D7（発火の消滅）を**まとめて弾く**。乱数で条件をつなぐだけの器は、植え込んだルールを回収できない（実測の66%は「玉が建つ」であって「見つける」ではない）。売買ゼロを最良に選ぶ器も回収できない。欠陥の字面に合わせた個別検査（案3 の型＝すり抜け可能）が不要になる。
- **(b) 目的のどの部分を担保するか**: 「（指標・閾値・時間足・パラメータの組み合わせを）**見つけることができる**」の能力の床。
- **(c) 担保できない部分（明記）**: **実データに在る未知のエッジを見つけられることは担保しない**（合成の既知ルールは実相場より見つけやすい）。合格の条件（E36＋E38 合算 月 $600）への到達も担保しない。最終の物差しは従来どおり、実データの score.py の net と封印期間と本番だけ。
- **★案4 との違い（まこさんが指摘した矮小化との区別）**: 案4 は「CC が P23 の条件を**手で書き写して**、実行器がそれを再現できるか」＝**書ける**の検査だった。E1 は「機械に答えを**教えずに**、探索が**自力で**見つけるか」＝**見つける**の検査。検査の対象が CC の作業痕ではなく、機械の能力そのもの。
- **実現性の根拠（内部の実測）**: このプロジェクトで実際に機能した検査は全部この型＝既知答えテスト（eval_engine 9/9・BH 法の既知答え・tuner_stats ⑨⑩⑪）と番人のメタ確認（2026-08-06 に CC 自身の誤りを3件 実際に捕まえた＝worklog §2）。宣言・チェックリスト型は1件も捕まえていない（false_positive §3＝内部発見ゼロ）。

### E2【Critical】完成の条件の「出所」を CC から剥がす（不正2＝自分で条件を引いて自分で満たす、の構造閉鎖）

- **(a)**: **いつ**＝完成の条件・検収の条件を書き足す／変えるとき（engine_tuner_requirements.json を変えるとき）。**何を**＝完成の条件の各項目に「合否の数値の出所」の欄を必須にし、許す出所を4つに限定する＝①E1 の正解 net ②score.py 系の審判の実測 ③台帳の機械可読の値（ROLE_FLOOR 等）④まこさんの逐語（日付つき）。**どう検査**＝gen_engine_tuner_requirements.py の生成時 verify に機械検査を足す。出所の無い条件（「表現できる」「機械出力が出る」だけの条件）は**文書の生成そのものが止まる**。
- これは「チェックリストを増やす」ではない。**条件を書く権限の構造を変える**。実現性はこのリポジトリで実証済み＝fix_map の出典照合は実際の改変を2回 止めた（4-15 の逐語の消滅・periods.py の窓変更）。同じ機構に載せる。
- **(b)**: 「条件を満たしたのに目的に届かない」（照合3＝9項目が全部 表現の検査だった）の再発防止。
- **(c) 担保できない**: 条件の**網羅性**（要る条件が全部あるか）は機械では担保できない。非同型レビュー（Web Claude）とまこさんの発注で補う。

### E3【Critical】型の表を生成の物理制約にする（D1 の直しを「強制」の形で言ったもの）
