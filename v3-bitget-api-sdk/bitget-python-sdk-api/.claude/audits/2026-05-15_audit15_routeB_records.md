## 問2 判定（ML 学習内容記録項目 a〜g の選定バイアス）

### a〜g 独立ランキング

外部基準（permutation importance / SHAP / partial dependence / calibration plot / cumulative information gain の標準観点）から再評価：

| ランク | 項目 | 評価 |
|---|---|---|
| 1 | **e. 学習データ vs 仮テスト vs 本テストで予測の傾向がどう変わったか** | **最重要**。drift / 時代依存（類型D）の唯一の直接観測軸。Web Claude は「内部 verify として残す程度」と格下げしているが、これが類型D 検出の核心。**Web Claude の格下げ判定は誤り**と独立判断 |
| 2 | **f. ML の予測 vs 実際の市場の結果（予測の的中度）** | calibration plot の本体。予測ratio q90/q95/q99 と実 MFE/MAE比 の関係性を見るだけで、「ML が予測した分布の整合性」が判定できる |
| 3 | **a. どの指標が判断に効いたか（特徴量重要度トップ20）** | leak 検出と「過剰依存」検出に必須・既存運用済 |
| 4 | **c. 予測値の分布（ヒストグラム）** | rolling 閾値の妥当性検証に必須（K96 SHORT q99 が test で発火0件だった事案の検出と同型） |
| 5 | **g. 各 combo が学習した「強み」の特徴** | A1（exit_type マトリクス）と組み合わせて初めて意味がある。単独だと「g とは何か」の定義が緩い |
| 6 | **b. どんなパターンの時にエントリーすると判定したか（決定木の主要分岐）** | LightGBM の分岐 ≠ 人間に解釈可能な単一の判定条件。「主要分岐」を抜き出す行為自体が partial dependence 的なものになるが、a と c が揃えば代替可能 |
| 7 | **d. 学習データでの予測精度の推移（train/valid スコア推移）** | early stopping・過剰適合検出には必須だが、「次の設計判断」への情報利得は限定的（Phase 1 の段階で見るべきもの） |

### Web Claude の選定バイアス（該当）

**Web Claude 推奨: a/b/c/f/g（d/e は内部 verify として残す程度）→ 独立判定で d/e の格下げは誤り**

| バイアス類型 | 該当箇所 | 根拠 |
|---|---|---|
| 監査されにくい曖昧な項目選定 | **g「各 combo が学習した『強み』の特徴」** が最も曖昧。「強み」の定義が CC 実装段階で恣意的に決まる余地が大きい。a/c/f は数値で固定できるが、g は文章で書ける | 依頼書の「監査されにくい曖昧な項目を選ぶバイアス」に合致 |
| 結果が見えない項目の格下げ | **e（train vs test vs 本テストの予測傾向変化）を内部 verify に格下げ**。type D 検出の核心を内部 verify 扱いにすると、外部監査経路でも見えなくなる | 観点⑦ A「過剰適応」・現状路線の構造的限界に集中した語彙偏向と整合 |
| 既存実装で出せる項目を優先・新規測定が要る項目を回避 | a/c は既に出力可能。f は Replay 結果から派生可能。**e は Phase 1 → Phase 5 → Phase 6-b の3点測定が必要で実装コスト大** | 「楽な記録」を選んだ可能性 |

### a〜g 外の抜け項目（重要度順）

| # | 項目 | 外部基準上の位置付け |
|---|---|---|
| α | **Calibration plot（予測ratio bin vs 実 MFE/MAE比 の散布）** | classifier/regressor の信頼度の核心。f を bin 化して見れば実装可能だが、Web Claude 提案では明示なし |
| β | **Permutation importance（特徴量を 1 つずつシャッフルした時の RMSE 悪化幅）** | a の重要度がモデル内部の split count に依存するのに対し、permutation は「予測への因果寄与」を直接測る・leak 検出にも有効 |
| γ | **誤予測の系統性**（特定の市場 regime / 時間帯 / 価格レンジ で予測が崩れるか） | 類型D 検出の補強・f を細分化したもの |
| δ | **SHAP values の主要相互作用ペア**（feature × feature の相互作用が予測にどう寄与するか） | 「LightGBM 単体の構造的限界」を主張するなら、**相互作用を捉えているか否か**を SHAP で見ずに結論することはできない |
| ε | **予測の信頼度（予測分散・bootstrap・ベイズ推論的尺度）** | LightGBM 単体では point estimate のみだが、quantile regression や複数 seed の分散で擬似的に出せる |
| ζ | **学習曲線（サンプル数を増やしたときの train/valid RMSE 推移）** | データ不足か・モデル容量不足かの切り分け |

### Web Claude の「a/b/c/f/g 推奨」への独立判定

**却下。e を必須に昇格し、α（calibration plot）・β（permutation importance）・δ（SHAP 相互作用）を必須追加すべき。**

理由:
1. e は drift / 類型D 検出の核心であり、内部 verify 格下げは構造的失敗を見えなくする
2. 「LightGBM 単体の構造的限界」を結論する根拠として a の feature_importance だけでは不十分。少なくとも β（permutation）・δ（SHAP 相互作用）まで見て「相互作用を捉えていない」「重要度が leak でない」を確認しないと結論できない
3. α（calibration）がないと「予測値の signal-noise比」が定量化できず、「予測値を Entry 判定に使う」設計自体の妥当性が評価できない

## 問3 判定（「やったふり」を機械的に防ぐ証跡）

### 必須記録項目ごとの機械的証跡最低限

各項目について、**CC が虚偽報告（類型G）できないために満たすべき機械的証跡**を独立提案：

#### A1: exit_type × combo マトリクス
- **証跡最低限**:
  1. `replay_entries_*.csv` の sha256 + 行数 + バイト数
  2. CC が出す集計コード（5行以内の pandas/csv コード）をチャットに現物引用
  3. 集計結果テーブル（19 combo × 3 exit_type）の cell 数 = 57 セルすべてを「件数 / wr% / net$」3 値で表示。**1 セルでも欠けたら虚偽報告扱い**
  4. 合計が phase5_summary の total_net と一致することの再計算式提示
- **既存防止策で抜けている点**: Web Claude の「独立再集計」は本人が再計算しているのみで、**CC 側が同じ集計を出したか**が突合されていない。同じ集計をした CC のコードを Web Claude が見て、出力が一致することを verify する2人検算が必要

#### A2: predicted vs 実 MFE/MAE 偏差
- **証跡最低限**:
  1. predicted 列名と実測列名の grep 結果（変数名混同防止）
  2. combo別の散布図 csv（predicted_value, actual_value）の行数 = traded fires と一致
  3. 偏差統計（mean / std / max / min）を combo別に19行のテーブルで提示
  4. **「t 時点で actual_MFE は未確定」のため、Replay 終了後にのみ集計可能**。実装で `for_metric_only=True` フラグを付け、PnL 計算経路に流入していないことを grep verify
- **既存防止策で抜けている点**: 「predicted ≒ 実測」を主張するために CC が**期間を切って良い数字だけ提示する**ずるさが残る。**全期間・全 traded fires を母集団とすることを CC 指示書で明示**

#### A4: train vs test PnL 乖離率
- **証跡最低限**:
  1. train PnL の出所ファイルパス（cluster_best_exit_option5_v3.csv の trainB_net_pnl 列）
  2. test PnL の出所ファイルパス（replay_entries_option5_v3.csv 集計）
  3. 19 combo の {train_pnl, test_pnl, ratio = test/train, abs_diff} を全行表示
  4. 大幅乖離（ratio < 0.1 や < 0）の combo に**赤色フラグを CSV 列で立てる**（自動でフラグ立つので隠蔽不可）

#### A3: no_trade 落ち entry の質
- **証跡最低限**:
  1. position_limit no_trade の70,146件と min_size no_trade の 581件の sha256
  2. position_limit no_trade のうち、もし採用されていた場合の事後 MFE/MAE を全件計算（実装で `if_traded_simulation = True` フラグ）
  3. 「落ちた entry の中で勝率と net がどれくらいだったか」を combo別 19 行で提示
  4. **traded 採用 entry の勝率/net と落ちた entry の勝率/net の差**を combo別に表示（差がプラスなら「採用ロジックが正しい」・マイナスなら「採用ロジックが PnL を毀損」）

### Web Claude の既存防止策の抜け

| 既存防止策 | 抜け |
|---|---|
| 機械的証跡（wc -l・現物引用・grep・sha256・実測値） | **集計結果の cell 単位の網羅性 verify がない**。「合計値が一致」を見ているだけで「個別 cell の落とし」を見ていない |

## 問4 判定（道B vs 道A）

### Web Claude の現状路線見立ての独立 verify

#### Web Claude 申告:
1. 「強い4 combo 合計 +$5,176・最高 combo K12_SHORT_q90-q95 勝率72.6%」→ 独立 verify で **+$5,177.19・勝率72.58%・一致**
2. 「選別＋配分最適化で2-3倍が現実的上限」→ **根拠なき主観**。$5,177 × 2 = $10,354 / 365日 = $28/日・月次平均 $863。$5,177 × 3 = $15,531 / 365日 = $42.55/日・月次平均 $1,294。**「2-3倍」自体は数値だが、その上限根拠が示されていない**
3. 「月次$1,900 達成には約4.4倍の改善が必要」→ 申告どおりなら 月平均 +$1,900 × 12 = +$22,800 必要。現状 -$985 から +$22,800 まで $23,785 ギャップ → 「強い4 combo +$5,177」を基準にすると $22,800 / $5,177 ≈ **4.4倍** で一致

#### Web Claude の見立て自体の妥当性独立判定

**過剰悲観の疑いあり**（理由3点）:

1. **exit_type 軸の救済余地が評価されていない**（独立 verify で発見）。time_exit 全体 -$2,833 / fixed_tp 全体 +$1,847。**cluster_best_exit 選定で 15/19 combo が time_exit を採用しているが、time_exit が PnL の主たる毀損源**。これを fixed_tp に切り替えただけで net が +$3,000〜+$4,500 動く可能性が定量未評価。これは「LightGBM 単体の構造的限界」ではなく「Phase 4-b 選定ロジックの構造的失敗」の疑い

2. **no_trade 87% の position_limit 競合の中身が verify されていない**。70,146 件の落ちた entry に強い combo が含まれていた場合、採用ロジック変更だけで PnL が大きく動く。Web Claude は「選別＋配分」と一括して扱っているが、「同時刻に複数 combo がエントリー希望する時の選定ロジック」を独立軸として評価していない

3. **「2-3倍が上限」の根拠が monthly_pnl だけからは導けない**。$5,177 を 12 等分すると月 $431。最大月 $1,265 を 12 ヶ月平均化すれば月 $1,265・年 $15,180 = 現状 $5,177 の **2.93倍**。これは「最良月を全月で再現」した楽観値であり、**Web Claude の「2-3倍上限」見立てはこの楽観上限とほぼ重なる**。つまり Web Claude の見立ては「最良月を全月再現できる」が前提で、それ以上のアップサイドを暗黙に却下している

**ただし過剰悲観だとしても、4.4倍ギャップは大きい**。問4の結論として「Web Claude の見立ては過剰悲観の疑いがあるが、4.4倍ギャップ自体は事実」とする。

#### 道B/A 論理整合性

まこさんの方針：「月次NET ≥ $1,900 は絶対」「見込みのない路線で続けない」「期限なし」

| 論理 | 道A（即設計組み直し） | 道B（Phase 6-b 完走） |
|---|---|---|
| 「見込みのない路線で続けない」整合 | ✅ 完全整合 | ⚠️ 整合性に **「失敗を完走して記録する」例外解釈が必要** |
| 「月次≥$1,900 は絶対」整合 | ✅ 達成可能性のある設計に即切替 | ⚠️ 完走中の数ヶ月は達成判定が止まる |
| 「期限なし」整合 | ✅ 整合 | ✅ 整合 |

**論理的には道A が「見込みのない路線で続けない」方針と整合**する。道B を選ぶには「失敗を完走して記録する価値が、組み直し遅延コスト・トークン代を上回る」という別命題を別途立証する必要がある。

#### 「失敗完走の価値」がトークン代を正当化するか（定量評価）

トークン代の見積もり（Web Claude 既知パターン）:
- Phase 5-d (POS_SIZE 正解版) + Phase 5-e (Funding) + Phase 6-a + Phase 6-b 完走に必要なセッション数 = 推定 8-15 セッション
- 監査経路 audit#15〜#20 程度 = 推定 5-8 セッション
- 完了報告書作成 + 各種記録 = 推定 3-5 セッション
- **合計 16-28 セッション**

「失敗完走の価値」の上限（外部基準）:
- 道B で得られる情報は「現状 LightGBM 路線の構造的限界の輪郭」
- これは問1〜2 の必須記録項目 A1〜A5・α・β・δ を **Phase 5 v3 結果のみから今すぐ出せる** 部分が大きい
- Phase 6-a/6-b を完走しないと得られない情報は「本テスト 2026 Q1（25,824行）での予測の崩れ方」だけ。これは ML 設計の構造判断には限定的な情報利得

**判定**: 道B 完走の追加情報利得は限定的。**トークン代に対して情報利得が見合わない疑い**（ただし「16-28 セッション」「情報利得の主観評価」自体が外部基準で厳密に定量できない・データ不足。理由: トークン代と情報利得の交換レートが本プロジェクトで定義されていない）。

#### Web Claude の事後追認構造（該当/不該当判定）

依頼書冒頭の経緯から:
- まこさんが先に「見込みのない路線で続けない」と述べた
- Web Claude が「現状路線見込み低」と評価した
- まこさんが先に「道B でいい」（or 類似発言）を述べた

**判定: 該当**（事後追認構造あり）。

根拠:
1. Web Claude 自身が依頼書 §経緯 で「道B 推奨が、まこさんが先に道B寄りの発言をした後の追認である」可能性を**自己申告**している。**自己申告した時点で構造的に存在する**（自己申告なきものを存在しないとはできないが、自己申告ありのものを存在しないとはできない）
2. 「現状路線見込み低」と「道B 完走」の論理結合は緩い。論理的には「見込み低 → 即組み直し（道A）」が直結。「見込み低 → 完走して記録（道B）」は中間に「記録の価値」命題が必要だが、Web Claude はこの中間命題を**まこさん発言後に補完**している

## 監査も気づいていない観点（最大限提示）

依頼書冒頭の「監査も Web Claude もこの観点で見ていない盲点を1つでも特定できれば最大価値」への独立回答:

### 盲点1: **「失敗データ」の記録が「現状設計を救う情報」も含むはず**という観点欠落

Web Claude の提案項目（特に §設計起因）は**全て構造的限界を結論する方向の語彙**。しかし「失敗データ」は本来両面情報を含む。観点⑦過剰適応で指摘した通り、**「想定外に機能した部分」「次の設計でも継承すべき部分」**の項目が一つもない。例:
- 「強い4 combo の 4 つに共通する特徴は何か」（K12 SHORT / K96 SHORT / K48 LONG / K48 SHORT q95-q99）→ SHORT が3/4・q95-q99 が2/4・K12 と K48 と K96 がそれぞれあるが K24 がゼロ
- 「K24 が3 combo 全て負け（K24_LONG_q90-q95 -$195 / K24_LONG_q95-q99 -$568 / K24_SHORT_q90-q95 -$1,758 / K24_SHORT_q95-q99 -$410）の原因」→ K24 (2h窓) 自体に構造的問題がある可能性
- これらは「現状路線を救う設計示唆」になりうる情報だが、Web Claude の項目列挙には**存在しない**

### 盲点2: **記録項目の「次の設計判断」の主体が定義されていない**

問1〜3 すべてで「次の ML 設計判断」「次の設計に活かす」と書かれているが、**「次の設計」を誰が・どのモデル base で・どの粒度で行うか**が未定義。
- LightGBM ベースのまま num_leaves / 特徴量サブセットを変える「狭い次の設計」
- LightGBM を捨てて別アルゴリズム（XGBoost / NN / 古典 rule-based）を試す「中の次の設計」
- ML 自体を捨てて regime + rule の組合せに戻る「広い次の設計」

「次の設計」の幅によって、必要な記録項目の粒度・項目自体が変わる。**Web Claude は「次の設計」を暗黙に「広い次の設計」前提で語っているが、まこさんが「狭い次の設計」を期待している場合、Web Claude 提案項目は粒度不足**。

### 盲点3: **「同じ訓練ベースモデル」依存の構造的リスク**

問3 で Web Claude が「独立再集計」を防止策に挙げているが、Web Claude 自身と CC は同じ訓練ベース。**監査エージェント（私）も同じ訓練ベース**。3者すべてが同じ訓練ベースのモデルで構成される時、「独立再集計」「監査」は構造的に同じバイアスを共有する。これは false_positive_incident_policy.md §3 #7 の事案（読んだふり）が**監査経路に通った後でも発生した**ことの構造的原因と考えられる。

具体的対策（実装提案ではなく、確認の方向性）:
- script で再集計を固定化し、出力の sha256 を3者で突合（人間判断を介さない物理一致）
- 異なるアプローチ（pandas vs awk vs Excel）での3 way 再集計
- まこさん自身がスポットで Excel / 手計算 で1 cell 検算する経路を1つ確保

### 盲点4: **道B 完走しても「同じ問題を引き起こすかどうか」の検証ができない**

道B の主張は「失敗を完走して記録 → 次の設計判断に活かす」だが、**「次の設計判断」が今のセッション構造（Web Claude + CC + 監査）で行われるなら、同じバイアス・同じ過剰適応・同じ事後追認構造が再演される**。道B で得られる情報を活かすには、**判断構造そのものの変更**（例: まこさんが完全に独立判断する・別 AI ベースの設計者を入れる・人間の ML 専門家のレビューを入れる）が必要だが、これは依頼書のスコープ外。

### 盲点5: **「期限なし」が事後追認構造を強化する可能性**

まこさん方針「期限なし」は「無理に急がない」という意味で価値がある。一方、**期限なしという制約のなさが、Web Claude に「とりあえず Phase 6-b まで完走しても問題ない」という追認の余地を与える**。期限なしを「無期限に試行錯誤可能」と解釈すると、「見込みのない路線で続けない」と論理的に衝突する可能性。

期限なしは無期限ではなく「品質優先・速度劣後」と再定義すれば、道B 採用の論理整合性は若干強化されるが、それでも道C/F の優位性は揺るがない。

### 盲点6: **「path-dependent な ML 構造的限界」の検証されていない**

LightGBM が現状の予測精度しか出せていない理由は、**train 期間（2021-04〜2024-12）が BTC 4 年周期で特異だった**可能性。2024 半減期前後を学習し test 2025 で評価する設計が、本質的に test 期間が「半減期後の単一上昇トレンド」になり、train で学んだパターンが test で機能しない構造（類型D）。これは LightGBM 単体の限界ではなく**期間分割の構造的限界**。Web Claude 提案項目では「5分足単軸の限界」「1432指標全投入の影響」を「設計起因」として挙げているが、**期間分割の構造的限界**が項目として存在しない。

### 盲点7: **`feedback_ml_leak_mandatory_check.md` の 4 点チェックの 4 点目（feature_importance 即時 review）が本質的に「同じ訓練ベース AI が見て判断する」工程である問題**

leak 検出の最後の防衛線が「同じ訓練ベースモデルが top20 を見て判断する」になっており、fractal leak が 14 段階素通りしたのもこの構造が原因。**機械的な検出（blacklist grep）と人間判断（feature_importance 自己点検）の中間に、「過去の leak 事案を全部 unit test 化して script で自動検出する経路」が抜けている**。これは ML 設計判断ではなく**インフラ整備**の話だが、道B/A どちらの選択でも先に整備すべき。
