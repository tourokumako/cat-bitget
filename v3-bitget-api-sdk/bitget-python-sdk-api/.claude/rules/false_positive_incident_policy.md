## 1. なぜこれが最重大なのか

このプロジェクトの目的は「本番で実資金を毀損しない BOT」である。エラーには 2 種類ある。

| エラー種別 | 資金への影響 |
|---|---|
| 未達が出る（「$1,900 に届かない」と正直に出る） | **資金を溶かさない。** まこさんはその数字を見て「本番に出さない」と正しく判断できる |
| 虚偽達成・虚偽報告が出る（leak・トリック・計算ミス・読んだふりで「達成」「確認済」が出る） | **資金を溶かす。** まこさんはその数字・報告を信じて本番投入し、市場に達成構造が存在しないため資金が毀損する |

**未達は事故ではない。虚偽達成・虚偽報告だけが、エラーの中で唯一「実資金毀損」に直接つながる。** だからこれを最重大インシデントとして扱う。「学習結果」「次の一手」「proxy」「近似」といった軽い語で流すことを禁止する。

## 2. インシデントの定義（類型）

実態より良い数字が出ること、および実態と異なる報告をすること。発生源を問わない。

### 類型 A: 未来データ・未来ラベル参照（look-ahead leak）
MFE/MAE 等の未来由来値を Entry/Exit/Replay/PnL 計算に使う。特徴量計算での `.shift(-)` / `j+1,j+2` / `center=True`。
発見方法: 変数名 grep だけでは名前変更で素通りするため、**PnL・判定の計算式の入力変数を列挙し、各変数が推論時点 t で因果的に存在するかを1行ずつ宣言**して確認する。

### 類型 B: バックテスト固有のトリック
期間全体ソートでの採用判定（L-182）、test データへの fit / idxmax（L-183）、生存バイアス、out-of-sample 合格を「leak なし」の証拠と誤認すること。
発見方法: fit/apply 分離の確認、採用ロジックが train 内で閉じているかの確認。

### 類型 C: 多重検定・パラメータ過剰最適化（leak なしでも発生する）
多数のパラメータ組合せをスキャンして「たまたま良かった」ものを選ぶ（データスヌーピング）。合格基準を結果確認後に変更する（L-190）。これらは grep で検出できない。
発見方法: 探索した組合せ総数と採用数の比、IS/OOS 乖離、基準が結果確認前に確定していたかの確認。

### 類型 D: レジーム過依存・時代依存（leak なしでも発生する）
train 期間特有の市場環境にのみ機能する規則を学習する。K96 SHORT q99 の暴騰局面集中（L-189）が該当。
発見方法: 月別・レジーム別の成績分散、test 2025 と test 2026 Q1 の単価あたり成績の乖離（auditor_template.md ①D 参照）。

### 類型 E: 単純な計算・集計ミス
手数料/Funding/スリッページの控除漏れ（グロスを NET と取り違える）、ポジションサイズの解釈違い（1 trade vs 合計上限）、丸め・単位・期間範囲の取り違え。
発見方法: 列名を信用せず実装で控除を確認、独立再集計。

### 類型 F: proxy と称した未来流用
「理想的な挙動を仮定」「近似」という名目で、実際には因果的に再現不可能な数字を出すこと。類型 A の言い換えによる重大度の偽装。

### 類型 G: 虚偽報告（読んだふり・確認したふり・完了したふり）
読んでいない正本を「読んだ」と述べる。verify していないものを「確認済」と述べる。実行していない手順を「完了」と述べる。
2026-05-15: Web Claude が `/mnt/project/` の正本を grep と部分 view で済ませ「全文読んだ」と複数回述べた。まこさんは毎回正本を同期し直しており、読んだふりはその信頼を直接裏切る。
発見方法: 自己申告を信用せず、機械的証跡（`wc -l`・位置指定の現物引用・grep 結果・sha256・`ls` 実在確認）を要求する。証跡なき「読んだ」「確認した」「完了した」は虚偽報告として扱う。

**疑わしい段階でインシデント扱いする。** 「proxy かもしれない」「丸めかもしれない」と軽い語に逃げない。確定するまで疑いとして最上位で扱う。

## 4. 発見時の強制手順

虚偽達成・虚偽報告インシデント（疑いを含む）が発見されたら、以下を順に実行する。順序を飛ばさない。

### Step 1: 即時 STOP・報告（報告先行）
- 進行中の作業を即時停止する。
- **まず報告する。** まこさんに「インシデントの疑いが発生した」と明示的に上げる。何が・どこで・どの数字/報告が疑わしいかを1〜3行で。報告を後回しにして自分で調べ始めない。Web Claude / CC が「自分で解決してから報告」しようとする動きを禁止する。早く上げるほど資金毀損から遠ざかる。
- 「合格」「達成」「確認済」「完了」という語を、原因が確定するまで一切使わない。

### Step 2: 監査チェック（範囲特定）
- 監査経路に回し、独立再現でインシデントの**波及範囲**を特定させる。
- 波及範囲は発見時点の見た目より広いと想定する（audit#12: Phase 5 だけと思ったら Phase 4-b の選定ロジックごと無効だった）。「該当 Phase だけ」と狭く見積もらない。
- 該当する過去成果物は、範囲が確定するまで「信頼性疑義」として扱う。

### Step 3: 都度判断（継続可否）
- 監査が特定した範囲に基づき、リカバリ可否・継続可否を**まこさんが**判断する。Web Claude が独断で「継続できる」と決めない。
- リカバリ可能なら：修正 → 再 verify（leak なら再 leak verify、虚偽報告なら機械的証跡の再取得）→ 監査再確認 → 継続。
- リカバリで足りないなら：該当成果物を `archive/` へ移動し、無効化を WORKFLOW.md に明記してやり直し。

### Step 4: 記録・防止策
- インシデントを記録する。単発の詳細は `leak_incident_YYYYMMDD.md` 形式、教訓は `lessons_active.md` に L-番号で。本ファイル §3 の再発記録表にも1行追記する（発見者・内部チェック失敗の原因の列を必ず埋める）。
- **再発防止策をセットで残す。** 「気をつける」では不可。物理的に同じミスを起こせない関所（§5）を1つ以上追加する。
- 「学習結果」として流して終わりにしない。インシデントとして扱った証跡を残す。
- web_claude_self_check.md のどのチェック項目がなぜ機能しなかったかを当該ファイルに追記し、項目を改訂する（有効性検証ループ）。

## 5. 防止の関所（文書だけにしない部分）

文書を増やすだけでは再発を止められない（L-159/L-160 を追加して1日で再発した前例あり）。以下の構造的関所で、虚偽達成・虚偽報告が混じったまま先に進めない状態を作る。

### 関所 A: 異常値の自動 STOP（数値条件・主観語を排除）
完了報告を受け取ったら、以下を無条件で確認する。いずれか1つでも該当したら「合格」と呼ばず自動で虚偽達成調査（§4）に入る：
- ① 勝率 > 70%
- ② 月次 NET > $3,800（合格ライン $1,900 の2倍）
- ③ IS/OOS の Sharpe 比 > 3倍乖離
- ④ 最大ドローダウンが月次 NET の 10% 未満
「桁違い」「大きく超える」等の主観語は使わない。CC は異常値が出たら完了報告に「合格」と書かず「異常値・要調査」と書く。

### 関所 B: 全工程の未来参照 verify（変数名でなく因果性で見る）
leak チェックを「ML 特徴量」に限定しない。**Entry / Exit / Replay / PnL 計算のすべて**で「未来データ・未来ラベルを参照していないか」を verify し、完了報告必須証跡に含める。
変数名 grep（`mfe_te[i]` 等）だけでは名前変更で素通りするため、**PnL・判定の計算式の入力変数を列挙させ、各変数が推論時点 t で因果的に存在するかを1行ずつ宣言させる**。

### 関所 C: NET の実体 verify
`net_pnl` 等の列名が「net」でも、中身がコスト控除後である保証にはならない。手数料・Funding・スリッページが exchange_spec.md 確定値で実際に控除されているかを verify する。

### 関所 D: 重大数字は監査経路を必ず通す
「達成」「合格」に関わる数字は、Web Claude と CC の2者だけで確定させない。第三者（監査）の独立再現を関所にする。
監査経路を、まこさんの一言・急ぎ・勢いを理由に飛ばさない。飛ばしたくなったときこそ通す。

### 関所 E: 報告先行
インシデントの疑いが出たら、調べる前にまず報告（§4 Step 1）。Web Claude / CC が「自分で解決してから報告」しようとする動きを禁止する。

### 関所 F: 読了の機械的証跡（虚偽報告＝類型 G の防止）
正本を「読んだ」と述べるには、機械的証跡（`wc -l` の総行数・総行数から算出した位置指定の現物引用・決定的事実の1行要約）をチャットに出す。証跡なき「読んだ」は虚偽報告として扱う。詳細は web_claude_self_check.md「読了ゲート」。
同様に「確認した」には grep 結果・sha256・`ls` 実在確認を、「完了した」には実行ログを伴わせる。

### 関所 G: チェックリストの有効性検証ループ
「チェックリストを通過したのにインシデントが発生した」場合、どのチェック項目がなぜ機能しなかったかを web_claude_self_check.md に追記し、当該項目を改訂する。チェックリストは固定資産ではなく、すり抜けるたびに穴を塞ぐ。
