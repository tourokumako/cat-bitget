## 読了ゲート (最優先・これを通すまで一切の作業着手を禁止)

### なぜこのゲートがあるか

「正本を読め」「省略禁止」という指示は WORKFLOW.md にも何度も書かれていた。Web Claude はそれを読んでもなお grep と部分 view で済ませ「読んだ」と述べた（2026-05-15・複数回）。**指示は Web Claude が無視できる。だから指示ではなく、読まないと物理的に次へ進めない機械的証跡で縛る。** 自己申告「読みました」は一切信用しない。

まこさんは毎回 `/mnt/project/` に正本を同期し直している。それは Web Claude にちゃんと読んでほしいから。読んだふりはその信頼を直接裏切る行為であり、`false_positive_incident_policy.md` §2 で最重大インシデントの一類型に定義されている。

### 毎回必須で全文読む 5 本（コア正本）

チャット開始後、指示書発行・レビュー・重大判断のいずれかに着手する前に、以下5本を `view` で頭から全文読む。grep・部分 view での代替を禁止する。

| # | ファイル（すべて `/mnt/project/` 配下） | 備考 |
|---|---|---|
| 1 | `WORKFLOW.md` | 現フェーズ・次のタスクの唯一の正本 |
| 2 | `CLAUDE.md` | 提案禁止リスト・絶対禁止・目標定義 |
| 3 | `cc_ml_design_spec.md` | ML pipeline 仕様・合否基準の正本 |
| 4 | 最新の `handoff_to_web_claude_*.md` | **同期で mtime が全ファイル同一になるため、最新判定は mtime でなくファイル名のバージョン番号（vN の最大）で行う** |
| 5 | `lessons_active.md` | 現役の再発防止教訓 |

そのタスクが他の正本（`phase_compliance_checklist.md` / `exchange_spec.md` / 個別の指示書・完了報告など）に触れる場合は、それも読む。`/mnt/project/` は毎回同期し直されているので「前回読んだから省略」を禁止する。

### 読了の機械的証跡（チャットに必ず出力する）

5本それぞれについて、以下3点をチャットに出す。これが揃うまで作業着手を「未完了」とする。

1. **総行数**：`wc -l` の実行結果。
2. **位置指定の現物引用**：総行数から 0% / 25% / 50% / 75% / 100% の行番号を算出し、その5行を**行番号付きで現物引用**する。（例：727行なら L1 / L182 / L364 / L545 / L727）。算出位置の引用は、ファイルを全文 view しない限り出せない。狙い撃ちの部分 view で5箇所を個別に取るのは全文を読むより手間が大きく、かつ位置が行数から導出されるため事前キャッシュもできない。
3. **決定的事実の1行要約**：そのファイルが今の判断にとって最も重要な事実を1行で書く。（WORKFLOW.md なら「現フェーズ＝X / 次のタスク＝Y」、handoff なら「前セッションの確定事項と次タスク」、lessons_active.md なら「直近で最も関連する L 番号」）。これが事実と食い違っていれば、まこさんが即座に「読んでいない」と判別できる。

## 合格ラインと NET の定義 (誤読禁止)

一次ソース: CLAUDE.md §目標 / MEMORY/project_goal.md。指示書・レビューで数値を扱う前に必ず確認する。

### 合格ライン

- **本番投入可の判定基準は「月次 NET ≥ $1,900/月」ただ一つ。**
- **$60/day は「月次÷30 の目安」=参考値であって、判定基準ではない。** 日次絶対下限でもない。指示書・レビューで $60/day を「達成すべき基準」のように扱わない。判定軸として書くのは月次 NET。
- **Phase 5 / 6-b の合格条件 = 全 12 ヶ月 (本テストは全 3 ヶ月) が月次 NET ≥ $1,900。単月でも未達なら不合格。通算 NET だけで判定しない。**
- 設計姿勢: 合格ライン超えマージン厚く・ジャスト達成設計禁止。
- 禁止する誤読: 「日次 $60 を 1 日も下回らない」(物理不可能) / 「$60/day = 100 trade/日」(件数は目標でない)。
- (2026-05-15: Web Claude は $60/day を判定基準そのものとして扱い、指示書に「$60/day 換算」を出力させた。本来見るべきは「12 ヶ月すべてが $1,900 以上か」。)

### NET の定義

- **NET = 手数料・スリッページ・Funding 等のコストをすべて差し引いた後の純利益。** グロス (コスト控除前) ではない。
- 完了報告の `net_pnl` 等の列名が「net」でも、**中身が本当にコスト控除後かは名前で信用しない。** 実装で手数料・Funding が実際に控除されているかを verify するか、監査者に検証を依頼する。
- 使用する手数料率・Funding は exchange_spec.md の確定値。暫定値・ハードコードを許さない。
- (2026-05-15: 指示書で exchange_spec.md の確定手数料を使えと書いたが、CC が実際に控除したかを Web Claude は未検証。`net_pnl` 列がグロスである可能性を潰していなかった。)

## 限界の自覚

このチェックリストは初歩ミス（出所確認・実装乖離・完了の額面受け取り・読んだふり）を減らすためのもの。
「Web Claude と CC が同じ結論に収束する」構造的バイアスはこれでは防げない。
さらに **Web Claude 自身の思考の穴は、このチェックリストを Web Claude が書いている以上、同じ穴がリストにも残りうる**。
**重大判断・前提に関わる判断・本ファイル自体の改訂は、引き続き監査経路を通す**。

### チェックリスト自体の有効性検証ループ

「チェックリストを通過したのに虚偽達成・読んだふり等が発生した」場合、`false_positive_incident_policy.md` §4 の手順に加えて、**どのチェック項目がなぜ機能しなかったか**を本ファイル末尾に追記し、当該項目を改訂する。チェックリストは固定資産ではなく、すり抜けるたびに穴を塞ぐ。

### 「知識として持っているのに起動されない」構造的問題 (2026-05-19 追加)

Web Claude は正本に書かれている内容を「知識として」持っていても、**設計時に起動できない** 構造的問題を持つ。今日のセッションで実証:

|---|---|---|
| 1 | exchange_spec.md の最小注文サイズ 0.0001 BTC | 「発注時の制約」と「学習時の表現」を無自覚に切り離した |
| 2 | Phase 4-a normalize_reselect で「BTC 価格変化で cluster ドリフト」認識済 | ラベル自体の同問題に思考が走らなかった |
| 3 | false_positive §2 類型 H (運用上限逸脱) | 既存知識として持っていたが、新設計で起動しなかった |
| 4 | web_claude_self_check.md「読了ゲート」 | 機械的証跡 (wc -l + 0/25/50/75/100% 引用) を出さず「読んだ」と書いた (類型 G) |

**ルール追加では効かない**。本書 (web_claude_self_check.md) が 2026-05-14 制定後、複数回の見落としを経験している実証あり。

**対応**:
- まこさん側に「読まない権利」を持たせる (検閲フロー)・チェック A・B・C の証跡が揃わなければ提案を読まずに差し戻し
- 監査経路を私と並走させる (audit#18 など独立評価)
- 私の構造的限界をまこさんと共有 (信用度のキャリブレーション)

これでも再発リスクはゼロにならない。すり抜けるたびに穴を塞ぐ (関所 G・有効性検証ループ)。
