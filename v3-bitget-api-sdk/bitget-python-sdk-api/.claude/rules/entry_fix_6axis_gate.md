## なぜこのファイルがあるか（読んだフリ・ドリフト防止）

`cc_entry_logic_self_study.md` §18.5 に「Phase 1 v6 6 案全滅の構造的原因 = **6 軸の多様性欠落**」が
既に記録されているのに、CC は新セッションでこれを踏まず、ボラ逃げ等の同型欠陥を**2 回以上再演**した
（L-223 + 2026-05-31 セッション）。原因は「資料を context に入れても CC が錨を下ろさない」構造（execlog
強制ロード済でも踏まなかった実証）。

→ 対策: §18.5 の診断を**文章でなく「✅/⬜ で状態が見えるチェックリスト」に変換**し、Entry 作業を
毎ステップこれに照合する。ドリフトすれば表のどこかが空欄/破損になり、まこさんが即止められる。

⚠️ **重要な設計姿勢（2026-05-31 まこさん指摘）**: 各軸の修正は「捨てる/外す」でなく
**「役割を正す / 多様性を足す」**。結果が出ないからと WebSearch せず反射的に道具を捨てる判断は禁止
（揺れ幅予測を「外す」と誤判断した事案の教訓）。

## 使い方（まこさんが realtime 執行できる）

1. **毎ステップ宣言義務**: Entry の設計/実装を出すとき、CC は必ず「この手は軸 N を閉じる・§18.5 逐語『…』(file:line)」
   と書く。引用なし・軸に紐づかない手は**まこさんが即却下**してよい。
2. **完了の定義**: 6 軸すべてが ✅（証跡つき）になるまで「Entry 修正完了」と言わない。途中で軸が ⬜ なら未完。
3. **再導入禁止**: 閉じた軸を後で壊したら違反（例: 揺れ幅を再び entry 方向スコアの主役に戻す）。
4. **強制ロード**: 本ファイルを SessionStart で強制ロードし、毎セッション冒頭に 6 軸状態を出す
   （= リセットしても ✅/⬜ が引き継がれる）。
5. **まこさん執行**: 「6 軸の状態を見せて」で CC は本表を証跡つきで出す。空欄/根拠なし✅は却下。
